# GitHub 优质项目洞察 · 2026-10-31

> 目标：不是列一份「高星榜」，而是回答三个问题——
> **① 2026 年 GitHub 的势能往哪走；② 哪些项目贴合你的技术栈；③ 哪些仓库真的能提 PR 并且能被合。**
>
> 数据来源：GitHub Search API（带 token）+ 仓库级指标接口，共 **13 组查询、90 个候选画像**。
> 原始数据落盘在 `d:\github\_insight\`（`q_*.json`、`candidates*.json`、`scout.py`、`profile.py`），可复核。

## 〇、先说结论

1. **2026 年的主线只有一个：Agent 基础设施。** 新晋高星榜前 12 名里有 10 个是 agent / skills / harness 类仓库。
2. **"优质"必须拆成三种，混在一起会误判：**
   - **趋势型**（star 涨得猛，但可能只是内容包 / 话题热度）；
   - **可贡献型**（有好上手 issue + 维护活跃 + 许可证干净）；
   - **可复用型**（能直接拿来改造成自己的工具链）。
3. **最贴合你当前处境（Python 后端 + 调度 + Agent）的可贡献标的是 `apache/airflow`**：GFI 110 条、30 天提交 ≥300、Apache-2.0、合并率 84%、外部贡献占 86.9%、中位合并 1.9 小时。
   **但它的 GFI 池已被抢空**：100 条抽样里 25 条已有 open PR、77 条评论里已有人认领、17 条已有 merged PR，近 30 天只开出 1 条新 GFI（见 8.5 / 8.6）——**"指标最好"和"现在能上手"是两件事**。
4. **GFI 数量不等于好标的**：`rtk` GFI 221 但合并率只有 42%、中位 102 小时；`excalidraw` 外部 PR 合并占比 11.1%。判据应是「合并率 + 外部占比 + 耗时」，不是 issue 数量。
5. **2026 年新增两个筛选条件**：**AI 政策**（elasticsearch 明确拒收 LLM 直出 PR，tiptap 要求披露），以及 **`AGENTS.md`/`CLAUDE.md`**——抽查的 11 个仓库里 10 个已带这类文件。
6. **star 已经严重通胀**：`mattpocock/skills` 30.8 万星、`morluto/rea` 41.4 万星，但 30 天提交只有 57 / ≥300。星数反映的是"传播"，不是"工程强度"。
7. **GFI 已经不能当入口**：10 个仓库的 30 天窗口里 **一个真空闲位都没有**（最后一个候选 open-design #9086 也被 `/claim` + assigned）。新 issue 的占位窗口只有几小时，`rtk` 30 天开 49 条 GFI 却条条有 2–3 个 PR——瓶颈在供给端，不在意愿。

## 五、数据口径与失效风险

| 项 | 说明 |
|---|---|
| 星数 | 2026-10-31 API 快照；skills 类仓库存在明显通胀，不能当质量指标 |
| 30 天提交 | 最多翻 3 页 × 100 条，**≥300 一律记为"≥300"**，不是精确值 |
| open_issues | 含 PR，不等于"待解决 bug 数" |
| GFI | 只统计 `good first issue` **标签**；有的仓库用别的标签（如 `beginner`），会漏 |
| 许可证 | `NOASSERTION` = GitHub 无法归类，**用前必须手工读 LICENSE**（dify / bun / pytorch / elastic / tldr 均属此类） |
| 未核验 | 首次响应时间中位数、CLA 机器人层面配置（PR 模板与贡献文档已核，见第九节） |
| 覆盖范围 | Search API 每个查询取前 30；"全网"不等于"全部" |

### 四个发现

1. **GFI 数量与"好标的"几乎无关。** `rtk` GFI 221 条看着最诱人，实测合并率只有 **42%**、中位 **102 小时**；
   `excalidraw` GFI 26 条，外部 PR 合并占比仅 **11.1%** —— 提 9 个合 1 个。
   反过来 `airflow` GFI 110 条、合并率 84%、中位 1.9 小时，**量和通过率同时成立**。
2. **2026 年多了个新变量：AI 政策。** `elasticsearch` 的 CONTRIBUTING 白纸黑字写着
   *"We typically reject PRs that appear to have come fairly directly from a LLM"*；
   `tiptap` 要求 PR 描述里**披露**是否用了 AI；`dify` 欢迎 AI 但会关闭未验证的低质提交。
   `airflow` 也不宽松——PR 模板第一项就是 *"Was generative AI tooling used to co-author this PR?"*，
   勾了还要写 `Generated-by: <工具名>`（细则见第九节）。
   对"自动化批量提 PR"这种模式，这是硬门槛，不是软建议。
3. **正则会把 "class" 误判成 "CLA"。** 首轮检测 `tiptap`/`aws-cdk`/`open-design` 全部命中，
   加词边界回读上下文后：tiptap 命中其实是 `Claude`；aws-cdk 是 `class`；
   open-design 原文是 **"We don't enforce a CLA"**（反向）。→ 许可证与 CLA 结论必须读原文。
4. **`AGENTS.md` / `CLAUDE.md` 已经是仓库标配。** 抽查 11 个仓库里 **10 个**带这类文件
   （`cvat` 是唯一没有的）；`airflow` 甚至有 `AGENTS.md` + `CLAUDE.md` + `.github/AGENTS.md` 三份。
   这说明"给 AI 代理看的仓库说明"已从个人偏好变成项目基建的一部分——也意味着**先读 AGENTS.md 再动手**，
   比读 CONTRIBUTING 更接近维护者真正期望的工作方式。

### 口径局限

- 样本是"最近被更新过的 100 条已关闭 PR"，偏向近期活跃仓库；
- 合并率的分母是**已关闭**，不是**已打开**，不含仍在排队的 PR；
- 外部占比按 `author_association` 判定，机器人 / 团队账号可能被误算；
- CLA 已按根目录实际文件名扫描（`CONTRIBUTING.md` / `.rst`、`.github/`、`docs/`），仍可能漏 PR 模板、CLA 机器人配置与 ICLA 制度（Apache 项目的一次性 PR 通常不受影响）。

### 9.3 写代码的硬边界

- **源码改动 ≤ 100 行**（测试 / 文档 / newsfragment / 翻译 / lock 文件**不计入**）。
  超过 100 行会被当作"新特性"，需要维护者先看，CI 也不会自动批准运行。
- **不要改 CI 定义文件**：`.github/`、`dev/breeze/`、`scripts/ci/`、`scripts/docker/`、
  `scripts/in_container/`、顶层 `Dockerfile*`、任何目录下的 `.pre-commit-config.yaml`。
  动了这类文件，workflow 必须等维护者人工批准。
- **不新增 provider、不改依赖**（`pyproject.toml` / lock / `package.json` / `go.mod` / Gradle）。
- 测试位置：provider 的单测在 `providers/<包>/tests/unit/...`，core 在 `airflow-core/tests/unit/...`。
  具体跑法按 `contributing-docs/` 与 breeze 为准——本报告不替项目发明命令。
- 提交信息按 [chris.beams.io](https://chris.beams.io/posts/git-commit/)。
  **作者与 co-author 的姓名/邮箱在合并后永久公开且不可撤回**，先确认 `git config user.email`（如果你有 git 的话）。
- 无 DCO/CLA 门槛：`contributing-docs/05_pull_requests.rst` 全文未出现 `Signed-off-by` / DCO / CLA 要求，
  PR 模板也没有。Apache 项目走 ALv2 授权，不签 DCO。

### 9.4 PR 描述逐项（照 `PULL_REQUEST_TEMPLATE.md` 填）

1. 顶部一段：改了什么、为什么（只重复标题不算数）。
2. 关联 issue：`closes: #74590`（或 `related: #74590`）。
3. **Gen-AI 披露**：用了就勾 `- [X] Yes`，并取消注释写
   `Generated-by: <工具名> following ...#gen-ai-assisted-contributions`。
   原文明确：可以边审核边用 AI，但**盲目粘贴会被关 PR，且会影响你在维护者那里的信誉**。
4. UI 改动附 before/after 截图或录屏。
5. 大的用户可见改动加 newsfragment：`airflow-core/newsfragments/{PR号}.significant.rst`
   —— PR 号建完 PR 才知道，**允许后续 commit 补**。
6. 基础性变更需要 AIP（Airflow Improvement Proposal），不是 PR 能直接推的。

### 9.5 会被转 Draft / 关闭的触发条件

| 触发 | 后果 |
|---|---|
| 静态检查不过（`prek run --from-ref main`：pre-commit / ruff / mypy） | 外部 PR 被自动转 Draft |
| 描述只有复选框/标题重复、没有实质说明 | 同上 |
| 未披露 Gen-AI | 同上 |
| 夹带无关改动 | 同上，评论会点名 |
| 同一贡献者有 **>3** 个 open PR 被标记质量问题 | 可能被关闭，label `closed because of multiple quality violations` |
| 无写权限者 open PR **超过 5 个** | GitHub 直接不让开新 PR；维护者会关闭超出的（Draft 也计数） |
| CI 预计 > 310 job-minutes、或改动 >100 行源码、或动了 CI 文件 | 需要维护者人工批准 workflow（label `need workflow approval`） |

> Draft **不是拒绝**，是"改到符合标准再来"。原话：
> *"Converting a PR to draft is not a rejection — it is an invitation."*
> 预期最短 **72 小时**才有回复，别催。

### 9.8 抢位策略（比"挑排名第一"更有效）

1. **判占位要看四个信号，缺一个就会误判。** ① `assignees`（search 结果里就有，最省事）；
   ② 评论里的 `/claim`、`I'll take this` 等认领话术（**`/claim` 是 slash 命令，普通关键词匹配会漏**）；
   ③ `timeline` 里 **open** 的 `cross-referenced` PR；④ `timeline` 里 **merged** 的 PR
   （#8621 就是这样漏的：修复已合入 `release/v3`，只是还没发布）。
   只看 assignee 不行（airflow 是 no-assignment 政策），只看 open PR 也不行。
2. **先看供给，再谈抢位。** 30 天窗口扫描（8.6）显示：`airflow` 只开出 1 条 GFI，
   `cognee`/`cvat`/`aws-cdk`/`PDFMathTranslate` 是 **0 条**——这些仓库根本没有"新窗口"可抢；
   `rtk` 开出 49 条但条条有 2–3 个 PR。所以"按时间抢新 issue"只在少数高频开 issue 的仓库成立，
   且要接受高竞争。
3. **先评论再动手。** 项目不分配 issue，实际占位方式就是在 issue 下留一句
   "I'm working on this, ETA …"；没有这一步，撞车概率极高。
4. **排除三类**：workshop 预留（#71945）、描述本身有误（#55693）、`needs-triage` 且多轮无回应的。
5. **换池子也有竞争**：`open-design` 合并率高（100%、中位 0.4h）但近 30 天的 9 条 GFI **全部**已被占；
   它 23 条 `help wanted` 也**全部**被占（#9086 是最后一个被 `/claim` 的）。
