## 附：真机音频缺口 —— 真机硬件/驱动缺口，代码不可修

**现象**：日志 `麦克风启动失败: Error querying device -1`。

**根因**（多轮实测坐实，**非代码 bug，是本机硬件/驱动缺口**）：
- 本机**无系统默认输入设备**：`sd.default.device = [-1, 1]`（输入 -1 = 无），MME/DirectSound/
  WASAPI 层 `default_input_device` 全 -1；系统 AudioEndpoint 里「麦克风 (Realtek)」状态 Unknown
  （扬声器 OK）→ 系统层就没启用麦克风端点
- 有输入通道的设备只有 3 个，全在 **WDM-KS**：8 麦克风、10 立体声混音、11 线路输入，但——
  - WDM-KS **不支持 blocking read**（`Blocking API not supported yet`）
  - 三设备 **16000Hz 全 `Invalid sample rate`**，只有 48000Hz（vosk 要 16k）
  - 按产品真实路径用**回调式 48kHz** 能建流，但建流后 `active=False`、**2.5s 零回调**（拿不到数据）

**为什么不是"改配置就能绕过"**：把 `proactive.duplex_mic_device` 指到 `8` 只解决了"跳过不存在的
default"，但底层仍 16k 无效 + 回调零数据。曾设想的「自动选设备 + 48k→16k 重采样」也**拿不到音频
数据**——卡在系统层没有可用麦克风端点，不是 Python 层能补的。

**结论 / 建议**：**真机硬件或驱动缺口，需先在系统里启用/插入麦克风端点**，让 MME/WASAPI 层出现
可用输入设备后再验。代码层（`audio_io.py` / `asr.py`）未改、也不宜改。

1. **必备文件**：36 个，逐条判存在。

   局限如实写明：动态 import 与 `from . import X` 里的属性名不判，那是 compileall 与

### 闭包抓到的真缺口（P2，非阻塞）

# 第九轮 · 修 `--root` 假绿 + 把 P2 链路钉死

## 1. 又一个「闸门自己会骗人」：验的不是目标包

第八轮把 `--root` 写成「可指向另一份待验交付包」，但 `check_self_heal` 里是

```python
from src.config import ensure_config_file     # sys.path[0] 是 SCRIPT_ROOT
```

`SCRIPT_ROOT` 是**闸门所在包**。也就是说 `--root B` 时，自愈三态验的是 A 的实现。
发布流程恰恰是最需要用 `--root` 验「刚打出来的那份包」，这个假绿比没有闸门更危险
（它给了一份看起来合格的报告）。

**复现（修前，已实测）**：临时目录放两份真实配置，`src/config.py` 写成恒返回
`("missing", path)`，调 `check_self_heal(tmp)` → 返回
`PASS 缺配置→created / 有实配→exists / 无模板→missing`。目标包坏成这样照样全绿。

## 2. 修法：从目标包自己的源码里抽出函数单独执行

新增 `_load_target_ensure(root)`：

- `ast.parse` 读 `root/src/config.py`；
- 只取 `ensure_config_file` 这一个 `FunctionDef` 与 `CONFIG_TEMPLATE_NAMES` 字面量常量；
- 放进干净命名空间 `{"os", "shutil", "CONFIG_TEMPLATE_NAMES"}` 里 `exec`。

好处：**不 import 整包**（不触发模块级副作用、不依赖 `yaml` / `win32` 等第三方库）、
**不落到 SCRIPT_ROOT 的 `src`**、仍是纯只读。取不到函数或常量 → **FAIL**（旧实现是 WARN），
提示「检查 `--root` 指向的是完整交付包；闸门不会再拿自己包里的实现顶替」。

**修后同一复现**：目标包恒 `missing` → `FAIL 行为异常：created, exists（实测 missing/missing/missing）`；
把目标包换成真实 `src/config.py` → `PASS 目标包自身实现：…`。两个方向都验过。

# 第十轮 · 补「文件在 ≠ 能用」（文件实体闸门）

## 1. 为什么这轮要查

同一类反模式在本项目里已经出现过三次，前两次都被修了，第三次漏在闸门自己身上：

| 轮次 | 反模式 | 修法 |
|---|---|---|
| 第一轮 | `os.path.isfile("api-ms-win-crt-runtime-l1-1-0.dll")` → 只看文件在不在，不看能不能加载 | 改 `ctypes.WinDLL()` 试加载 |
| 第一轮 | `os.path.exists(handshake)` → 只看文件在不在，不看进程活不活 | 改 loopback TCP 判活 |
| **第十轮** | `os.path.isfile(rel)` 判必备文件 → **只看文件在不在，不看内容对不对** | 新增「文件实体」检查 |

第三处的危害最直接：打包脚本在解压/复制阶段被中断，或磁盘满、或 antivirus 把
`electron.exe` 截成 0 字节，`check_required_files` 依然报 **36 个必备文件齐全**，
`check_required_dirs` 依然数得到 120 个文件（空文件也计数），闸门全绿放行。

## 2. 复现（修前）

构造一个最小交付包：所有必备文件写入 `b"x"*128` 占位、资源子树按各自下限补空文件，
然后把两个最关键的产物弄坏：

- `src/ui/web/index.html` → **0 字节**（用户看到的整个界面没了）
- `shell/node_modules/electron/dist/electron.exe` → **1 字节 `b"M"`**（桌宠壳起不来）

修前实测：

```text

 'check_source_closure': 'WARN', 'check_template': 'PASS',
 'check_template_secrets': 'PASS', 'check_self_heal': 'PASS'}
FAIL 数 = 0
```

**0 FAIL。** 一个打不开界面、起不了壳的包被判为「可放行」。

## 3. 修法：用魔数/结构标记，不猜大小

新增 `check_file_integrity()`，对 19 个关键产物按类型取客观判据（缺文件的由
`check_required_files` 报，这里跳过以免重复刷屏）：

| 类型 | 文件 | 判据 |
|---|---|---|
| PE（6） | `python.exe` / `pythonw.exe` / `python312.dll` / `vcruntime140.dll` / `electron.exe` / `Uninstall.exe` | 头 2 字节 `MZ` + ≥64 字节 |
| HTML（4） | `web/index.html` / `loading.html` / `notify.html` / `live2d/rig/index.html` | 含 `<!doctype` / `<html` / `<head` / `<body` 之一 + ≥64 字节 |
| 音频（1） | `assets/voices/daniya_ref.wav` | 头 `RIFF`、第 8-12 字节 `WAVE` |
| 文本（7） | `shell/main.js`、`shell/preload.js`、`requirements.txt`、4 个 prompt | 前 4KB 去空白后非空 |
| 配置（1） | `config.yaml` | `yaml.safe_load` 结果是 `dict`（不是列表/标量/解析失败） |

`MIN_ARTIFACT_BYTES = 64` 只用来挡空文件/残片——真实产物最小的也有 2KB，
设成 64 是刻意留出「不猜体积」的余量，真正的判据是格式标记。

**为什么不是「大小阈值」**：阈值必然要么误伤（未来某个资源变小）要么漏检
（截断到阈值以上）。魔数是文件格式自带的约束，不随版本漂移。

# 第十一轮 · 依赖是否真的装进了内置运行时

## 1. 为什么这轮要查

doctor 有一项「核心依赖」：从 `requirements.txt` 的「核心」段取 12 个发行包，逐个
`importlib.import_module`，缺一个就 FAIL。问题在于**它只能在用户机器上跑** —— 等它报红，
包已经发出去了，用户已经双击了。

而闸门这边只硬编码了 4 个 site-packages 标记（`yaml` / `sounddevice` / `vosk` / `webview`），
其中只有 3 个属于核心档（`vosk` 其实在「重要」档）。也就是说 `requirements.txt` 的 12 个
核心依赖里有 **9 个**（`httpx` / `numpy` / `websockets` / `dashscope` / `mss` / `Pillow` /
`requests` / `rich` / `psutil`）**没有任何交付期校验**。
典型翻车场景：改了 `requirements.txt` 加了新依赖，忘了重跑 `make_dist.py --install-deps`，
打出来的包在开发机上跑得好好的（开发机装过），到用户机上 `ModuleNotFoundError`。

## 2. 实测基线（真实交付包）

| 档位 | requirements 条目 | 包内已装 | 缺 |
|---|---|---|---|
| 核心（缺一不可） | 12 | **12** | 0 |
| 重要（功能降级） | 13 | **13** | 0 |
| 可选（失败不影响启动） | 16 | 4 | 12 |

可选缺的 12 项（`rapidocr-onnxruntime` / `pynput` / `opencv-python` …）与 doctor 的
既有 WARN 完全对得上，属预期。**核心与重要都是满的** —— 说明当前这个包的打包是干净的，
这一项在真实包上应当是 PASS，不制造噪音。

## 3. 修法：dist-info 作为「pip 真装过」的权威痕迹

新增 `check_dependencies()`，**不 import、不执行目标包代码**（保持闸门只读）：

1. 用与 `tools/doctor.py:_parse_requirements` **完全相同**的分节约定读 `requirements.txt`
   （`# ===== 核心 =====` 这类注释行）。两边各读一套会互相打架，所以约定必须共用。
2. 扫 `python/Lib/site-packages/*.dist-info`，目录名按 wheel 规范从右切版本号
   （`PyYAML-6.0.2.dist-info` → `PyYAML`），名字做 `-/_/.` 归一化后建索引。
3. 分级判定：**核心缺 → FAIL**；重要缺 → WARN；可选不管。
4. 兜底：dist-info 没了但模块本体在（`<import>/__init__.py` 或 `<import>.py`）→ WARN
   「能用但缺元数据」，不误判成 FAIL。

判据为什么选 dist-info 而不是「目录在不在」：目录可以被手工拷贝伪造，`dist-info` 是
`pip install` 留下的唯一权威记录，含版本与 `RECORD`。它同时也回答「装的是哪个版本」。

## 4. 我自己踩的一个测量坑（值得记下来）

第一次探测时，`dist-info` 侧按 `-` 切成 `edge`，需求侧却拿完整的 `edge-tts` 去比，
于是 `edge-tts`、`websocket-client` 被误报为「缺失」。差一点就把这条写进结论。

修正归一化（两侧统一 `-/_/.` 去分隔符）后，重要档从「13 项缺 2」变成 **13/13 全在**。
教训：**任何「名字比对」类判据，必须先让两侧用同一个归一化函数**，否则误报会伪装成缺陷。
这条也写进了代码注释（`_norm_dist` 与 doctor 的 `_norm` 同款）。

## 5. 变异矩阵（新增 4 刀）

| 场景 | 破坏方式 | 期望 | 实测 |
|---|---|---|---|
| Y | 删掉 `numpy` 的 dist-info 且无模块 | `check_dependencies` FAIL | ✅ |
| Z | 删掉「重要」档 `pypinyin` 的 dist-info | 只 WARN，不许 FAIL | ✅ |

## 6. 附记：一次无法复现的 1 FAIL（取证教训，不是产品缺陷）

本轮验证时，有一次 doctor 报 **15 PASS / 3 WARN / 1 FAIL**。此后连续 **9 次**
（含 3 次与 `compileall` 并行、5 次与闸门+两个 selftest 并行、4 次纯顺序）全部为
**16 PASS / 3 WARN / 0 FAIL**，无法复现。

没能定性的原因在我自己的取证方式：当时用 `| tail -3` 取汇总，**FAIL 那一行被截掉了**。
doctor 不落盘（已确认 `logs/` 里无 doctor 痕迹），事后无从恢复。

两点结论：
- 该次 FAIL 未复现，且 9 次复跑干净，不据此判产品缺陷；但 doctor 会真起一次 Electron 壳、
  真合成一次音频，**并发跑时存在资源争用**，属于「工具被并发调用」的使用问题。
- **跑 doctor 不要用 `tail` 截断**：要么看全量，要么 `grep -E "\[FAIL\]"`。这条已写进本章，
  后续所有复验都按此执行。

# 第十二轮 · 让闸门「真跑一次」：可选 `--smoke`

## 1. 为什么这轮要查

前十轮把闸门做成 8 项，全部是**静态判据**：文件在不在、内容对不对、模块能不能解析、
依赖有没有 dist-info。它们能挡住「漏发」，但挡不住一类问题 —— **东西都在，就是跑不起来**：

| 静态判据看不出的事 | 后果 |
|---|---|
| 内置 `python.exe` 与 `.pyd` 位数不匹配（32/64） | 解释器起不来，或 numpy 导入失败 |
| UCRT / VC 运行时在目标机缺失 | `numpy` 等 C 扩展加载失败（第一轮踩过的正是这个） |
| 安全软件把 `python.exe` 隔离/拦截 | 双击没反应 |
| `site-packages` 里只有目录、没有可加载的 `.pyd` | `import` 才炸 |

这几件事有一个共同点：**只有真执行一次才知道**。而唯一能报出它们的 doctor，
本身就跑在这个解释器上 —— 解释器坏了，doctor 连启动都做不到。

## 2. 设计：默认关闭，只在自己打的包上开

`--smoke` 是**可选**的第 9 项，不放进默认 `CHECKS`：

```python
checks = CHECKS + ((check_runtime_smoke,) if args.smoke else ())
```

理由：闸门此前承诺「只读、不执行目标包代码」，这条承诺被 `--root` 场景依赖着
（拿它验来路不明的目录时，不该执行里面的程序）。所以：

- **默认**：仍是 8 项纯静态，`7 PASS / 1 WARN / 0 FAIL`。
- **`--smoke`**：追加执行 `{root}/python/python.exe -c "<固定探针>"`，`8 PASS / 1 WARN / 0 FAIL`。

探针只做三件事，不读配置、不写文件、不联网：

```python
SMOKE_PROBE = (
    "import sys, numpy, yaml;"
    "print('SMOKE_OK', sys.version_info[0], sys.version_info[1],"
    " numpy.__version__, yaml.__version__, int(getattr(sys.flags, 'isolated', 0)))"
)
SMOKE_TIMEOUT_S = 120
```

**为什么探针里一定要有 `numpy`**：它是包里唯一同时依赖 UCRT、BLAS 和 `.pyd` 加载的核心扩展。
`numpy` 导得进来，说明「位数 + VC 运行时 + 扩展加载」这条链是通的；只 `import sys`
证明不了任何有价值的东西。

判定用「退出码 + 成功标记」双条件，不只看退出码：`python.exe -c` 在某些拦截场景下
会以 0 退出但什么都没跑，只看 `returncode` 会假绿。

## 3. 实测（真实交付包）

```text
[PASS] 运行时冒烟      python 3.12 · numpy 2.5.4 · PyYAML 6.0.3 · isolated=1
```

`isolated=1` 顺带印证了 doctor「运行期隔离」那一项：内置运行时确实由 `python312._pth`
固定在 isolated 模式，不会加载包外路径。若某次打包漏了 `_pth`，这里会显示 `isolated=0`，
并附一句提示（**只提示、不判红** —— 因为 doctor 才是这项的权威判据，闸门不越权抢红）。

## 4. 变异矩阵（新增 4 刀）

| 场景 | 破坏方式 | 期望 | 实测 |
|---|---|---|---|
| AC | CLI `--smoke` 打在 `python.exe` 是占位的最小包上 | rc=1，FAIL 落在「运行时冒烟」 | ✅ |
| AD | `subprocess.run` 返回 `exit=0` 但没有 `SMOKE_OK` 标记 | FAIL（证明不是只看退出码） | ✅ |
| AE | 探针输出 `isolated=0` | PASS + 提示，不判红 | ✅ |

判据只看语法，不做控制流分析（宁漏不误）：一条语句「必定离开当前块」= `Return`/`Raise`/`Continue`/`Break`，
或 `if` 有 `else` 且两支末句都必离开，或 `try` 的 body + **全部** handler（+ `else`/`finally`）末句都必离开。
其后若还有语句 → 不可达。

**豁免机制是本轮的设计重点**：不可达语句那行、或它**紧邻的连续注释块**里含
`# unreachable-ok: <原因>` 即放行。**不用行号白名单**——行号会随任何编辑漂移，
漂移后闸门静默失效且没人知道（本仓在 `check_web_js_syntax` 的硬编码行号上踩过）。
标记跟着代码走，删代码时标记一起消失，不会留下"看起来还在保护、其实早就不指向任何东西"的白名单项。

### 变异刀 `tools/_qc_unreachable_mutation.py`（218 行，六刀 + 对照）

刀不碰真实源码——闸门吃的是**路径**，在临时目录里造样本喂给它。所以刀永远不会把仓库改坏，
也不需要"还原校验"（比第十五轮那把刀少一个失败面）。

```
  基线：6 个样本里 4 处不可达（M1/M3/M4/M5 各 1），1 处豁免
  PASS M1（return 之后的死语句）：exit 1 且点名 dead_plain.py:3
  PASS M2（加 unreachable-ok 后豁免）：exit 0，不可达 0 处
  PASS M3（标记隔着空行不算豁免）：exit 1 且点名 dead_marked_far.py:6
  PASS M4（try/except 双分支 return 之后）：exit 1 且点名 dead_try_both.py:6
  PASS M5（循环体里 continue 之后）：exit 1 且点名 dead_loop_continue.py:5
  PASS M6（语法错误不许静默通过）：exit 2 且明确报「无法判定」
```

- **M3** 证明不是"文件里出现过 `unreachable-ok` 就豁免"——隔着空行就失效，否则随便一段无关注释就能把闸门弄哑；
- **M4** 是第十五轮那个真形状；
- **M5** 证明递归进了 `if`/`for` 体（只查函数顶层会漏掉这一类）；

断言的是"抓到了注入的那个错"（点名文件 + 行号），不是"任意非零退出"——否则分不清闸门在工作、
还是闸门自己崩了（两者都 exit 1）。

# 第十八轮 · 「finally 里 return」与一张只进不出的任务表

前两轮找的是**死代码**（不可达语句、被覆盖的同名定义）。本轮换目标：**代码都活着，
但有一半的作用被悄悄抵消掉了**。

## 1. 换了四次角度才落到真问题上

先做的四份普查，结果都记下来——因为"没找到"本身是判据可用性的证据：

| 角度 | 全仓命中 | 结论 |
|---|---|---|
| 常量条件分支（`if False:` / `while 0:` / `if True: else`） | **1** | 真问题，但 `main_window.py:248` 正被 #7 修改，本轮不动 |
| 带装饰器的同名覆盖（#10 判据「两边都无装饰器」的盲区） | 38 | 37 处是 `@_t(...)` 注册式写法（合法）、1 处是 #10 已处理的 `relation_block_text_v2` → **判据不需要放宽** |
| 「只进不出的成员容器」（`self.X[k]=v` 有写入、全文件无 `pop`/`del`/`clear`） | 16 | **判据不可用**：15 处键空间有界（`_last[engine]`、`_rules[type]`、`_procs[pid]`、`_defaults[key]`），报出来全是噪声 → 放弃 |
| 静默失效四类：`finally` 里跳出 / 可变默认参数 / `is` 比较字面量 / 裸 `except: pass` | **1** / 0 / 0 / 0 | 第一类见下；`is` 的 408 处全是 `is True`/`is False`，是惯用法不是缺陷 |

第三行那次放弃是刻意的：一个 16 处命中里 15 处是噪声的判据，收进闸门后唯一的命运
是被加进白名单。**先量再收**，是前几轮定下的规矩。

## 2. 真问题一：`finally` 里的 `return`（`src/ui/webapp.py:5848`）

```python
finally:
    # 【2026-10-18】早退（无引擎/参数错）时 backend 为 None，
    # 这里跳过卸载逻辑，避免 finally 抛 UnboundLocalError 覆盖真实错误。
    if backend is None:
        return            # ← 作者以为只是"跳过卸载"
    if backend.name in self._LOCAL_MOUNT_ENGINES:
        ... 卸载显存 / 延迟 kill 服务 ...
    def _cleanup():
        _t.sleep(60)
        self._voice_tasks.pop(task_id, None)
    threading.Thread(target=_cleanup, daemon=True).start()
```

`return` 在 `finally` 里做的事比"提前收工"多两件，两件都不出声：

1. **吞异常**。`try` 体或 `except` 分支自身正在抛异常时，`finally` 的 `return` 把它丢掉，
   函数正常返回。上层看到的是"什么都没发生"，日志里一个字都没有。
2. **跳过其后的清理**。`return` 退出的是**整个函数**——排在它后面的 `_cleanup`
   一条都不执行。

第 2 条正是这个 bug：`backend is None` 意味着"没配引擎 / `create_backend` 抛了"，
而这恰恰是**用户最常撞到**的路径（角色页音色档没选服务商就点试听）。
每撞一次，`_voice_tasks` 里就多一条永不回收的记录。

修法不是删 `return`，而是把它从"控制流"降级成"条件守卫"：

```python
if backend is not None and backend.name in self._LOCAL_MOUNT_ENGINES:
```

只跳过卸载，清理照旧。**这是本轮唯一的行为变化**。

## 3. 真问题二：同一张表，另一条路根本没有清理

顺着 `_voice_tasks` 的 `pop` 调用点查下去：

| 入口 | 线程体 | 清理 |
|---|---|---|
| `test_voice`（本地/克隆引擎试听） | `_run_voice_test` | 有，但被上面那句 `return` 跳过 |
| `preview_cloud_voice`（云端双工试听） | `_run_cloud_preview` | **完全没有** |

全文件的 `self._voice_tasks.pop(...)` 只有一处（在 `_run_voice_test` 的内联 `_cleanup` 里）。
`preview_cloud_voice` 每被点一次就往表里加一条，进程活多久留多久。

两处都不报错、不占 CPU、日志无痕。这类缺陷的共性：**表本身是对的，写入是对的，
只有"谁负责收尾"这件事没人管**。

改动：把内联的 `_cleanup` 抽成 `_schedule_voice_task_cleanup(task_id, delay=60.0)`，
`_run_cloud_preview` 补一个 `finally` 调用它。两条路共用一个助手，不再各自长。
前端 `get_voice_test_status` 对缺失任务本来就返回 `phase="gone"`，清理提前不会让前端炸。

## 4. 闸门 `tools/check_finally_jump.py`（182 行，纯 stdlib）

  用 `ast.walk` 图省事就会在这里假红。

  `for ...: break`，绑的是那个内层 `for`，完全合法。

## 5. 变异刀 `_qc_finally_jump_mutation.py`（八刀 + 对照，193 行）

# 第十九轮 · 恒真恒假条件：一半代码是死的，一半判据是假的

第十八轮修的是"语句不可达"，本轮修的是**条件恒定**——`if False:`、`or True` 这类写法让
整个判断失去意义。它比前几轮更隐蔽的地方在于：**它同时污染测试层**。一条
`check(x or True, "…")` 永远通过，于是"这个功能有判据守着"变成一句空话。

## 1. 五份普查，四份是干净的

按惯例先量再收，结果全记下来：

| 角度 | 命中 | 结论 |
|---|---|---|
| 字典字面量重复键（后者静默覆盖前者） | **0** | 干净 |
| `if/elif` 链里重复条件（第二分支永不进入） | **0** | 干净 |
| 同一 `try` 里重复的 `except` 类型 | **0** | 干净 |
| `hasattr(x, "NAME")` 而 NAME 全仓不存在（守卫恒 False） | **0** | 152 处守卫全是真的（6 个疑似里 4 个是 `__await__` 这种 dunder、2 个是测试里**故意**断言"这个名字已经不存在"） |
| `except` 分支返回成功形态（`return True` / `{"success": True}`） | 27 | **不是缺陷**：这套代码里 `success` 普遍表示"查询/调用完成"，真正的答案是 `usable` / `reachable` / `ok` 另一个字段。逐条看过 5 处 `{"success": True}` 全是这个约定 → 判据不成立，放弃 |
| **条件恒定**（字面量让判断恒真/恒假） | **10** | 见下，本轮的真问题 |

# 第二十轮 · 三道闸门永远绿：判据算对了，就是没人按它退出

前十九轮查的都是「判据写得对不对」——`or True` 让断言恒真、`if False:` 让代码恒死、
`finally` 里的 `return` 让清理恒被跳过。这一轮换了个角度：**判据有没有牙**。

## 1. 切入点：`GATES` 是靠退出码说话的

`tools/check_all.py` 的 `GATES` 是全仓「有哪些判据在守」的唯一清单：

```python
GATES: list[tuple[str, str, list[str], bool]] = [
    ("名称", 解释器, 参数, 是否慢项),
    ...
]
```

它跑每一项、收每项的**退出码**、汇总成 `PASS：N 项全部通过` 或 `FAIL：M/N 项未通过`。
所以一个只 `print("[FAIL] …")`、始终 `exit 0` 的脚本，会：

1. 占着清单里的一行；
2. 每次全量闸门都跑一遍（浪费时间）；
3. 永远显示 ✓。

**它不守任何东西，但它的存在让人以为「这件事有判据」。** 这比没有闸门更糟——没有闸门时
人会去查，有闸门时人会放心。

这个形状在本仓已经复发过很多次，只是每次的具体表现不同：

| 时间 | 表现 |
|---|---|
| 第十五轮 | `check_web_js_syntax` 打印完就 exit 0 |
| 更早 | `check_requirements` 遇 SyntaxError 静默跳过、退出码仍 0 |
| 更早 | 唤醒词 / 桥接 / 广播各自「看着绿、其实整文件没被扫」 |
| **本轮** | **三个脚本连判据都没有，只有 print** |

前几次是**判据写错**，这次是**根本没写判据**。区别在于：判据写错还能靠读代码发现，
没写判据只能靠"它怎么从来不红"这种元层面的怀疑。

## 2. 做法：先写闸门，再用闸门找病灶

没有先去读那 195 个登记脚本（读不完），而是先写一道元闸门——「登记在 `GATES` 里的脚本，
必须存在一条能红的退出路径」——然后让它自己去找。

判据只查 `argv[0]` 以 `.py` 结尾的项（`-m compileall` 这类外部命令不归它管）。
脚本里出现下面任一形态即算「能红」：

| 形态 | 为什么算 |
|---|---|
| `sys.exit(x)` / `os._exit(x)`，`x` 不是常量 `0`/`None` | 显式退出码 |
| `unittest.main(...)` / `pytest.main(...)` | 它们自己会按结果非零退出 |
| 任何 `raise`（含 `raise SystemExit(1)`） | 异常本身就是非零退出 |
| 任何 `assert` | 同上 |

豁免：确属「只出报告、不判通过/失败」的脚本，写 `# gate-exit-ok: <原因>`。
注释里明写了「**不要用它给『忘了写退出码』开脱**——那种情况应该去补退出码」。

第一版跑 master（`b65e645`）的结果：


## 3. 病灶一：`test_judge_confirm_clause.py` —— 连累计变量都没有

## 4. 病灶二、三：结论算对了、印出来了，就是没退出

这两个比第一个更值得记，因为**代码看起来是对的**：


```python

```

两个都算出了结论、都打印了结论，然后脚本结束、`exit 0`。

这种缺陷为什么比「判据写错」更难发现：

* 屏幕上红的是**结论文字**，绿的是**退出码**，而 CI 只看后者；
* 人去看输出时，看到 `HAS FAILURE` 会以为「它报了」，不会想到「它报了但没生效」；
* 静态读代码时，`allok = all(...)` 这一行看上去就是判据本身——判据确实写了，缺的是最后一步。

修法各一行：

```python
sys.exit(0 if allok else 1)     # test_prompt_companion_clause.py
sys.exit(0 if ok else 1)        # test_fabrication_guard.py
```

## 5. 附带发现：`exit 0` 不只吞掉 `[FAIL]`，它吞掉一切

验证时用系统 python（没装 `yaml`）跑 `test_prompt_companion_clause.py`：

```

    import yaml
ModuleNotFoundError: No module named 'yaml'
```

改前：**崩完仍然 exit 0**。改后：`exit 1`。

也就是说这类脚本的失效面不止「判据不生效」，还包括「脚本自己崩了也不生效」——
连 `SyntaxError`、`ImportError` 这种最基础的失败都被 `exit 0` 吃掉了。这条副作用比原缺陷
更值得记：**`exit 0` 不是一个"通过"的返回值，它是一个"我什么都不说"的返回值。**

顺带说明：这条也解释了为什么本仓要用包内 `python/python.exe` 跑闸门——用错解释器时，
改前是静默通过，改后是明确红。后者才是对的。

# 第二十一轮 · 同一形状第三次：跨模块死引用

前二十轮查的是「判据写错」（`or True`）、「代码恒死」（`if False:`）、「清理被跳过」
（`finally` 里 `return`）、「闸门不会红」（永远 `exit 0`）。这一轮查的是**引用本身指向空**。

它不是新发现的形状——是**同一个形状的第三次**。这就是本轮真正的切入点。

## 1. 同一形状，三次，全在通知窗那条线上

| 轮次 | 位置 | 不存在的符号 |
|---|---|---|
| 第十五轮 | `src/ui/mode_notify.py` `create_notify_window` | `NotifyJsBridge`（无此类） |
| 第十九轮 | `src/ui/main_window.py:248` | `_mn._notify_slide_if`（无此函数） |
| **第二十一轮** | `src/ui/notify_geom.py:107` | `_mn._push_cmd`（无此函数） |

三次的根因逐字相同：**通知窗从 WebView2 迁到 WPF 原生窗之后，旧 API 的调用点没跟着删。**
`mode_notify._win` 的注释自己写着「迁移到 WPF 原生窗后已无此对象」，但调用方还在按 WebView2
时代的样子调它。

三次没被发现的原因也逐字相同：**都被 `except Exception: pass` 或 `if False:` 包着。**
`AttributeError` 不会冒出来，只是那个功能静默地什么都不做——不报错、不写日志、功能就是不发生。

> 前两次都是「一条一条读代码读出来的」。**同一个形状第三次出现，说明靠人读是拦不住的。**
> 一个形状出现两次可以当巧合，出现三次就该当成一类缺陷，并且给它一道闸门。

## 2. 本轮缺陷：`_push_cmd`（`src/ui/notify_geom.py:107`）

```python
if not showing:
    # 滑出完成、窗口已在屏外 → 通知前端复位卡片（此时复位不可见，
    # 避免"先黑再飞"；也保证下次 show 能重新初始化）。
    try:
        from . import mode_notify as _mn
        _mn._push_cmd({"type": "reset"})
    except Exception:  # noqa: BLE001
        pass
```

这段代码读起来是**对的**：意图清楚、注释完整、异常处理齐全。唯一的问题是 `_push_cmd`
在 `mode_notify` 里不存在，全仓也没有任何地方定义过它。

于是每次滑出都抛 `AttributeError` → 被下一行的 `except` 吃掉 → **"复位"这件事从写下那天起
就没发生过**。而它恰好是那种"看不见所以不会有人报"的功能：复位是为了"下次 show 能重新初始化"，
不生效的表现是**下次通知卡片偶尔状态不对**——没人会把这个和 300 行外的一行代码联系起来。

处置：删掉死调用，**行为逐字不变**（原本就是抛异常→被吞→无事发生），原地留墓碑：为什么删、
证据是什么、前两处在哪。

> 墓碑里明写了：**复位本身是否还需要，留给维护者定夺。** 若仍需要，得走 WPF 原生窗的新通道，
> 那是产品改动，不在质检范围内。**不替人做决定，也不假装"删掉就等于没问题"。**

### 顺带：一个从来没跑过的诊断探针

`tools/real_software_drive.py:194`：

```python
from src.companion.conversation_history import get_history   # 修复前
```

`conversation_history` 里**没有 `get_history`**。这个探针每次都在抛 `ImportError`，被 `except`
接住，永远只打印「读取跳过」——**看起来像"环境里没有对话记录"，其实是代码在骗自己。**

改成真实入口 `shared_history()`（返回 `ConversationHistory`，它有 `get_recent`）。已核对模块级
导出为 `shared_history` / `shared_history_for` / `all_histories` / `load_context` / `rehydrate`。

这类"诊断工具自己在静默失败"比产品代码里的更麻烦：**它的输出是判断依据**。一个永远打印
「读取跳过」的探针，会让人得出"这条链路没问题、只是环境没数据"的结论。

## 3. 先量五个族，才决定做什么

没有一上来就写闸门。先对 **715 个 `.py`（解析失败 0）** 量了五个候选缺陷族：

| 族 | 命中 | 结论 |
|---|---|---|
| A 可变默认参数 `def f(x=[])` | **0** | 真阴性 |
| B 可变类属性 | 44 | 逐个看过，是本仓刻意的共享状态写法（缓存/注册表），**没有证据就是没有缺陷** |
| C 裸 `except:` | **0** | 真阴性（`check_silent_except` 已在守） |
| D `src/` 里 `sys.exit` | 32 | 事实，不是缺陷（都是测试入口） |
| E 模块级覆盖内置名 | **0** | 真阴性 |

另有两个"看着有料、其实没用"的族：

* **`except X: pass` 全仓 879 处。** 879 处的清单不是判据，是噪声——它会立刻被加进白名单，
  然后什么都不守。**闸门的价值不在于能报多少，而在于报出来的每一条都该看。**
* `CharacterAPI._switch_tasks` 有剪枝、`_clone_dl_state` 会增长但被用户操作数天然限住——
  两个都查了，都不构成缺陷。

**三个真阴性（0 命中）本身就是结论**：它们说明这几族在这个仓里已经被守住了，不需要再写闸门。
普查的意义不只是找缺陷，也包括**排除掉不该做的事**——否则每轮都在重复扫同一批干净的族。

## 4. 角度转换：数病因，不数症状

879 个静默 `except` 不可用，但它们是**症状**。症状背后是病因：**这些 `except` 吞掉的是
"引用了一个不存在的符号"这个异常。**

于是换个方向：不去数 879 个 `except`，去数**引用**。

引用是有限且可判的：`from M import y` 和 `mod.attr` 里的符号，要么存在，要么不存在。
前两轮那两处、本轮这一处，都落在这一族里。**一个可判的有限集合，胜过一个不可判的无限集合。**

## 5. 闸门设计：两层 + 四条限定

`tools/check_cross_ref.py`（300 行，纯 stdlib，只读 AST，不 import 被测目标）。

两层，置信度不同，**分开判、分开报**：

* **L1** `from M import y` —— `M` 能解析到本地模块时，`y` 必须是 `M` 的顶层名字，或是 `M` 的子模块
* **L2** `mod.attr` —— `mod` 绑定到本地模块时，`attr` 必须是该模块的顶层名字

四条限定，**每一条都是量出来的，不是拍脑袋**：

| # | 限定 | 挡掉了什么（实测） |
|---|---|---|
| ① | 只认**本地**模块，外部包一律不管 | `import requests` / `from yaml import safe_load`——外部包的符号表不在本仓，判不了就不判，而不是猜 |
| ② | 被 `import *` 污染的模块跳过 | 符号表不可静态确定 |
| ③ | 名字在同文件里被重新绑定就不再当模块别名 | `test_desktop_watch_hotapply.py` 的 `va.calls`（`va = RecVA()` 覆盖了 `import ... as va`） |
| ④ | `hasattr(x,"y")` / `getattr(x,"y",默认)` 里出现过的 `(x,y)`，`x.y` 允许不存在 | `_smoke_import_20260924.py` 的 `pro.CompanionCore`——**代码自己声明了「它可能没有」，闸门不该比代码更确定** |

豁免 `# crossref-ok: <原因>`，扫上方连续注释块、空行终止，**不用行号白名单**（行号白名单会在
下一次改动后静默失效，这是前几轮反复确认过的）。

**解析失败 / 根目录不存在 / 扫到 0 个 `.py` → exit 2，不是 0。**「0 命中」只有在知道分母时才有意义。

### 分母

715 个模块，L1 实际判定 **1059 条本地 `ImportFrom`**（874 条外部 import 按限定①跳过），
L2 判定所有绑定到本地模块的 `mod.attr`。

结果：**0 处命中 / exit 0。**

## 6. 我在自己的扫描器上踩的两个坑（本轮最该记下来的部分）

原型第一次跑，报 **0 处**。

0 是很危险的数字。所以做了一个注入测试：往干净树里塞一个
`from src.ui.mode_notify import _push_cmd`，看它会不会红。

**没红。** 是假阴性。

查出来两个 bug：

### ① `top_names()` 返回 `{star}` 而不是 `(names, star)`

下游写 `if star:`，而 `{False}` 在 Python 里是**真值**（非空集合恒真）。于是
**每一个本地模块都被当成"被 star 污染"跳过了**——整个 L1 从来没执行过。

```python
def top_names(tree):
    ...
    if star:
        return {star}      # 错：返回了集合，不是元组
```

**`{False}` 为真。** 这不是笔误，是语义陷阱：本该返回 `(names, star)` 的函数返回了一个集合，
调用方解包失败后又用了真值判断，两层错误互相掩护，最终表现是"跑通了、0 命中"。

### ② 包内 `__init__.py` 里的 `.` 指包自己，不是父目录

```python
# 错
pkg = me.rsplit(".", 1)[0] if "." in me else ""
# 对
pkg = me if is_init else (me.rsplit(".", 1)[0] if "." in me else "")
```

写错之后 `src/proactive_pack/__init__.py` 一处报了 **10 个假阳性**。

修完再跑，L2 报 3 处，**全部是假阳性**，每一处正好被一条限定挡住：

```
tools/test_desktop_watch_hotapply.py:172  va.calls            → 限定③ 别名被 va = RecVA() 重绑
tools/test_model_downloader.py:96         mc.__file__         → dunder 集合
tools/_smoke_import_20260924.py:46        pro.CompanionCore   → 限定④ hasattr 声明过
```

> **"0 命中"必须靠注入证明它不是一个坏掉的扫描器。**
> 这一轮这条教训是用自己的两个 bug 换来的——而这两个 bug 都表现为"完美通过"。

# 第二十二轮 · 「刀全绿」到底证明了什么

前二十一轮在这条线上走：判据写错（`or True`）→ 代码恒死（`if False:`）→ 清理被跳过
（`finally` 里 `return`）→ 闸门不会红（永远 `exit 0`）→ 引用指向空（`_push_cmd`）。

每一轮都给闸门配了**变异刀**，每个 PR 里都写着「刀全绿 ⇒ 判据有牙」。这一轮把这句话
本身当成待查对象。

## 1. 一个套件能证明的，比它声称的少一半

「刀全绿」只证明一件事：**闸门正常工作时，刀会红。** 它没证明：

| 退化 | 谁发现不了 |
|---|---|
| 闸门**永远不红**（判据被改松成「一律不报」） | 只断言"必须变绿"的套件：全过 |
| 闸门**永远红**（判据被改紧成「一律报」） | 只断言"必须变红"的套件：全过 |

两边只要缺一边，那个套件就是**空转**的。它占着 `GATES` 一行、每次全量都跑、永远 ✓，
和第十九轮查的「永远 `exit 0` 的闸门」是同一族——只是这次包在**验证层**里。

> 一个只断言"必须红"的套件，把闸门换成 `sys.exit(1)` 也能全过。
> 一个只断言"必须绿"的套件，把闸门换成 `sys.exit(0)` 也能全过。

## 2. 做法：把闸门换成退化实现

对每一对 (刀套件, 它验的闸门)，在**仓库副本**里跑三个阶段：

```
D0 原样            → 套件必须 exit 0（否则它本来就红，后面的观察没意义）
D1 闸门 ≡ exit 0   → 套件必须 exit != 0
D2 闸门 ≡ exit 1   → 套件必须 exit != 0
```

三阶段全过才叫 `CERTIFIED`。退化实现只有两行，且**必须 import-safe**（见第 5 节坑①）：

```python
if __name__ == "__main__":
    raise SystemExit(0)      # 或 1
```

## 3. 查出来的真缺陷：`check_web_js_syntax.py` 的 import 路径

```python
ROOT = os.path.dirname(os.path.dirname(os.path.abspath(__file__)))
if ROOT not in sys.path:
    sys.path.insert(0, ROOT)

from check_bridge_methods import is_draft_html, is_draft_js   # ← 它在 tools/ 里，不在 ROOT 里
```

`check_bridge_methods.py` 在 `tools/` 下，但这里只把**仓根**加进了 `sys.path`。
它靠的是「解释器会把脚本所在目录塞进 `sys.path[0]`」。

正常 CPython / venv **确实会塞**，所以一直没暴露。但交付包自带的 `python/` 是**可嵌入版**
（embeddable）：只要 `python312._pth` 存在，解释器就**不再**把脚本目录加进 `sys.path`。

同一个文件，两个解释器两种命运：

```
# 内置运行时 —— 也就是 GATES 里 PY_RUNTIME 指向的那个
$ python/python.exe tools/check_web_js_syntax.py
ModuleNotFoundError: No module named 'check_bridge_methods'
exit=1

# 修好之后
$ python/python.exe tools/check_web_js_syntax.py
扫描范围：页面 45 个 / 内联块 64 段 / 外链 JS 23 个 = 共 87 段（其中 2 段按 module 解析）
PASS：87 段全部通过语法检查（0 错）
exit=0
```

**87 段 JS/HTML 从来没被检查过。** 而且它不是"静默变绿"，是"一启动就崩"——
`GATES` 里登记的正是 `PY_RUNTIME`，也就是**每次用内置运行时跑全量闸门，这道门都在崩**。
它的变异刀同样死在起跑线：

```
$ python/python.exe tools/_qc_web_js_syntax_mutation.py
FAIL 起点就不是绿的，变异没有意义
```

这不是本文件独有的写法问题，而是**本目录里唯一一个没把 `tools/` 显式加进去的**：
`check_api_wiring` / `check_bridge_guards` / `check_broadcast_types` /
`check_runtime_audio_guard` / `check_site_counts` 五个都加了。补齐即可，一行的事。

修好之后它的刀也第一次能跑（三刀全 PASS）。

> 这一条的形状值得单独记：**它不报错、不静默，它是"红着但不跑"。**
> 一个永远红的闸门和永远绿的闸门一样没用——**红久了就没人看了**，
> 而"红"让人以为"判据在工作，只是代码有问题"。

## 5. 工具自己踩的两个坑（本轮最该记的部分）

### 坑① 退化桩必须 import-safe —— 它差点让我误报一个"空转"缺陷

第一版桩写成顶层 `sys.exit(0)`。跑 `_qc_bridge_guards_mutation.py` 时它报了：

```
✗ D1 闸门≡exit 0：套件仍然全绿 —— 空转（判据这样退化它发现不了）
```

看起来是个漂亮的发现。**但那是桩的错，不是套件的错**：这个套件为了动态取"哪个导出有守卫
在用"，会 `import check_bridge_guards`。顶层 `sys.exit(0)` 在 **import 时**就把它带走了——
整个套件**一行刀都没跑**，却以 exit 0 收场。

改成 `if __name__ == "__main__":` 之后，同一对的表现是崩溃
（`AttributeError: module 'check_bridge_guards' has no attribute 'scan_files'`），
说明它其实**会**失败，只是本工具对它不适用（进程内 import，换文件无效）。

> 与第二十一轮 `{star}` 那个 bug 是同一类：**测别人之前先测自己的仪器。**
> 一个"发现"如果只来自一次没有对照的观察，很可能只是仪器坏了。

### 坑② 套件的输出里会混进闸门的 Traceback

第一版判"崩溃"用的是 `"Traceback" in out`。但套件普遍写成
`(p.stdout or "") + (p.stderr or "")`，于是**闸门**抛的 Traceback 被算成套件崩了。
实测 `_qc_silent_mutation.py` 明明规规矩矩印了「FAIL：5 刀未抓住」，却被判成 `WEAK`。

正确判据：traceback 的帧里必须出现**套件自己的文件名**。K9 就是钉这个的。

## 6. 十刀 + 对照

样本全建在 tempfile，每个刀一套独立小仓（`tools/` 里只有桩闸门 + 桩套件），
**不碰仓库一个字节**。

```
PASS K1  只判退出码的正向套件        → VACUOUS（D2 方向空转）
PASS K2  只断言"必须绿"的套件        → VACUOUS（D1 方向空转）
PASS K3  两个方向都断言的套件        → CERTIFIED（不许把好套件误判成空转）
PASS K4  退化时崩溃的套件            → WEAK（不算空转，也不算通过）
PASS K5  进程内 import 闸门的套件    → SKIP
PASS K6  基线本来就红的套件          → ERROR
PASS K7  闸门文件不存在              → ABSENT / exit 2
PASS K8  全部 SKIP                   → exit 2（一对都没跑成 ≠ 通过）
PASS K9  输出里有闸门 Traceback 但自己报了失败 → 仍 CERTIFIED（坑②的钉子）
PASS K10 对照：真实仓                 → 无空转、CERTIFIED ≥ 6、exit 0
```

K1 用的是**真实反模式**：`ok = code != 0`，只判非零退出、不判点名。这正是
`_qc_unreachable_mutation.py` 的 docstring 里警告过的「断言的是任意非零退出，
而不是抓到了注入的那个错」——闸门恒红时它分辨不出来。

K3 是**限位刀**：它防的是"把好套件误判成空转"。少了它，把判据改成"只要退化就报 VACUOUS"
也能让 K1/K2 全过，然后工具变成噪声源。

## 2. 缺陷形状：一句话把两件事当一件事

```python
caught = r.returncode != 0
```

它同时承认了两种完全不同的情况：

| 情况 | 实际发生了什么 | 应该算「抓住」吗 |
|---|---|---|
| 闸门 `exit 1`，输出里点名了注入的那个错 | 判据在工作 | 是 |
| 闸门 `exit 1`，因为它在第一行就崩了 | **判据根本没跑** | **不是** |

实测（把闸门整个换成 `raise RuntimeError("闸门自己崩了")`）：

```
$ python tools/_qc_release_numbers_mutation.py
  已抓住：<无输出>
  ...
5 刀全红
exit=0
```

「已抓住：<无输出>」就是全部证据——它抓到的是**空输出**，不是那个注入的错。
一个连第一行都跑不完的闸门，被认证成"五刀全抓"。

> 这和第十八轮 `_qc_unreachable_mutation.py` docstring 里警告过的是同一件事：
> 「断言的是任意非零退出，而不是抓到了注入的那个错」。当时只在那一把刀里写了一句
> 警告，没有推广成判据——**写在注释里的纪律不是纪律。**

## 3. 更隐蔽的一层：恒红的闸门能让**每一把**刀都变红

只把 `!= 0` 换成「要有 `FAIL` 标记」还不够。因为：

> **起点不绿的时候，"全红"这个读数本身什么都不证明。**

闸门恒红 → 每把刀注入后都红 → 套件打印「N 刀全红」→ `exit 0`。
它和"真的抓到了 N 次"长得一模一样，而且比假绿更危险：**假绿还能靠人工复核发现，
"全红"会让人以为判据特别灵敏。**

所以修法是两件事，缺一不可：

```python
def _judged(r) -> bool:
    """闸门是「判出了问题」而不是「崩了」或「什么都没说」。"""
    out = (r.stdout or "") + (r.stderr or "")
    if "Traceback (most recent call last)" in out:
        return False
    return r.returncode != 0 and ("FAIL" in out or "✗" in out)


def _baseline_green() -> bool:
    r = _run_test()
    out = (r.stdout or "") + (r.stderr or "")
    return r.returncode == 0 and "Traceback" not in out
```

```python
if not _baseline_green():
    print("FAIL 起点就不是绿的 —— 恒红的闸门能让每把刀都变红，这种\"全红\"不证明任何事")
    return 1
```

## 2. 第一层缺陷：判定文件不一定在 `tools/` 下

工具一律拼 `tools/<名字>`。特性族的判定在 `src/tests/test_*.py` 或 `tools/test_*.py`：

13 对**全部** `ABSENT`。而 `ABSENT` 的语义是「本树没有这一对，**不计失败也不计通过**」：

```
结果：ABSENT 13
exit 0
```

**一个都没验，却什么都没说。** 这比 `VACUOUS` 更难发现——`VACUOUS` 至少会红。

`ABSENT` 本来是为了让 `PAIRS` 能比本树超前（某一对还在未合的 PR 里），
结果它把"我把路径拼错了"也一起吸收了。这是**同一个类别判断被用在了两种完全不同的情况上**：

| 情况 | 正确结论 |
|---|---|
| 套件不在本树 | `ABSENT`（本树没有这一对） |
| **套件在、判定不在** | **`ERROR`（PAIRS 声明错了：改名 / 拼错 / 路径规则不对）** |

修法：`_resolve()` 带 `/` 的一律当仓根相对路径；ABSENT/ERROR 拆开。

## 3. 第二层缺陷：12/13 判据失效（还是那一句）

## 4. 第三层缺陷：`_judged` 第一版太严，把"判出来了"记成"没抓住"

第一版判据是「非零退出 **且** 有 FAIL **且** 输出里没有 Traceback」。

一个字都没有——那才叫"什么都没说"。

> 这是本轮第三次"仪器太窄"。前两次：第二十三轮的 `FAIL_MARKS` 缺「没抓住」；
> 第二十二轮的 `_is_suite_crash` 把闸门的 Traceback 算成套件崩溃。

## 5. 第四层缺陷：`count(old) == 1` 不保证锚点从行首开始

`_qc_pathrefs_mutation.py` 的 H 刀：

```python
E("                    except OSError:"),        # 20 空格
```

而 `tools/_qc_path_refs.py:144` 是 **24 空格**。20 空格的串正好是 24 空格那一行的**子串**，
所以 `orig.count(old)` 还是 1 —— 锚点守卫**放行**了。

replace 之后 `except` 掉到第 4 列，缩进全乱：

```

```

而刀只判 `returncode != 0`，于是**"变异把代码改坏了"被算成"抓住了"**。

# 十一、空变异体检：另外 48 把刀的空转风险一直是零覆盖（2026-11-08 追加，并入 PR #18）

## 1. 为什么还要第二个工具

第十节的工具靠「把**判定文件**换成退化实现」。前提是刀有一个独立的判定文件——全仓
79 把 `_qc_*` 里只有 26 对有，另外 48 把是「改完源码自己在进程内断言」，换文件对它们
完全无效。也就是说**那 48 把的空转风险一直是零覆盖**，而"零覆盖"在汇总里和"全验过"
长得一模一样。

这一轮换方向：**不退化判定，退化变异本身**。

```
空变异 = 把 MUTS 里的 (old, new) 换成 (old, old)
```

它等于"什么都没改"。此时：

| 判定 | 刀应该怎样 | 说明 |
|---|---|---|
| 有牙 | 报「没抓住」→ `exit != 0` | 没东西可抓，它知道 |
| 空转 | 报「N 刀全红」→ `exit 0` | **什么都没改，它却说全抓到了** |

这个方向不需要知道判定在哪、也不需要它是文件还是进程内断言——对 79 把一视同仁。
两个方向是互补的两半：

| 手法 | 证明什么 |
|---|---|
| 换判定文件（第十节） | 判定变坏时刀会红 |
| 空变异（本节） | 没东西可抓时刀不会假红 |

## 2. 普查先抓到的是仪器自己的两次错

**① `_noop()` 盲取"最后两个元素"当 `(old, new)`。** `_qc_about_tier_mutation` 的形状是
`(名字, old_thunk, new_thunk, 说明)`，于是它把 **说明** 换成了 `new_thunk`：空变异根本
没发生，刀照常跑、照常全红，工具却判它 `VACUOUS`。第一次普查报 6 把空转，**5 把是假的**。
修法：按载荷类型定位（两个可调用对象 / 两个 bytes / 嵌套对），改完再用 `is` 验证
old 与 new 是同一个对象——**宁可 `SKIP`，也不产出一个假的 `VACUOUS`**。

**② runner 把刀换了个环境跑。** runner 从临时目录启动，`sys.path[0]` 变成 runner 所在
目录，于是 `_qc_api_wiring_mutation` 一进来就
`ModuleNotFoundError: No module named 'check_api_wiring'`，被记成 `ERROR`。可刀平时是
`python tools/_qc_x.py` 跑的，那时 `sys.path[0]` 就是 `tools/`。补一行 `sys.path.insert`
之后它从 `ERROR` 变成 `CERTIFIED`。

两次都是「仪器太窄」——本轮是第 4、第 5 次。

## 3. 顺带查出的真缺陷：`导入冒烟复核` 在 `PY_VENV` 下一直是 6 FAIL

普查里 `_qc_smoke_retry_mutation` 报「起点就红」，手工
`python tools/test_smoke_import_retry.py` 却是 12 PASS / 0 FAIL。差别只在解释器——而
`check_all.py` 给这道门配的正是 `PY_VENV`。两层原因，都不在产品代码里：

1. **`env["PYTHONPATH"] = root` 在随包嵌入式运行时下是死代码。** `python/` 是带 `._pth`
   的嵌入式运行时：`sys.path` 固定，不吃 `PYTHONPATH`、也不加 cwd。
   ```
   PYTHONPATH=<root> .venv/Scripts/python.exe -c "import src.fixturepkg.ok"  → ModuleNotFoundError
   sys.path.insert(0, root) 之后                                            → rc 0
   ```
   后果不止夹具：`--root` 指向的树**可能根本不是被 import 的那棵树**（`._pth` 里有包根）。
2. **夹具的 `src/` 少了 `__init__.py`**，成了**命名空间包**。命名空间包是兜底——只有所有
   `sys.path` 条目里都没找到常规包时才用它；而 `DaniaAI\src` 是常规包，直接胜出，
   `src.fixturepkg` 永远解析不到。

| | before | after |
|---|---|---|
| `.venv/Scripts/python.exe` | 6 PASS / 6 FAIL | **12 PASS / 0 FAIL**，exit 0 |
| `python` | 12 PASS / 0 FAIL | 12 PASS / 0 FAIL |
| `_qc_smoke_retry_mutation`（venv） | 起点就红 | 3 刀全红 + 起点绿 + 还原后绿 |

**这两处没有变异刀，而且不该硬造**：在常规 CPython 下把它们改回去，整套自测仍然全绿
（没有第二个 `src` 来抢，`PYTHONPATH` 也照常生效），刀抓不到任何东西——那就是空转刀。
能钉住它们的只有「换一个把包根放进 `sys.path` 的解释器跑」。

## 2. A5 探针：给"没有样本"一个自己的状态

## 3. A5 刀：先修起点，再修刀

## 5. 在场感：修产品，不修测试
