## 附：真机音频缺口 —— 真机硬件/驱动缺口，代码不可修

**现象**：日志 `麦克风启动失败: Error querying device -1`。

**根因**（多轮实测坐实，**非代码 bug，是本机硬件/驱动缺口**）：
- 本机**无系统默认输入设备**：`sd.default.device = [-1, 1]`（输入 -1 = 无），MME/DirectSound/
  WASAPI 层 `default_input_device` 全 -1；系统 AudioEndpoint 里「麦克风 (Realtek)」状态 Unknown
  （扬声器 OK）→ 系统层就没启用麦克风端点
- 有输入通道的设备只有 3 个，全在 **WDM-KS**：8 麦克风、10 立体声混音、11 线路输入，但——
  - WDM-KS **不支持 blocking read**（`Blocking API not supported yet`）
  - 三设备 **16000Hz 全 `Invalid sample rate`**，只有 48000Hz（vosk 要 16k）
  - 按产品真实路径用**回调式 48kHz** 能建流，但建流后 `active=False`、**2.5s 零回调**（拿不到数据）

**为什么不是"改配置就能绕过"**：把 `proactive.duplex_mic_device` 指到 `8` 只解决了"跳过不存在的
default"，但底层仍 16k 无效 + 回调零数据。曾设想的「自动选设备 + 48k→16k 重采样」也**拿不到音频
数据**——卡在系统层没有可用麦克风端点，不是 Python 层能补的。

**结论 / 建议**：**真机硬件或驱动缺口，需先在系统里启用/插入麦克风端点**，让 MME/WASAPI 层出现
可用输入设备后再验。代码层（`audio_io.py` / `asr.py`）未改、也不宜改。

1. **必备文件**：36 个，逐条判存在。

   局限如实写明：动态 import 与 `from . import X` 里的属性名不判，那是 compileall 与

### 闭包抓到的真缺口（P2，非阻塞）

# 第九轮 · 修 `--root` 假绿 + 把 P2 链路钉死

## 1. 又一个「闸门自己会骗人」：验的不是目标包

第八轮把 `--root` 写成「可指向另一份待验交付包」，但 `check_self_heal` 里是

```python
from src.config import ensure_config_file     # sys.path[0] 是 SCRIPT_ROOT
```

`SCRIPT_ROOT` 是**闸门所在包**。也就是说 `--root B` 时，自愈三态验的是 A 的实现。
发布流程恰恰是最需要用 `--root` 验「刚打出来的那份包」，这个假绿比没有闸门更危险
（它给了一份看起来合格的报告）。

**复现（修前，已实测）**：临时目录放两份真实配置，`src/config.py` 写成恒返回
`("missing", path)`，调 `check_self_heal(tmp)` → 返回
`PASS 缺配置→created / 有实配→exists / 无模板→missing`。目标包坏成这样照样全绿。

## 2. 修法：从目标包自己的源码里抽出函数单独执行

新增 `_load_target_ensure(root)`：

- `ast.parse` 读 `root/src/config.py`；
- 只取 `ensure_config_file` 这一个 `FunctionDef` 与 `CONFIG_TEMPLATE_NAMES` 字面量常量；
- 放进干净命名空间 `{"os", "shutil", "CONFIG_TEMPLATE_NAMES"}` 里 `exec`。

好处：**不 import 整包**（不触发模块级副作用、不依赖 `yaml` / `win32` 等第三方库）、
**不落到 SCRIPT_ROOT 的 `src`**、仍是纯只读。取不到函数或常量 → **FAIL**（旧实现是 WARN），
提示「检查 `--root` 指向的是完整交付包；闸门不会再拿自己包里的实现顶替」。

**修后同一复现**：目标包恒 `missing` → `FAIL 行为异常：created, exists（实测 missing/missing/missing）`；
把目标包换成真实 `src/config.py` → `PASS 目标包自身实现：…`。两个方向都验过。

# 第十轮 · 补「文件在 ≠ 能用」（文件实体闸门）

## 1. 为什么这轮要查

同一类反模式在本项目里已经出现过三次，前两次都被修了，第三次漏在闸门自己身上：

| 轮次 | 反模式 | 修法 |
|---|---|---|
| 第一轮 | `os.path.isfile("api-ms-win-crt-runtime-l1-1-0.dll")` → 只看文件在不在，不看能不能加载 | 改 `ctypes.WinDLL()` 试加载 |
| 第一轮 | `os.path.exists(handshake)` → 只看文件在不在，不看进程活不活 | 改 loopback TCP 判活 |
| **第十轮** | `os.path.isfile(rel)` 判必备文件 → **只看文件在不在，不看内容对不对** | 新增「文件实体」检查 |

第三处的危害最直接：打包脚本在解压/复制阶段被中断，或磁盘满、或 antivirus 把
`electron.exe` 截成 0 字节，`check_required_files` 依然报 **36 个必备文件齐全**，
`check_required_dirs` 依然数得到 120 个文件（空文件也计数），闸门全绿放行。

## 2. 复现（修前）

构造一个最小交付包：所有必备文件写入 `b"x"*128` 占位、资源子树按各自下限补空文件，
然后把两个最关键的产物弄坏：

- `src/ui/web/index.html` → **0 字节**（用户看到的整个界面没了）
- `shell/node_modules/electron/dist/electron.exe` → **1 字节 `b"M"`**（桌宠壳起不来）

修前实测：

```text

 'check_source_closure': 'WARN', 'check_template': 'PASS',
 'check_template_secrets': 'PASS', 'check_self_heal': 'PASS'}
FAIL 数 = 0
```

**0 FAIL。** 一个打不开界面、起不了壳的包被判为「可放行」。

## 3. 修法：用魔数/结构标记，不猜大小

新增 `check_file_integrity()`，对 19 个关键产物按类型取客观判据（缺文件的由
`check_required_files` 报，这里跳过以免重复刷屏）：

| 类型 | 文件 | 判据 |
|---|---|---|
| PE（6） | `python.exe` / `pythonw.exe` / `python312.dll` / `vcruntime140.dll` / `electron.exe` / `Uninstall.exe` | 头 2 字节 `MZ` + ≥64 字节 |
| HTML（4） | `web/index.html` / `loading.html` / `notify.html` / `live2d/rig/index.html` | 含 `<!doctype` / `<html` / `<head` / `<body` 之一 + ≥64 字节 |
| 音频（1） | `assets/voices/daniya_ref.wav` | 头 `RIFF`、第 8-12 字节 `WAVE` |
| 文本（7） | `shell/main.js`、`shell/preload.js`、`requirements.txt`、4 个 prompt | 前 4KB 去空白后非空 |
| 配置（1） | `config.yaml` | `yaml.safe_load` 结果是 `dict`（不是列表/标量/解析失败） |

`MIN_ARTIFACT_BYTES = 64` 只用来挡空文件/残片——真实产物最小的也有 2KB，
设成 64 是刻意留出「不猜体积」的余量，真正的判据是格式标记。

**为什么不是「大小阈值」**：阈值必然要么误伤（未来某个资源变小）要么漏检
（截断到阈值以上）。魔数是文件格式自带的约束，不随版本漂移。

# 第十一轮 · 依赖是否真的装进了内置运行时

## 1. 为什么这轮要查

doctor 有一项「核心依赖」：从 `requirements.txt` 的「核心」段取 12 个发行包，逐个
`importlib.import_module`，缺一个就 FAIL。问题在于**它只能在用户机器上跑** —— 等它报红，
包已经发出去了，用户已经双击了。

而闸门这边只硬编码了 4 个 site-packages 标记（`yaml` / `sounddevice` / `vosk` / `webview`），
其中只有 3 个属于核心档（`vosk` 其实在「重要」档）。也就是说 `requirements.txt` 的 12 个
核心依赖里有 **9 个**（`httpx` / `numpy` / `websockets` / `dashscope` / `mss` / `Pillow` /
`requests` / `rich` / `psutil`）**没有任何交付期校验**。
典型翻车场景：改了 `requirements.txt` 加了新依赖，忘了重跑 `make_dist.py --install-deps`，
打出来的包在开发机上跑得好好的（开发机装过），到用户机上 `ModuleNotFoundError`。

## 2. 实测基线（真实交付包）

| 档位 | requirements 条目 | 包内已装 | 缺 |
|---|---|---|---|
| 核心（缺一不可） | 12 | **12** | 0 |
| 重要（功能降级） | 13 | **13** | 0 |
| 可选（失败不影响启动） | 16 | 4 | 12 |

可选缺的 12 项（`rapidocr-onnxruntime` / `pynput` / `opencv-python` …）与 doctor 的
既有 WARN 完全对得上，属预期。**核心与重要都是满的** —— 说明当前这个包的打包是干净的，
这一项在真实包上应当是 PASS，不制造噪音。

## 3. 修法：dist-info 作为「pip 真装过」的权威痕迹

新增 `check_dependencies()`，**不 import、不执行目标包代码**（保持闸门只读）：

1. 用与 `tools/doctor.py:_parse_requirements` **完全相同**的分节约定读 `requirements.txt`
   （`# ===== 核心 =====` 这类注释行）。两边各读一套会互相打架，所以约定必须共用。
2. 扫 `python/Lib/site-packages/*.dist-info`，目录名按 wheel 规范从右切版本号
   （`PyYAML-6.0.2.dist-info` → `PyYAML`），名字做 `-/_/.` 归一化后建索引。
3. 分级判定：**核心缺 → FAIL**；重要缺 → WARN；可选不管。
4. 兜底：dist-info 没了但模块本体在（`<import>/__init__.py` 或 `<import>.py`）→ WARN
   「能用但缺元数据」，不误判成 FAIL。

判据为什么选 dist-info 而不是「目录在不在」：目录可以被手工拷贝伪造，`dist-info` 是
`pip install` 留下的唯一权威记录，含版本与 `RECORD`。它同时也回答「装的是哪个版本」。

## 4. 我自己踩的一个测量坑（值得记下来）

第一次探测时，`dist-info` 侧按 `-` 切成 `edge`，需求侧却拿完整的 `edge-tts` 去比，
于是 `edge-tts`、`websocket-client` 被误报为「缺失」。差一点就把这条写进结论。

修正归一化（两侧统一 `-/_/.` 去分隔符）后，重要档从「13 项缺 2」变成 **13/13 全在**。
教训：**任何「名字比对」类判据，必须先让两侧用同一个归一化函数**，否则误报会伪装成缺陷。
这条也写进了代码注释（`_norm_dist` 与 doctor 的 `_norm` 同款）。

## 5. 变异矩阵（新增 4 刀）

| 场景 | 破坏方式 | 期望 | 实测 |
|---|---|---|---|
| Y | 删掉 `numpy` 的 dist-info 且无模块 | `check_dependencies` FAIL | ✅ |
| Z | 删掉「重要」档 `pypinyin` 的 dist-info | 只 WARN，不许 FAIL | ✅ |

## 6. 附记：一次无法复现的 1 FAIL（取证教训，不是产品缺陷）

本轮验证时，有一次 doctor 报 **15 PASS / 3 WARN / 1 FAIL**。此后连续 **9 次**
（含 3 次与 `compileall` 并行、5 次与闸门+两个 selftest 并行、4 次纯顺序）全部为
**16 PASS / 3 WARN / 0 FAIL**，无法复现。

没能定性的原因在我自己的取证方式：当时用 `| tail -3` 取汇总，**FAIL 那一行被截掉了**。
doctor 不落盘（已确认 `logs/` 里无 doctor 痕迹），事后无从恢复。

两点结论：
- 该次 FAIL 未复现，且 9 次复跑干净，不据此判产品缺陷；但 doctor 会真起一次 Electron 壳、
  真合成一次音频，**并发跑时存在资源争用**，属于「工具被并发调用」的使用问题。
- **跑 doctor 不要用 `tail` 截断**：要么看全量，要么 `grep -E "\[FAIL\]"`。这条已写进本章，
  后续所有复验都按此执行。

# 第十二轮 · 让闸门「真跑一次」：可选 `--smoke`

## 1. 为什么这轮要查

前十轮把闸门做成 8 项，全部是**静态判据**：文件在不在、内容对不对、模块能不能解析、
依赖有没有 dist-info。它们能挡住「漏发」，但挡不住一类问题 —— **东西都在，就是跑不起来**：

| 静态判据看不出的事 | 后果 |
|---|---|
| 内置 `python.exe` 与 `.pyd` 位数不匹配（32/64） | 解释器起不来，或 numpy 导入失败 |
| UCRT / VC 运行时在目标机缺失 | `numpy` 等 C 扩展加载失败（第一轮踩过的正是这个） |
| 安全软件把 `python.exe` 隔离/拦截 | 双击没反应 |
| `site-packages` 里只有目录、没有可加载的 `.pyd` | `import` 才炸 |

这几件事有一个共同点：**只有真执行一次才知道**。而唯一能报出它们的 doctor，
本身就跑在这个解释器上 —— 解释器坏了，doctor 连启动都做不到。

## 2. 设计：默认关闭，只在自己打的包上开

`--smoke` 是**可选**的第 9 项，不放进默认 `CHECKS`：

```python
checks = CHECKS + ((check_runtime_smoke,) if args.smoke else ())
```

理由：闸门此前承诺「只读、不执行目标包代码」，这条承诺被 `--root` 场景依赖着
（拿它验来路不明的目录时，不该执行里面的程序）。所以：

- **默认**：仍是 8 项纯静态，`7 PASS / 1 WARN / 0 FAIL`。
- **`--smoke`**：追加执行 `{root}/python/python.exe -c "<固定探针>"`，`8 PASS / 1 WARN / 0 FAIL`。

探针只做三件事，不读配置、不写文件、不联网：

```python
SMOKE_PROBE = (
    "import sys, numpy, yaml;"
    "print('SMOKE_OK', sys.version_info[0], sys.version_info[1],"
    " numpy.__version__, yaml.__version__, int(getattr(sys.flags, 'isolated', 0)))"
)
SMOKE_TIMEOUT_S = 120
```

**为什么探针里一定要有 `numpy`**：它是包里唯一同时依赖 UCRT、BLAS 和 `.pyd` 加载的核心扩展。
`numpy` 导得进来，说明「位数 + VC 运行时 + 扩展加载」这条链是通的；只 `import sys`
证明不了任何有价值的东西。

判定用「退出码 + 成功标记」双条件，不只看退出码：`python.exe -c` 在某些拦截场景下
会以 0 退出但什么都没跑，只看 `returncode` 会假绿。

## 3. 实测（真实交付包）

```text
[PASS] 运行时冒烟      python 3.12 · numpy 2.5.4 · PyYAML 6.0.3 · isolated=1
```

`isolated=1` 顺带印证了 doctor「运行期隔离」那一项：内置运行时确实由 `python312._pth`
固定在 isolated 模式，不会加载包外路径。若某次打包漏了 `_pth`，这里会显示 `isolated=0`，
并附一句提示（**只提示、不判红** —— 因为 doctor 才是这项的权威判据，闸门不越权抢红）。

## 4. 变异矩阵（新增 4 刀）

| 场景 | 破坏方式 | 期望 | 实测 |
|---|---|---|---|
| AC | CLI `--smoke` 打在 `python.exe` 是占位的最小包上 | rc=1，FAIL 落在「运行时冒烟」 | ✅ |
| AD | `subprocess.run` 返回 `exit=0` 但没有 `SMOKE_OK` 标记 | FAIL（证明不是只看退出码） | ✅ |
| AE | 探针输出 `isolated=0` | PASS + 提示，不判红 | ✅ |

# 第十四轮 · 解释器守卫：挡住「用错 python 跑 doctor」的误导性 FAIL

## 1. 前提变化

用户给「全部授权，自行优化」。前一轮已把桌宠回退链的源码缺口真正修掉；本轮换口径再扫——
不看「产品功能缺口」，看「授权内还能动真格、且用户没提过的地方」。

## 2. 新发现（之前十二轮都没查过的角度）

跑全量自检时，`tools/doctor.py` 用**系统 python**（agent runtime 的解释器）跑得到
**10 PASS / 5 WARN / 4 FAIL**，而用**包内** `python/python.exe` 跑得到干净的
**16 PASS / 3 WARN / 0 FAIL**。两套 FAIL 全是「该解释器没装包依赖」的假象：

- `[FAIL] 核心依赖缺失：sounddevice / pywebview / dashscope / mss`
- `[FAIL] 语音合成 pyttsx3 / 语音识别 vosk 未装`
- `[FAIL] PermissionError 自检项自身异常（CHAT_REFERENCE_PROTECTED）`
- `[WARN] 唤醒词 pypinyin 未装，退化为精确匹配`

包内 `python/` 齐全（`python/python.exe` + 完整 site-packages，isolated 模式）。但**包内
python 不在系统 PATH**，用户很容易直接 `python main.py --doctor` 触发同样假象——doctor
第一句甚至自己就 WARN「非项目解释器」，但仍往下输出一堆误导 FAIL，把真信号（签名、api_key）
埋进噪声。这会让用户误判「包是坏的」。

## 3. 改动

`main.py` 的 `--doctor` 截获块（第 125 行）——它是"零三方依赖也能跑"的诊断入口，正好
在 doctor 真结果前有插入点。加**解释器守卫**：检测到「交付包存在 `python/python.exe`」
且「当前 `sys.executable` 不是它」时，在 doctor 跑之前打一段醒目提示：

- 列出非内置解释器跑 doctor 会看到的假象（核心依赖/语音/唤醒词三类）
- 给出正确的重跑命令（内置 python 绝对路径）
- **不阻止运行、不改退出码、不改变 doctor 自身输出**——纯只读提醒，让用户自己决定

## 4. 双向变异验证

| 场景 | 结果 |
|---|---|
| 系统 python 跑 → **打印守卫提示**（当前/内置解释器路径 + 三类假象 + 重跑命令）+ 4 个误导 FAIL | ✓ 正确（提示出现） |
| 包内 python 跑 → **无守卫提示**，直接干净 16-3-0 | ✓ 正确（不误报） |
