## 三、核心发现：openpyxl 的 sheet 数与 save 耗时近似线性

### 3.1 分段定位

`export/class-schedule` 748ms 的构成：

```
load_from_excel          1.0 ms
build_from_entries       3.0 ms
按班级分组                0.0 ms   (17 个班)
scan_cross_course        0.6 ms
group_by_course×N        0.1 ms
建 sheet + 写行           6.5 ms
wb.save()              736.9 ms   ← 98.5%
```

**全部时间在 `wb.save()`。**

### 3.2 不是样式的问题

| 模式 | save 耗时 |
|---|---:|
| A 纯数据（无任何样式） | **762.9 ms** |
| B 仅表头加粗（当前实现） | 683.2 ms |
| C 每行首列也加粗（假设最坏） | 742.4 ms |

**纯数据反而最慢。** 样式被 openpyxl 合并进共享样式表，不构成瓶颈。

### 3.3 是 sheet 数的问题

固定变量测试（每行 9 列，内容相同）：

| sheet 数 | 行/表 | 总行 | save 耗时 | 每 sheet 均摊 |
|---:|---:|---:|---:|---:|
| 1 | 433 | 433 | **87 ms** | 87 |
| 5 | 87 | 435 | 245 ms | 49 |
| 17 | 25 | 425 | **720 ms** | 42 |
| 17 | **1** | **17** | **757 ms** | 45 |
| 50 | 1 | 50 | 2124 ms | 42 |
| 100 | 1 | 100 | 4202 ms | 42 |
| 200 | 1 | 200 | **8620 ms** | 43 |

**决定性证据**：17 个 sheet、**只有 17 行**（每表 1 行）也要 757ms，与 17 个 sheet、425 行的 720ms 几乎相同。

**每增加一个 sheet，约 +43ms 固定开销。**

### 3.4 为什么学校规模下会更慢

当前是 17 个班 → 747ms。若某学院有 50 个班：

```
50 × 43ms ≈ 2.1 秒
100 个班 ≈ 4.2 秒
```

**这不是理论值，上表 50/100/200 sheet 是实测的。**

## 四、其他性能观察

### 4.1 parse_cache 价值极大

| | 耗时 | 加速比 |
|---|---:|---:|
| 冷解析（433 行） | 161.6 ms | 1× |
| 热解析（缓存） | 0.4 ms | **404×** |

`get_teacher_roles` 的对比更极端：

| | 耗时 |
|---|---:|
| 缓存命中 | **0.0 ms** |
| 缓存未命中（重新 load_workbook） | **156.1 ms** |

**缓存把一次 156ms 的重复解析降到可忽略（< 0.1ms），至少 1500 倍以上。**

缓存按 `path + mtime_ns + size` 做签名，文件不变就不会失效。这个设计是对的。

### 4.2 CP-SAT 求解 686ms 是合理的

单班求解 686ms，涉及 17 门课 × 多组约束。这是求解器本身的开销，不是代码问题。

对照：`get_course_overview` 只要 0.3ms（纯内存聚合）。

### 4.3 冲突扫描极快

433 行全表 0.7ms，命中 5 条。说明 `scan_table` 的索引（`_by_time` / `_by_room` / `_by_teacher` / `_by_class`）生效了。

## 五、R13 过程中我修正的两个测量错误

### 错误 1：手工构造缓存导致误报 143ms

第一版基线里 `get_teacher_roles` 显示 143.6ms，而 `get_all_teachers` 是 0.0ms。

查原因：我用 `parse_cache.save()` 手工写了缓存，**没写 `roles` 字段**，导致它走了 `load_workbook` 慢路径。

**页面真实加载时不会这样**——`load_from_excel` 会一并写入 `roles`。

### 错误 2：测度时环境变量已被切回 `PARSE_CACHE=0`

修了错误 1 后仍然 165ms。再查：`parse_cache._enabled()` 是**每次调用时读环境变量**，而脚本在测完热解析后把 `PARSE_CACHE` 切回了 `"0"`。

所以 `get_teacher_roles` 里的 `parse_cache.load()` 直接返回 `None`。

### 教训

**性能测量对环境状态的敏感性远超功能测试。**

同一个函数，缓存开/关差 1500 倍以上。基准脚本必须先固定环境，再测；不能"顺手切一下再切回来"。

这与 R12 的教训同源：**测试环境和目标环境不一致时，测出来的数字毫无意义。**

## 六、优化建议（本轮不改）

### P1 · 班级课表导出分批

**问题**：17 sheet = 747ms，50 sheet 会到 2s。

**可选方案**：

| 方案 | 改动量 | 效果 |
|---|---|---|
| 导出时按班级筛选（一次 1-2 个 sheet） | 小 | 单次 < 130ms，但用户要多点几次 |
| 保留全量但加进度提示 | 小 | 体感改善，实际耗时不变 |
| 换 `xlsxwriter` 写多 sheet | 中 | 已知比 openpyxl 快 3-5 倍，需引入新依赖 |
| 服务端缓存导出结果（按数据指纹） | 中 | 二次导出 < 10ms |

**推荐**：先加"导出全部班级需要约 1 秒"的提示，成本最低；若学校规模扩大，再考虑换库或缓存。

**不建议**：把 17 个 sheet 合并成 1 个（破坏"每班一页"的产品设计）。

### P2 · 冷启动预热

当前冷解析 161.6ms，发生在首个请求（`_ensure_loaded`）。已经有 `warmup.start_background()` 预热 CP-SAT，可以一并预热解析。

**但从数据看**：热解析只要 0.4ms，且 `parse_cache` 落盘。**只有真正的首次部署**会付 161ms。优先级低。

### P3 · 不必优化

- 内存查询 < 0.1ms
- 冲突扫描 0.7ms
- 台账导出 2.1ms

**这些已经是"不可能成为瓶颈"的量级。**

## 八、结论

**这个项目的性能是健康的。**

- 99% 的路径在 20ms 内
- 唯一的 747ms 有明确的、可量化的原因（openpyxl 每 sheet 43ms 固定开销）
- 而且这个原因**不在项目代码里**，是第三方库特性

`wb.save()` 87ms（1 sheet）→ 8620ms（200 sheet）的曲线说明：**如果学校规模扩大，班级课表导出会成为第一个瓶颈。**

但在当前 17 个班的规模下，747ms 是可接受的（用户点一次导出，等不到 1 秒）。

**建议不做代码改动，只在 UI 上给个"正在生成…"的提示**，成本 1 行，收益是消除"是不是卡死了"的疑虑。
