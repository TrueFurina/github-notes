# R75：把「一次被锁的撤销按住整个事件循环 11 秒」关掉

- 日期：2026-11-02 21:52–22:2x
- 分支基线：R74（782 passed / 32 skipped，`2079c07815`）
- 本轮性质：**改生产代码**（`backend/app/api/reschedule.py`）+ 只加测试（`test_event_loop_blocking.py`）
- 关闭的遗留：R74 §6「`land_undo` 是 `async def`、`with _land_lock:` 里同步调 `undo` ⇒ 事件循环停摆 11.08 s」

## 1. 结论先行

同一段业务、同一把锁、同一个库，**只改"跑在哪条线程"**：

| 组 | 形状 | undo 耗时 | 事件循环心跳最大滞后 |
|---|---|---|---|
| A | `async def` 里同步 `with _land_lock:`（改前） | 0.469 s | **459.0 ms** |
| B | `await run_in_threadpool(_locked_land_undo, ...)` | 0.484 s | **6.0 ms** |
| B′ | 同上，busy_timeout 用生产值 5 s | **11.047 s** | **22.0 ms**（714 拍） |

**耗时一点没变**（该等的 sqlite 还是等 11 秒），变的是这 11 秒里**别人还能不能动**。
改前：并发请求、健康检查、SSE 心跳全部排队；改后：只有这一个请求在等。

## 3. 为什么"把 undo 包进 `run_in_threadpool`"是错的

这是本轮最值得记的一条。锁竞争有**两个**面，只治一面等于没治：

```python
# ✗ 看起来改了，其实只治了「锁内的活」
with _land_lock:                                   # ← 等锁仍然发生在事件循环线程上
    out = await run_in_threadpool(plan_landing.undo, _db, _landings())

# ✓ 锁与活一起进工作线程
out = await run_in_threadpool(_locked_land_undo, actor)   # 里面才是 with _land_lock:
```

`_land_lock` 同时是 `_db.entries` 的写锁（`_DB_WRITE_LOCK`，R28）。一次慢落地持锁 11 秒期内，
所有落地/撤销入口都要在**事件循环上原地排队**。第一种写法对"锁内的 sqlite 等待"有效，
对"等锁"完全无效。

**变异体 V4 就是第一种写法，它的结果是死锁而不是变慢**：

```text
== V4: 顺手改法：锁留在事件循环、只把 undo 丢线程池 ==
  ⚠️ 整文件 90 s 未跑完 —— 用例挂死
    🔴 test_land_undo_waiting_on_write_lock_does_not_stall_heartbeat（红）
    🔴 test_two_concurrent_undos_still_serialize（挂死）
```

两个撤销并发时：第一个在事件循环线程上拿到锁、`await` 出去；第二个在**同一条线程**上
等这把锁 ⇒ 事件循环停住 ⇒ 第一个永远回不来。**"看起来更安全"的改法把停摆升级成了死锁。**

## 4. 改动

`backend/app/api/reschedule.py`（唯一改动的生产文件）：

| 位置 | 改什么 |
|---|---|
| 新增 `_locked_land_commit(plan, note, actor)` | `diff → snapshot → apply → save`（失败 `restore` 再抛）整段连同 `with _land_lock:` 一起搬进工作线程 |
| `land_commit` | `diff, rec, applied = await run_in_threadpool(_locked_land_commit, plan, req.note or "", land_by or "")` |
| 新增 `_locked_land_undo(actor)` | 撤销 + **锁内**读 `latest()` 算 R73 的回执 |
| `land_undo` | `out = await run_in_threadpool(_locked_land_undo, actor or "")`；404/500 分型一字未动 |

三处不能想当然的细节：

1. **回执的 `latest()` 必须在锁内读**（R73 的结论）。搬迁时整段一起搬，顺带保住了这条；
   如果只搬 `undo`、把 `undo_receipt` 留在锁外，回执描述的就是"别人插队之后"的状态。
2. **`HTTPException` 跨线程抛是安全的**：`anyio.to_thread` 在同进程内传对象引用、不 pickle，
   异常原样穿透 `await`。`test_land_rollback.py` 的 3 条用例现在自动走这条跨线程路径，全绿。
3. **锁内顺序不许动**：`diff` 必须现算（预览与采纳之间可能有审批调课生效），
   `snapshot` 必须在 `apply` 之前，`save` 失败必须 `restore` 再抛 —— 搬迁是纯搬，不是重写。

## 9. 边界（写清楚，别当成"事件循环再也不会卡"）

1. **只解决了"锁等待"这一型**。其他同步重活（Excel 全量解析、CP-SAT、导出建表、LLM）
   各自有自己的下沉点，本轮一个都没碰。
2. **线程池会被占满**：`run_in_threadpool` 默认 40 个 token。极端情况下 40 个并发
   落地/撤销各等 11 秒，会把线程池占满，导出、求解这些同样用线程池的接口要排队。
   这比"整站停摆 11 秒"好，但**不是零代价** —— 真要治得给"锁等待"单独限流（未做）。
3. **审计脚本仍然看不见锁等待**（R74 的发现没变）：`HEAVY` 按名字排除 `sqlite execute`，
   理由"单条 insert <1 ms"在锁竞争下不成立。本轮的守门人是那两条心跳用例，不是审计脚本。
4. **没有端点层真锁用例**（HTTP 500 + detail + 22 s 白等）：默认连接 5 s，一条要等 22 s。
   同一段代码由单测覆盖，接线由 `test_landing_endpoints.py` / `test_land_rollback.py` 覆盖。
5. **跨机器/CI 的时序未测**：心跳阈值 150 ms 是本地实测（旧形状 459 ms、新形状 6 ms）留的余量，
   CI 上并发负载更重时未取过数。

## 10. 仪器教训第 11 次：`finally` 不保证执行

V4 那次变异让 pytest 死锁，`subprocess` 没有超时 ⇒ 整个执行器被 SIGTERM 打断，
`try/finally` 里的 `restore()` **一行都没跑**，`reschedule.py` 留在变异态：

```
64e65b7fe6... work-repo/backend/app/api/reschedule.py     ← 变异态
302ede98a8... _r75_src_reschedule.py                      ← 真正的版本
```

发现它的方式：随手 `md5sum` 比对（R73 第 8 次之后加的规矩）。修法两条：

1. 执行器给子进程加 `timeout=90`，超时先 `kill` 再**在正常控制流里**复原；
2. 每个变异体跑完都打印并核对 `matches_backup`，不只看脚本自己说"已复原"。

**判据：`SIGTERM`/`Ctrl-C`/进程被杀，都不是"异常"，`finally` 不欠你任何东西。
凡是"改文件→跑测试→复原"的脚本，复原结论必须来自脚本之外的独立核对。**

顺带第二条小的：第一版执行器用 `-k "land_"` 选用例，
`test_two_concurrent_undos_still_serialize` 名字里没有 `land_`，被悄悄过滤掉 ——
V2（丢锁）当时只报 1 red，差点得出"序列化用例对丢锁失明"的错误结论。
**过滤式选择器会把守卫排除在外；变异一律跑整个文件。**
