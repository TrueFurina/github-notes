## R55 · 2026-10-31 · 点一次"撤销"，这次落地就从历史里消失了

### 缺陷：撤销是 DELETE，不是"标记"

`landed_plans` 表存着「方案 + 落地前快照 + 时间」——本来是个不错的审计设计。
但撤销的实现是：

```python
def pop_latest(self):
    rec = self.latest()
    conn.execute("DELETE FROM landed_plans WHERE id = ?", (rec["id"],))
```

**删行。** 于是教秘点一次"撤销"，这次落地在库里一根毛都不剩：什么时候落的、
改了哪些单元、影响多少条 —— 全没了。同时 `actor` 从来没记过：`require_admin`
一直有返回值，但落地时只写 `note=req.note`（调用方可留空），"谁点的采纳"只能事后问人。

而教秘点撤销的本意是**"把课表恢复"**，不是"把这件事从历史里抹掉"。
审计表和能 pop 的栈，在正常使用下看不出区别；出事时是"有据可查"与"什么都没有"。

具体场景：周一落了一键排全校，周三发现某班撞课，撤销。周五教务问"这个班的课
怎么变过两次" —— 现在答不上来，因为周三那次按钮把周一的证据删了。

### 本轮的教训（两条）

**一、"可撤销"和"可审计"是两个模型，冲突点就在"删除"。**

栈的语义天然要 pop（撤销后"当前状态"就该回到前一版），审计的语义天然是
append-only（发生过的事不能消失）。用一张表同时承担，必须先决定谁是主。
这次选**审计为主**：行不删，`revoked_at` 一填，栈就从同一个表里**过滤**出来
（`latest()` = 最后一条未撤销的）。效果是栈的行为一点没变，历史一条不少。

判断依据很简单：**pop 是给"当前状态"用的，delete 才是给"历史"用的。**
如果一次操作既改了当前状态、又删了历史，那它一定搞混了这两件事。

**二、schema 演进最容易在"用户点按钮那一刻"爆炸。**

`CREATE TABLE IF NOT EXISTS` 不会给已存在的表补列。如果只改建表语句，报错会出现在
**教秘刚点完"采纳"**的那一刻（INSERT 带新列 → `no such column`），而不是启动时。
所以迁移必须幂等、必须在 `init_schema()` 里做，并且要有一条"带数据的老库"用例。

顺带说一句诚实的：这条用例是我**先想到才写的**，不是被 bug 教的。但它值这个位置 ——
凡是"改了表结构"的改动，最容易漏的永远是"已经有人在用的那张老表"。
