## 1. 搬的是什么

从 `reschedule.py` 1688–1901 行整块移出（214 行），一个符号都不改语义：

```
LandPlanRequest          # 请求模型
_land_plan_or_400        # 校验（缺字段列出，不静默丢）
land_preview             # POST /parallel/land/preview
_locked_land_commit      # 落地阻塞主体（R75 加的）
land_commit              # POST /parallel/land
_locked_land_undo        # 撤销阻塞主体（R75 加的）
land_undo                # POST /parallel/land/undo
land_history             # GET  /parallel/land/history
land_status              # GET  /parallel/land/status
```

**为什么这一族值得单独成模块**：它自带一套三段式语义（预览不写 / 采纳现算 diff /
撤销弹一条），与调课工单、主数据 CRUD、导出、聊天是四件不相干的事；而 R73 / R74 / R75
三轮的改动**全部**落在这 214 行里 —— 它已经是一个独立的变化单元，只是还挤在 3300 行
的文件中段。

## 2. 搬迁最自然的写法，恰好是最坏的写法

新模块要用 `_db`、`_DB_PATH`、`_landing_store`、`_land_lock`、`_landings()`、
`_ensure_loaded_async()`。这些都是 `reschedule` 的**可变模块状态**，测试靠
`monkeypatch.setattr(reschedule, "_db", db)` 把整条链路指向临时库
（`test_landing_endpoints.py::env`、`test_event_loop_blocking.py::_land_env`）。

**坏的写法**（也是最顺手的）：

```python
from app.api.reschedule import _db, _land_lock, _landings   # ← 值绑定
```

拿到的是**导入那一刻**的对象。之后所有 patch 全部失明，而且**一声不响**：

- 测试可能仍然是绿的 —— 它自己在 fixture 里另建了一份库，端点写进真库也不报错；
- 线上表现为"落了地但状态栏说没落""撤销撤的是别人的方案"。

**采用的写法**：

```python
from app.api import reschedule as _api
...
plan_landing.diff_plan(plan, _api._db.entries)     # 每次调用现取
```

同理 `_land_lock` 不能复制一份：复制 = 两把锁 = 锁等于没锁，R28 修好的"同一间教室同一
时段被排进两门课"重新打开，而任何单线程测试都发现不了。**必须是与 `reschedule._land_lock`
`is` 恒等的同一个对象。**

### 依赖方向（导入期不成环）

- `landing` → `reschedule`：单向，顶层 `from app.api import reschedule as _api`。
- 反向只有 `reschedule` 末尾的模块级 `__getattr__`（PEP 562）**惰性**转发，
  导入期一次都不触发。

先试过普通 import（`reschedule` 末尾 `from app.api.landing import land_commit`），
**实测直接炸**：

```
ImportError: cannot import name 'f' from partially initialized module 'pkg_a'
             (most likely due to a circular import)
```

`from X import 名字` 在 X 尚未执行完时拿不到名字（子模块形式 `from pkg import a` 可以，
因为它走 `sys.modules` 回退；名字不行）。所以改成惰性转发，代价是 `dir()` 与 IDE 补全
看不到这几个旧名 —— 它们只被测试引用，生产代码本轮全仓 grep 确认 0 处。

## 4. 定向变异 5/5：守卫真的会红，而且红在该红的那一条

执行器 `R76-new/mutrun_r76.py`（零删除、junit 取数、每条打印 `matches_backup`、
子进程 `timeout=180`），判定要求**期望的用例名出现在 junit 的失败清单里** —— 只红一条
无关用例不算通过。

| 变异 | 内容 | 期望红 | 结果 |
|---|---|---|---|
| V1 | 加 `from app.api.reschedule import _land_lock as _copied` | 值绑定守卫 | 检出并命中（1 failed / 10） |
| V2 | `with _api._land_lock:` → `with threading.Lock():` | 第二把锁守卫 | 检出并命中 |
| V3 | `reschedule.router.add_api_route('/parallel/land/status', ...)` | 第二份实现守卫 | 检出并命中 |
| V4 | 锁与活一起回事件循环（R75 的缺陷形状） | 同步锁守卫 | 检出并命中 |
| V5 | `await _api._ensure_loaded_async()` → `_api._ensure_loaded()` | 阻塞调用守卫 | 检出并命中 |

五条复原后 md5 与备份**逐字节一致**（`landing.py = 0db2b80f0a`、`reschedule.py = e0fcec2f13`）。

### 一条自我推翻（第一版守卫是错的）

第 9 条守卫第一版用 `ast.walk(async_fn)` 收集 `with`，于是把 `approve_request` 与
`apply_move` 报成违规 —— 而它们是**正确**写法：

```python
async def apply_move(...):
    def _locked_apply():            # ← 内层是**同步**函数
        with _DB_WRITE_LOCK:        #    锁和工作都在工作线程里
            return _apply_reschedule(...)
    result = await run_in_threadpool(_locked_apply)
```

`ast.walk` 会走进嵌套函数，把内层的 `with` 算到外层 `async def` 头上。改成"只走一层
作用域（遇到 `FunctionDef`/`AsyncFunctionDef`/`Lambda`/`ClassDef` 停住）"之后才正确。
**这条自我推翻有价值**：它反过来确认了守卫能区分"锁在 async 里"（坏）与"锁在 async
里嵌的同步函数里"（好）—— V4 变异就是前者，能红。

## 6. 搬迁顺手撞出的两件事（都不在计划里）

### 6.1 审计门静默缩了半张表（本轮第 13 条教训）

`scripts/audit_async_blocking.py` 里写的是：

```python
path = args[0] if args else "backend/app/api/reschedule.py"
```

于是第一次跑 `audit_async_blocking.py reschedule.py landing.py`：**只扫了第一个文件**，
表里 48 个路由、landing 的 5 条一条没有，`rc=0`、结尾写着"✅ 零 await 轻查询与基线一致"。

> **一道门把一半代码悄悄看漏，比没有这道门更糟** —— 因为它给出的是"已覆盖"的错觉。
> 这与 R75 的 `-k "land_"` 把守卫用例静默过滤是同一类：**过滤式选择器不会告诉你它滤掉了什么。**

处置：

1. 脚本**拒绝多参数**（宁可报错，不猜）：
   ```
   本脚本一次只扫一个文件（收到 2 个：['a.py', 'b.py']）。
   行号列与基线都按单文件计，多文件请分开跑。
   ```
2. CI 里改成两条命令，landing 带 `--no-baseline`：
   ```yaml
   run: |
     python scripts/audit_async_blocking.py backend/app/api/reschedule.py
     python scripts/audit_async_blocking.py backend/app/api/landing.py --no-baseline
   ```
3. 新增 `--no-baseline`：**不比对**基线，但零 await 路由**照样判红**。
   理由：基线是按单文件攒的（reschedule 的 8 个），拿它比 landing 只会打印一句假的
   "✅ 有 8 个零 await 路由被消除"，每个 PR 都来一遍，噪音还会盖掉真正被消除的那几个；
   而"本文件出现零 await 路由就红"比"和别人比"更严格。

实测：两条命令各自 `exit 0`，landing 报"共 5 个路由；零 await 0；重活 0"。

## 8. 没做 / 边界（交下一轮）

1. **`reschedule.py` 仍有 3311 行**：这轮只搬了最独立的一族。按
   `docs/拆分方案-reschedule-api-20261024.md` 还有主数据 CRUD、导出、工单、聊天四块。
   下一刀建议主数据 CRUD（机械性强、守卫多）。
2. **`_landings()` / `_land_lock` / `_DB_PATH` 仍住在 `reschedule`**：`landing` 靠
   `_api.xxx` 取值。更彻底的做法是抽一个 `app/state.py` 承载这些可变状态，但那要动
   `reschedule` 里所有 `_db` 引用与测试的 patch 点，属于另一轮。
3. **端点层真锁 HTTP 用例**（R75 §9 遗留）未做：默认 5 s 连接下一条用例白等 22 s。
4. **线程池 40 token 被"等锁请求"占满**的风险仍在（比停摆好，但不是零代价）。
5. **`--no-baseline` 是新机制**：它只对"新增文件"成立。若将来 landing 里出现零 await
   的轻查询，要么改写成有 await，要么把基线改造成带文件维度 —— 那时 `--no-baseline`
   应该被替换掉，而不是继续加开关。
