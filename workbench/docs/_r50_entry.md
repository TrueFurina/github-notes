## R50 · 2026-10-31 · 教师端「我的课程」：课程归属整条链路缺失，周次区间在编数字

### 这一轮为什么查这张卡片

`GET /teachers/{name}/courses` 是**唯一**让教师看到"我教了什么"的入口，也是调课
申请的起点：卡片 → `POST /requests` → 审批 → `POST /apply-move`。这张卡片错了，
后面每一步都在错的基础上走。

上一期把安全/边界/并发/契约/导出/主数据这些域查完了，剩的五个域里「教师端归属」
是唯一一条**同时被界面、申请单、审批台三处消费**的路径。

### 发现一：课程归属，整条链路都没进这张卡片

R-66 起 `ScheduleEntry` 就有显式 `course` 外键；2026-10-24 产品决策 B 把真实表
433 条逐行归到三门课（大学物理实验 B/C、普通物理实验 3）；
`course_bridge.resolve_course` 也早就会算 —— 但 `get_teacher_courses` **一个字都
没用**。分组键只有 `(实验项目, 班级)`。

构造：同一老师、同一班、同一项目，两条记录分属两门课。

```
卡片数 = 1     ← 期望 2，塌缩了
{'course_name': '扭摆法测物体转动惯量', 'class_name': '24物理1班',
 'original_time': '周一 345', 'room': 'A504', 'week_range': '3-5周', ...}
```

后果不是"少一个字段"，是**两门课的课被合成一张卡片**，教师看不到自己上的到底
是哪门课。`course_bridge` 的模块注释里已经写明这个塌缩（"同名项目跨两门课时，
主数据以项目名为 key 会把它们塌缩成一门"），只是没接到这条路径上。

### 发现二：`week_range` 会凭空造出一段连续的周次

```
实际周次 [3, 5, 9, 11]（单双周轮换 —— 物理实验最常见的排法）
week_range = '3-11周'
```

这个字段**是渲染在界面上的**（`views/CoursesView.tsx:60`：
`{original_time} · {room} · {week_range}`）。教师读到"3-11周"只会有两种理解，
而两种都凭空多 5 次课。没有报错、没有空值、没有红色 —— 只是一个看起来很正常
的数字。这正是这一期要找的那一类：**输出错了但无声。**

刻意**不做**的两件事：

1. **分组键不加课程。** 加了会把一张卡片拆成两张，而 `apply-move` 的匹配口径是
   `_label_matches(course_name, e.experiment)`（按实验名）。拆开只会让所有历史
   申请单匹配不上 —— 那是把一个"看不见"的缺陷换成一个"到处报错"的缺陷。
   所以选：**一张卡片 + 显式标记它横跨两门课**。归因要说全，不能让第一门课
   冒充整张卡片。
2. **`course_name` 语义不动**（它一直是实验项目名）。用例 8 专门锁死这一点。

### 本轮的教训（两条，都很硬）

**一、全量测试跑在共享工作副本上，会被别人的半成品污染。**

第一次全量：623 passed。第二次：8 failed，全是 `test_api_auth` 的"伪造令牌必须
401"。看起来像我改坏了鉴权。实际是——另一个会话在 01:06:14 启动了
`mutation_check.py`，把 `app/security.py` 的签名校验改成了
`if False:  # MUTANT: 永远认为签名正确`，我跑测试时文件正处在被变异状态。

排查链条值得记：
1. 全量里 8 条全集中在鉴权，我的改动只碰了教师卡片 —— 域不重叠，先怀疑环境；
2. `find -name "*.mutbak"` 找到 `security.py.mutbak`；
3. `grep MUTANT` 在源文件里直接看到 `if False:`；
4. 文件 mtime 落在我这次测试的时间窗内；
5. `Get-CimInstance Win32_Process` 看到另一个 python 正跑 `mutation_check.py`。

结论不是"我的改动没问题"，而是**"这份工作副本此刻不是可以信任的基线"**。
所以这轮全部验证搬到隔离副本：`/tmp/verify` = 完整工作副本 + 远端原版
`security.py`，跑出 635 passed。

**二、`diff` 之前先看换行符。**

推送前差点重演 R43：本地 `reschedule.py` 是 **CRLF**（3311 行），远端是 **LF**
（3298 行）。直接推，GitHub 会把整个 3298 行文件全标成改动 —— 真正的 9 行修改
埋在里面谁也看不见，而"我明明只改了几行"的认知会让我跳过核对。

做法改成三步：**拿远端原文 → 在它上面打我的补丁 → 再 `diff` 一次，
只允许出现我那一处。** 顺带发现本地还夹着一处**别人未推送的改动**
（`master_store.consume_corrupt_flag()`），按"只推自己的"排除了。

最终提交 `+9/−2`、`+62/−7`、`+230/0` —— 这三个数字才是"逐行核对"过了的证据。

> 教训：逐行核对不是核对 diff，是核对**"远端 + 我的补丁"与"我要推的东西"
> 是否逐字节相同**。中间任何一次文件重写（换行、编码、格式化）都会让这个
> 等式失效，而失效时 `diff` 会给你一个"看起来很多改动"的假象，
> 让人误以为"反正改动这么多，不用细看"。
