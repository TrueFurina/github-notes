# R74 · 撤销的重试：真锁下的 11 秒

> **一句话**：从 R45 起，「撤销标记写失败 ⇒ 重试一次」这条分支只有 monkeypatch 用例。
> 用真锁一测，它不但**几乎不会自愈**，还会把整个事件循环按住 **11.08 秒** ——
> 而专门用来抓事件循环阻塞的那道 CI 门，结构上看不见这种阻塞。

- 日期：2026-11-02 21:26–22:0x
- 分支基线：R73（`2a93cc20ed` / 779 passed）
- 本轮性质：**只加测试，不改生产代码**（原因见 §6）

---

## 1. 为什么"补一条真锁用例"不是补覆盖率

R45 / R59 的三条失败分支用例都长这样：

```python
def boom(*a, **kw):
    raise RuntimeError("模拟 sqlite 写入失败（磁盘满）")
monkeypatch.setattr(store, "revoke", boom)
```

它们证明的是 `undo` 的**异常处理结构**，一点没碰 sqlite。于是三件事一直没被证过：

1. 真锁抛的是 `sqlite3.OperationalError: database is locked`，不是别的错；
2. 两次尝试真的都在等锁（而不是立刻放弃）；
3. 错误文案里那句"**请重试撤销**"是真的能成功的 —— 从来没有人真去重试过。

第 1 条不是洁癖。`undo` 的兜底是 `except Exception as first:`，一旦有人把它收窄成
`except RuntimeError`（看起来"更精确"），三条旧用例**全绿**，而锁竞争这条最常见的
现实失败会变成裸 500。这一支本轮用变异体 V3 实测打出来了（§5）。

## 2. 取证（真锁，不是模拟）

`R74-new/probe_lock.py`：临时库落地一次，另一条连接 `BEGIN IMMEDIATE` 拿 RESERVED 锁，
生产连接保持默认 `busy_timeout=5s`。

```
正常撤销                    0.008 s
持锁期间 store.latest()     0.001 s   ← 只读不受 RESERVED 影响，undo 才会走到 revoke
单次 store.revoke()         5.50 s   ← sqlite3.OperationalError: database is locked
一次完整 undo              11.04 s    success=False, rolled_back=True,
                                     error 里 "database is locked" 出现 2 次（首次+重试）
释放锁后再撤一次            0.017 s   success=True
```

并发的三组对照（`R74-new/probe_loop.py`，50ms 心跳协程记录最大滞后）：

| 组 | undo 耗时 | 心跳最大滞后 | 说明 |
|---|---|---|---|
| A 不持锁 / 同步调用 | 0.01 s | **13 ms** | 基线 |
| B 真锁 / 同步调用 | 11.08 s | **11076 ms** | **当前生产形状**（`async def` 里同步调 `undo`） |
| C 真锁 / `to_thread` | 11.08 s | **14 ms**（184 拍） | 耗时一样，循环活着 |

B 就是 `land_undo` 的真实形状：

```python
async def land_undo(actor: str = Depends(require_admin)):
    await _ensure_loaded_async()
    with _land_lock:                      # threading.Lock，不是 asyncio.Lock
        out = plan_landing.undo(...)      # ← 同步、可能卡 11 s
```

`threading.Lock` 不 yield，`undo` 里有两次 sqlite busy 等待 —— 这 11 秒里**整个进程的
事件循环不转**：并发请求、健康检查、SSE 心跳全部排队。

## 3. 三个发现

### ① "重试一次通常就能自愈"这句注释，基本上是错的

- sqlite 自己已经有 `busy_timeout=5s` 的忙等：**锁在 5 秒内消失，根本进不了 except 分支**。
  新用例 `test_lock_shorter_than_busy_timeout_never_reaches_retry` 把这条钉住
  （锁持 0.03 s、busy_timeout 1 s ⇒ undo 成功且耗时远小于 1 s）。
- 能进 except 的锁，意味着它**已经撑过了 5 秒**。两次尝试之间没有任何间隔（背靠背立刻重打），
  锁不可能在这几微秒里消失。重试的实际效果只是把 5.5 秒的等待变成 **11 秒**的等待。
- 换句话说：**自愈的是 sqlite 的 busy handler，不是那个 `try` 第二次**。
  要让重试有意义，两次之间必须有间隔（退避），这是行为变更，本轮没动（§6）。

### ② 一次被锁的撤销 = 事件循环停摆 11 秒

见 §2 表 B。代价不是"这条请求慢"，而是"**所有**请求慢"。

### ③ 抓事件循环阻塞的那道 CI 门，看不见这一型

`scripts/audit_async_blocking.py` 的 `HEAVY` 白名单**刻意**排除了 `sqlite execute`，
文件里写明了理由：

> 为什么刻意不收 `save` / `load` / `read` / `execute` 这类通用名：
> `sqlite execute` 单条 insert **<1 ms** —— 它们出现在闭包里是常态，报出来等于一次报 18 个路由。

这个前提在**锁竞争**下不成立：同样一条 UPDATE，没人持锁时 0.4 ms，被锁时 5.5 s。
判据是"单次调用的典型耗时"，而锁等待的耗时由**别人**决定 —— 所以这 11 秒对它天然不可见。
这不是脚本写得不好，是"按名字估算耗时"这个方法本身的边界，值得写进它的限制段（下一轮）。

## 7. 一条可复用的判据

> **"重试"要能被证伪，就必须能量出"两次尝试之间环境变了"。**

背靠背的 `try/except` 重试，在 sqlite 这种**自带 busy_timeout** 的驱动上，
跟"把超时调成两倍"在行为上无法区分（本轮的 5.5 s → 11 s 就是证据）。
写"重试"之前先问一句：**第一次失败之后，到我第二次尝试之前，什么变了？**
如果答案是"什么都没变"，那这段代码只是在延长等待。

配套的第二条：**兜底的 `except` 写得越宽，越需要一条真异常的用例**。
`except Exception` 加三条 `RuntimeError` 用例，等于没有用例 ——
变异体 V3 一句话就把这个组合证伪了。

## 8. 仪器教训第 10 次：**每轮最多 50 次删除**（并推翻 R73 的归因）

跑全量变异时又出现大批"无效 · pytest 退出码 1: ?"。这次抓到了原文：

```
[safe-delete][SAFE_DELETE_BULK_CONFIRM_REQUIRED]
  {"count":50,"threshold":50,"scope":"turn",
   "targets":["D:\\github\\work-repo\\backend\\app\\api\\reschedule.py.r74mj"],"targetCount":1}
```

宿主有个 safe-delete 闸门：**同一轮里第 50 次删除直接被拦下，进程随即结束**。
而 `mutation_check.py` 每跑完一条就 `os.remove(path + ".mutbak")` ——
第 50 条之后，子进程在打印汇总行之前被带走，框架只能判"无效·退出码 1: ?"。

**这同时推翻了 R73 的结论**。R73 第 9 次教训写的是"pytest 临时目录垃圾 >50 触发清理钩子"，
并给出"每批独立 TEMP"的解法 —— 那个解法当时确实让 8/8 恢复（因为每批只有 8 次删除，
远低于 50），但**归因是错的**：真正被计数的不是临时目录，是**删除动作本身**。
R74 里我按那条经验给了每批独立 TEMP，结果 49 条仍然无效 —— 因为变异体数量摆在那儿。

本轮的做法（`R74-new/run_mut_junit.py`）：

1. **零删除**：备份改成"每个被变异文件一份、原地覆写"（放在 `R74-new/mjbak/`），
   复原用 `shutil.copy2` 覆盖回去，不再 `os.remove`；
2. **判定不读 stdout**：`--junitxml` 由 pytest 在 sessionfinish 阶段**先于**终端汇总写盘，
   进程被带走也不影响报告（R73 定向变异也是这么绕开的）；
3. 仍有一条（M39）第一次没留下 junit 报告 —— 单独重跑得 `1 failed / 9 passed`，
   56 条最终 **56 命中 / 0 存活 / 0 无效**。

**可复用判据**：仪器报"无效"，先问"它是在**哪个动作**之后死的"。
"退出码 1 + 没有统计行"这一个症状，背后可以是临时目录、可以是删除闸门，
也可以是 `-k` 写错（那会返回 5）。症状一样，原因完全不同 ——
**只有当你能把原因写成一句可复现的话，才算归因完成**。
