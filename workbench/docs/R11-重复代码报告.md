## 一、结论先行

**生产代码的重复程度很低，不需要动。**

| 维度 | 结果 |
|---|---|
| 完全相同的 `.py` 文件 | 1 组（4 个空 `__init__.py`，正常） |
| 完全相同的函数（生产代码） | **1 组**，且是 2 行的 `__init__` |
| 跨文件重复代码块（≥6 行，生产） | **1 处**（Excel 表头样式，6 行） |
| 完全相同的函数（测试代码） | **10 组**，涉及 15 个文件 |

**与 `MARS-408` 的对比**：那边是 283 组重复、817 个文件（占 87%），因为同一份代码存了三份副本。这个项目**没有那种结构性问题**。

## 二、唯一的实质重复：Excel 表头样式

### 位置

- `backend/app/master_workbook.py:213`（`_sheet` 内部函数）
- `backend/app/api/reschedule.py:1416`（`_write_sheet` 模块函数）

### 代码

```python
ws.append(headers)
for c in ws[1]:
    c.font = Font(bold=True)
    c.alignment = Alignment(horizontal="center")
for col, w in zip("ABCDEFGH", widths):
    ws.column_dimensions[col].width = w
```

两边一字不差。

### 但差异不在代码，在语义

| | `master_workbook._sheet` | `reschedule._write_sheet` |
|---|---|---|
| 是否保存 | 否（只建 sheet 返回） | 否（同上） |
| 调用方 | 五表台账导出 | 教务标准课表导出 |
| 列宽来源 | 硬编码列表 | 硬编码列表 |
| `Font`/`Alignment` 导入位置 | 函数内 | 函数内 |

**它们确实是同一个东西。**

### 为什么我建议提取，但不建议现在做

**理由（支持提取）**：
- 如果哪天产品要求"导出的表头加背景色"，要改两个地方
- `"ABCDEFGH"` 这个硬编码意味着**最多 8 列**，两处都有这个隐含上限

**理由（支持暂缓）**：
- 6 行代码，改动收益低于回归风险
- 两处都已被导出测试覆盖，合并后需要重跑两套测试
- 当前没有第三方导出模块要用它

**建议**：如果 R14 之后还有维护窗口，提取到 `app/utils/excel_style.py`；否则留在原地，在两处加注释互相指向（成本 2 行，收益是避免"只改了一处"）。

## 三、生产代码唯一的"重复函数"

```python
# auto_scheduler.py:100
def __init__(self, db: ScheduleDatabase, extra_tasks: Optional[List] = None):
    self.db = db
    self.extra_tasks = list(extra_tasks or [])

# parallel_scheduler.py:46
def __init__(self, db: ScheduleDatabase, extra_tasks: Optional[List] = None):
    self.db = db
    self.extra_tasks = list(extra_tasks or [])
```

**这是合理重复，不该合并。** 两个调度器是两个独立类，共享两个字段不代表要共享基类。

引入 `BaseScheduler` 只会增加一层间接，对 2 行代码是不划算的抽象。

### 两个调度器是否有职责重叠

| | `auto_scheduler.py`（523 行） | `parallel_scheduler.py`（521 行） |
|---|---|---|
| 主要方法 | `solve` / `solve_all` / `_get_course_sections` / `_occupancy` | `solve` / `solve_school` / `_tasks_of` / `_unit_day_map` |
| 场景 | 单教师/单课程求解 | 按班级批量、全校一键 |
| 共享 | `cp_model`（OR-Tools） | 同上 |

**方法名有重名（都是 `solve`），但语义不同**：前者按 section 求解，后者按 class 求解。这是**同名不同义**，不是重复。

规模相当（523 vs 521 行）容易让人误以为是复制出来的，实际是从不同需求独立长出来的。

## 八、本轮的方法说明

### 三层检测

1. **文件级**：SHA-256 全文件哈希 → 找完全相同的文件
2. **函数级**：AST 转 dump 后哈希 → 找完全相同的函数
3. **代码块级**：连续 6 行归一化（去注释空行）→ 找跨文件复制粘贴

三层都用了，才能区分"函数相同"和"片段相同"。

### 一个容易误判的点

`auto_scheduler.solve` 和 `parallel_scheduler.solve` **方法名相同、规模相近**，很容易被判定为"复制出来的两个模块"。

实际要看**内部实现**：一个是按 section 求解，一个是按 class 求解，共享的只有 OR-Tools 的 `CpModel` 用法。这种"看起来像、实际不同"的情况，只能靠读代码判断，不能靠工具。
