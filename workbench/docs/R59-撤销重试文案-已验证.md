# R59 · 撤销重试链：两次失败都要报，别让 noqa 挡住那半个原因

**状态：已落地并推送（commit `16e1a47de7`，父 `1bd1ea30eb`）。**

## 1. 一句话

`undo()` 在撤销标记连续写失败两次时，**只报第二次的原因**，第一次被
`# noqa: F841` 挡在那里无人使用 —— "磁盘满 + database is locked" 同时发生时，
调用方会去查锁，而真正的原因在磁盘。

## 2. 缺陷在哪，怎么发现的

`app/plan_landing.py:540`（改前）：

```python
    except Exception as first:  # noqa: F841
        try:
            mark = store.revoke(rec["id"], actor=actor)      # 重试一次
        except Exception as again:
            return {..., "error": ("…撤销记录写入失败（%s）。…" % again)}
```

`first` 绑定了、从来没用过，靠 `# noqa: F841` 让 ruff 闭嘴。
这不是"无害的抑制"：那个变量本来就该出现在错误文案里，抑制顺手把这个缺口也盖住了。

实测（改前，新用例直接红）：

```
assert '磁盘满' in "课表已回滚到落地前，但撤销记录写入失败（模拟重试失败：database is locked）。…"
E       AssertionError
```

第一次的 `模拟首次失败：磁盘满` 完全没有出现在返回给前端/教秘的文案里。

## 6. 仪器：同一个坑第三次踩到，这次记清触发条件

第一遍我按"每 8 条一批"跑，但七批写在**同一个 shell** 里：

```
for b in 0 8 … 48; do for i in $(seq $b $e); do …_mut_one.py $i; done; done > log
```

结果 **56 行里 52 条 `???? 无效 pytest 退出码 1: ?`**，只有前 4 条正常。

改成**每批一次独立 shell 调用**（7 次工具调用，各自一个进程）后，同一份代码
**56/56 全检出**。所以跑法不是"分批就行"，而是：

> 一条变异体一个 python 进程 **且** 一批（≤8 条）一个独立 shell 进程。

另外这次还复现了日志重复：沙箱拦截后自动升级重跑，`>>` 让同一条变异体出现两次记录
（96 行 / 56 条 = 40 行重复）。**统计必须按 M 编号取最后一次判定**，不能 `grep -c '^PASS'`。
这一遍的原始日志：`_mut_R59.log`（坏的，52 无效）与 `_mut_R59b.log`（好的，96 行 56 条）。
