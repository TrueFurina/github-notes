# 口径分歧：同一个 flag，两套正则，两种结论

- 日期：2026-11-01（R107）
- 起因：R106 修好「无真值算通过」后，想看看还有没有同类"判定口径"问题
- 结果：找到一处**方向相反**的缺陷——不是高估，是**低估**

---

## 一、R106 和 R107 是同一枚硬币的两面

| | R106 的缺陷 | R107 的缺陷 |
|---|---|---|
| 位置 | `_verify_numeric_dispatch` | 4 处 flag 内文提取 |
| 形态 | 无真值时 `return True` | `\{(.+)\}` 贪婪匹配 |
| 后果 | **高估**解题率 | **低估**解题率 |
| 机理 | "没法反驳"被算成"答对了" | "答对了"被判成"答错了" |

两者都属于同一类：**判定口径错了，数字失真**。区别只是一个让分数虚高，一个让分数虚低。

---

## 二、发现方式：一次定向扫描

用 `ast` 剥掉注释后，扫全部 175 个脚本，找 `no_truth / 无真值 / truth is None` 附近是否 `return True`：

```
命中 5 处：
  _audit_corpus_integrity.py:52          [not truth]     ← 误报（是 return False）
  _audit_truth_consistency.py:57         [not truth]     ← 误报
  _stratify_external_benchmark.py:62     [not truth]     ← 误报
  _verify_presolve_truth.py:76           [NO_GROUND]     ← R105 已修，正常
  _verify_presolve_truth.py:87           [无真值]         ← 同上
```

**5 处全是误报。** 那三处的形状是 `if not truth: return False`——正确的 fail-closed。

但扫的过程中我注意到一个细节：这三个正确处理空白真值的函数，**内文正则不一样**。

---

## 三、真正的缺陷：`(.+)` vs `(.+?)`

| 文件 | 写法 |
|---|---|
| `_audit_corpus_integrity.py` | `rb"\{(.+)\}"` ← **贪婪** |
| `_stratify_external_benchmark.py` | `rb"\{(.+)\}"` ← **贪婪** |
| `_export_external_benchmark.py` | `r"\{(.+)\}"` ← **贪婪** |
| `_audit_truth_consistency.py` | `rb"\{(.+?)\}"` ← 非贪婪 |
| `verify/flag_checker.py` | `r"flag\{(.+)\}"` ← **贪婪** |

全仓共 **9 处**同样的提取逻辑：**5 处贪婪、4 处非贪婪**。

### 后果

候选串带上下文时（LLM/工具输出里很常见）：

```
the answer is flag{correct_one} (hint: {not_this})
```

| 实现 | 提取的内文 | 判定 |
|---|---|---|
| 贪婪 | `correct_one} (hint: {not_this` | sha256 与真值不符 → **判错** |
| 非贪婪 | `correct_one` | sha256 相符 → 判对 |

**答对的题被判成答错。**

### 最尴尬的一条证据

`_audit_truth_consistency.matches_truth` 的 docstring：

> 与 `_stratify_external_benchmark.matches_truth` **完全同口径**（直接复用）。
> 复用实现而非重写，避免两工具判定漂移。

而它自己用非贪婪、"被复用的那个"用贪婪——**它自己就是那个漂移源。**

它写这句话的意图完全正确（复用避免漂移），但实际做的是复制粘贴了一份实现，然后修改了其中一个字符。

---

## 四、为什么贪婪在这里一定是错的

flag 的语义决定内文不含花括号。这一点在 `verify/flag_checker.py` 里有明文：

```python
# 花括号配对检查（未闭合括号直接拒绝）
if f.count("{") != 1 or f.count("}") != 1:
    return V_REJECT
```

既然内文不可能含 `}`，非贪婪就是唯一正确解。

### 一个例外

`ctfplatform/dasctf.py:714`：

```python
_FLAG_WRAPPER_RE = re.compile(r"^(?:flag|FLAG|ctf|CTF|DASCTF)\{(.+)\}$", re.DOTALL)
```

它是**全串锚定**（`^...$`），贪婪不会跨出结尾那个 `}`。行为正确，**不改**。

测试里专门为这个例外写了一条反向断言：如果哪天有人把 `^...$` 去掉，那条测试会红。

## 五、修复与验证

### 改动（4 处）

```
scripts/_audit_corpus_integrity.py        rb"\{(.+)\}"  → rb"\{(.+?)\}"
scripts/_stratify_external_benchmark.py   rb"\{(.+)\}"  → rb"\{(.+?)\}"
scripts/_export_external_benchmark.py     r"\{(.+)\}"   → r"\{(.+?)\}"
verify/flag_checker.py                    flag\{(.+)\}  → flag\{(.+?)\}
```

### 守卫（`tests/test_flag_inner_parity.py`，9 条）

- **5 条参数化**：判定路径上不得出现贪婪写法
- **1 条反向自检**：全串锚定的实现允许贪婪，但必须真的带 `^`
- **3 条行为级**：非贪婪只取 flag；贪婪会吞掉 decoy（作为回归证据）；`sha256_matches` 端到端接受带上下文的候选

### 变异验证

| 变异体 | 结果 |
|---|---|
| `_audit_corpus_integrity` 改回贪婪 | 1 failed ✅ |
| `_stratify_external_benchmark` 改回贪婪 | 1 failed ✅ |
| `flag_checker` 改回贪婪 | **2 failed**（静态 + 行为级）✅ |

## 六、过程中排除的两个假象

### 假象一：定向扫描 5 处全误报

扫描模式 `(no_truth|无真值) ... return True` 命中了 5 处，但逐条读代码后全部是 `return False`。
**静态扫描给出的从来不是结论，只是候选。**

### 假象二：全量回归里的 1 个失败

```
FAILED tests/test_xor_bruteforce_fallback.py::test_negative_embedded_key_md5_mismatch_rejected
```

单独跑 5 次全绿；与该测试引用的文件与我改动**零交集**（grep 确认它不 import `flag_checker` 也不碰 `verify`）。
判为**既有的资源竞争波动**（它通过 `SubprocessExecutor` 起子进程，全量 2100+ 测试并行时抢 CPU）。

**记录在案，但不算我的回归**——这种判断必须靠证据，不能靠"应该是吧"。

## 八、这一轮真正想说的

R106 和 R107 加起来说明一件事：

> **一个仓库里"同一个数字有几处实现"，就有几处可能给出不同答案。**

我审过的仓库里，`解出数` 这个概念至少有 5 处实现：`_verify_presolve_truth`、
`_verify_numeric_dispatch`、`_audit_corpus_integrity`、`_stratify_external_benchmark`、
`verify/flag_checker`。R106 修好了其中一处的口径，R107 修好了另外四处的正则。

**这类问题的可发现性极低**：每处实现单独看都是"合理的"，都能跑，都有测试。
只有在**横向比对**时才会暴露——而横向比对不是任何人的日常工作。

所以最该留下的不是这 4 个字符的改动，而是这条检查：

```python
def test_both_scripts_agree_on_no_truth_semantics()
def test_no_greedy_inner_brace_in_verdict_paths(rel)
```

**它们不验证"某个实现对不对"，而是验证"多个实现彼此一致"。**
后者是单点测试永远覆盖不到的一层。
