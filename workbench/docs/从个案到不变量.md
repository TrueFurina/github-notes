# 从个案到不变量：把"合计对不上"变成一条可复用的断言

- 日期：2026-11-01（R115）
- 起点：R113 / R114 连续两轮都落在同一个脚本 `_scene8_build.py`
- 这轮换做法：**不再追个案，把判据本身做成可复用的**

---

## 一、为什么停止追个案

R113 修"遍历范围漏分类"，R114 修"行列合计两套口径"。两轮之后我意识到：

**这不是那个脚本特有的问题。任何"二维表 + 合计"的结构都有三套必经口径：**

```
Σ(行合计)  ==  Σ(列合计)  ==  格点总计  ==  单元格总和  ==  外部声称的总数
```

只要其中任一处的遍历范围与他人不同，就会分叉。

而分叉的症状永远是同一句：**"合计看起来像算错了"**——人就会去查算法，
而问题在遍历范围。这个误导每次都会发生。

**再修第五个、第六个同类脚本没有意义。该做的是一条通用断言。**

## 二、交付 1：`tools/check_table_invariants.py`

```python
from check_table_invariants import assert_table_consistent

s = assert_table_consistent(
    mat,                           # {行: {列: 数}}
    row_keys=..., col_keys=...,    # 若给出，只在这些格点上统计
    expected_total=reg["total"],   # 外部声称的总数
    allow_outside=False,           # 是否容忍格点外的题
)
# 不一致时抛 InconsistentTable，并说明差在哪
```

### 它报错时报什么

R114 的缺陷数据（新增 `forensics` 10 题 + `pwn/EXPERT` 3 题，但列表未更新）：

```
❌ 矩阵全量 60 != 格点总计 47
   （有 13 题在格点外：['pwn × EXPERT', 'forensics × MEDIUM']）；
   外部声称总数 60 != 格点总计 47
```

**它不只说"对不上"，还指出是哪两个格点**——`pwn × EXPERT`、`forensics × MEDIUM`。
这是"有 13 题在格点外"和"有 13 题在格点外，具体是这两类"的区别。

### 5 项自检

```
[PASS] T1 一致矩阵 → 通过
[PASS] T2 总数不符 → 检出
[PASS] T3 格点外有题 → 检出
[PASS] T4 允许格点外 → 通过        ← 豁免路径也要验
[PASS] T5 空表 → 通过
```

T4 特别重要：检查器有两个方向（该报的要报、该放的要放）。
只测前一个，把判据写成"一律报错"也能全过。

## 三、交付 2：让热力图脚本自己 fail-closed

R114 加的是 `print` 提示。这轮升级为**直接失败**：

```python
_invariant = {
    "Σ行合计": _row_sum,
    "Σ列合计": _col_sum,
    "格点总计": _grid_total,
    "矩阵全量": _all_cells,
    "reg.total": reg["total"],
}
if len(set(_invariant.values())) != 1:
    raise SystemExit(f"[FAIL] 热力矩阵统计不自洽：{detail} ...")
```

**为什么用 raise 而不是 print：**
一张自己跟自己对不上的表，不该被发出去。警告会被忽略，失败不会。

行为验证：

| 数据 | 五个量 | 结果 |
|---|---|---|
| 真实（47 题） | 47 / 47 / 47 / 47 / 47 | ✅ 通过 |
| 缺陷（新增 13 题未入表） | 47 / 47 / 47 / **60** / **60** | ❌ 正确拦下 |

## 四、这轮我自己又空转了两次

### 第一次：断言只看字符串存在

加了 3 条"不变量必须存在"的测试，全过。变异验证：`if len(set(...)) != 1:` → `if False:` →

```
12 passed    ← 没抓到
```

原因：我的断言是 `assert "_invariant" in code`——`if False:` 之后字样还在。

**断言太粗。** 改成必须匹配**真实的比较语句**：

```python
assert re.search(r"if\s+len\(\s*set\(\s*_invariant\.values\(\s*\)\s*\)\s*\)\s*!=\s*1\s*:", code)
assert re.search(r"raise\s+SystemExit", code)
```

重新变异：`1 failed, 11 passed` ✅

### 第二次：verify 命令漏了参数

台账里 `check_table_invariants.py` 的验证命令写的是 `["python", "tools/check_table_invariants.py"]`，
没有 `--self-test`——它跑到 `print_help(); return 2`，被判定为失败。

如果我没去查那一行，会得出"修复代码在但行为已回归"的错误结论。

## 五、这轮的元判断

回头看 R112–R115 四轮：

| 轮次 | 做了什么 | 性质 |
|---|---|---|
| R112 | 发现"固定列表静默丢弃"，工具化 | 个案 → 工具 |
| R113 | 做检测器扫全仓（278→12），找到热力图 | 工具 → 个案 |
| R114 | 发现行列合计两套口径 | 个案 |
| **R115** | **把"合计必须相等"做成通用断言** | **个案 → 不变量** |

**R113 的检测器找的是"代码形态"，R115 的不变量验的是"数据关系"。**

前者靠模式匹配，会有误报；后者只对具体数据表判断，**非黑即白**。

对于"合计"这一类问题，不变量比模式匹配可靠得多——
因为"四个数必须相等"是可判定的数学事实，不需要猜代码意图。

## 七、三条可复用的

1. **同类问题修到第二次，就该写不变量而不是修第三处。**
   R113、R114 都在同一个文件上打补丁。第三轮才意识到：该写的是判据。

2. **不变量比模式匹配可靠。**
   "行合计必须等于列合计"是可判定的数学事实；
   "这段代码是不是在漏数据"要靠猜。前者非黑即白，后者需要人工复核。

3. **断言"字符串存在"是最弱的守卫。**
   `if False:` 之后字样还在。要断言**结构**（正则匹配真实的比较语句），
   不是断言**痕迹**。
