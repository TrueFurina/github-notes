# 前端错误文案：让 413 说人话

> 前几轮一直在补后端防护。这一轮换到用户视角：
> **用户真正看到的是什么？** 结果发现一个"三重错误"的提示。

---

## 一、问题

后端加了 32MB 上传上限后，用户上传超大文件会收到：

```
HTTP 413
detail: 文件超过上限（32 MB）。如确需上传更大的表格，请设置环境变量 MAX_UPLOAD_MB 后重启服务。
```

前端 `describeApiError` 的逻辑是：有 `detail` 就原样用，不带"下一步"指引时自动补一句。

于是教秘看到的是：

> 文件超过上限（32 MB）。如确需上传更大的表格，**请设置环境变量 MAX_UPLOAD_MB 后重启服务**。（请稍后重试或刷新页面）

### 三重错误

| # | 问题 | 为什么错 |
|---|---|---|
| 1 | 让用户去设环境变量 | 那是运维的事，教秘不会也不该做 |
| 2 | 让用户"重试" | 同一个超限文件，重试一万次也是 413 |
| 3 | 让用户"刷新页面" | 刷新不会让文件变小 |

**三条建议全都没用。** 真正该说的是：换个更小的文件，或者拆分成多个。

---

## 二、根因

`src/utils/apiError.ts` 里：

```ts
// 429 有专门分支（读 Retry-After）
if (status === 429) { ... }

// 413 没有分支 → 落到这里
if (detail) return ensureHint(detail);
```

`ensureHint` 的逻辑是：

```ts
const HAS_HINT = /重试|再试|刷新|稍后|稍候|检查|联系/;
function ensureHint(text: string): string {
  return HAS_HINT.test(text) ? text : `${text}（请稍后重试或刷新页面）`;
}
```

后端文案里没有这些词，所以被追加了一句"请稍后重试或刷新页面"。

**这个模块本身质量很高**——文件头注释明确写了它存在的理由（避免 axios 英文原文漏到界面），429 甚至读了 `Retry-After` 头。问题只在于：新增了 413 这个状态，前端没跟上。

---

## 三、修复

### 加了 413 分支

```ts
// 413 单独处理：后端 `detail` 会写"设置环境变量 MAX_UPLOAD_MB"，
// 那是**运维**要做的事，教秘看到只会更困惑。而且 ensureHint 会追加
// "请稍后重试或刷新页面"——重试同一个超限文件永远不会成功。
//
// 正确的指引是：换个更小的文件（或拆分表格）。
// 上限值从 `X-Max-Upload-Bytes` 头读，前端不必硬编码 32MB。
if (status === 413) {
  const cap = maxUploadBytes(res.headers);
  const capText = cap ? `（上限 ${Math.round(cap / (1024 * 1024))} MB）` : '';
  return `文件太大${capText}，请压缩表格或拆分成多个文件后重试。`;
}
```

### 用上了后端早就返回的头

```ts
function maxUploadBytes(headers: Record<string, unknown> | undefined): number {
  if (!headers) return 0;
  const raw = headers['x-max-upload-bytes'] ?? headers['X-Max-Upload-Bytes'];
  const n = Number(raw);
  return Number.isFinite(n) && n > 0 ? n : 0;
}
```

后端在 413 响应里带了 `X-Max-Upload-Bytes: 33554432`，但**前端从没读过**。现在读上了：调整上限时前端文案会自动跟着变，不用改代码。

## 四、改前改后对比

| | 文案 |
|---|---|
| **改前** | 文件超过上限（32 MB）。如确需上传更大的表格，请设置环境变量 MAX_UPLOAD_MB 后重启服务。（请稍后重试或刷新页面） |
| **改后** | 文件太大（上限 32 MB），请压缩表格或拆分成多个文件后重试。 |

有头时显示具体上限，无头时退化为：

> 文件太大，请压缩表格或拆分成多个文件后重试。

（第一版的兜底写成了"文件太大（上限 服务端上限）"，读起来别扭，已修正。）

## 七、这轮为什么值得做

前面几轮的视角都是"防护对不对"，这轮是"用户看到什么"。

两件事都重要，但**只有后者决定用户会不会被困住**。

后端 413 返回得很正确——状态码对、头对、detail 信息量足。但前端把运维话术原样转给了教秘，还补了句错误的建议。

**这种问题不会在任何测试里暴露**：后端测试断言 `status == 413`，前端测试（改动前）根本不测 413。两边都绿，用户还是看不懂。

---

## 八、一个方法论观察

前几轮的检查清单是"该有的防护有没有"、"防护有没有被测住"。

这轮加一条：**"防护生效时，用户看到什么"**。

三层检查：

| 层 | 问题 | 手段 |
|---|---|---|
| 1 | 有防护吗 | 读代码 / 构造攻击 |
| 2 | 防护被测住吗 | 变异测试 |
| 3 | **防护触发时用户体验如何** | **读前端错误处理** |

第 3 层最容易被跳过，因为它不在测试范围内——测试验证的是"系统行为正确"，不是"用户能理解"。
