> 对应遗留项：`Solve` 无 `random_seed`（D2 §6 第 7 条，第二期报告里写着"**生产侧未修**"）
> 落点：`app/engine/solver_factory.py`（53 → 91 行）、

## 一、这条以前只被写成"可能"

第二期三天总报告的 §6.2 第 7 条原文：

> `Solve` 无 `random_seed` / `num_search_workers` / `max_time_in_seconds`；
> R58 只在测试侧绕开，**生产侧未修**，同数据两次排课可能不同

"可能不同"这四个字挂了整整一期，没人实测过。R58 把 M42 那条概率性变异从**测试侧**
绕开了（把候选格压到只剩一格），但那是为了让测试不依赖求解器 —
**求解器本身照旧每次给不同的答案**。

这轮第一件事就是把它从"可能"变成"是"或"不是"。

## 二、取证：三组实验，结论是"是"

机器：20 逻辑核；`ortools 9.11.4210`；数据：`schedule.demo.xlsx`（84865 B，433 条记录）。

### 2.1 小模型上是**概率性**的（这本身就是非确定性的证据）

同一配置（worker=8、默认时限）跑 `solve(max_sections=30)`，各跑三次：

| 实验 | 3 次结果 | distinct |
|---|---|---|
| 第一次 | 三次全同 | 1 / 3 |
| 第二次（同配置，隔几分钟） | **run1 与 run2 差 56 行** | **2 / 3** |

⚠️ **同一份代码、同一份数据、同一个配置，两次实验给出不同结论** ——
这不是"实验误差"，这就是非确定性的定义。任何"我跑了一次是稳的"都不成立。

### 2.2 真实链路：两次就完全不同，而且两个都是最优解

`solve_all(chunk_size=60)`（3 片，410 行结果）：

| worker | 两次结果 | 逐条差异 | 耗时 |
|---|---|---|---|
| **8**（旧默认） | **完全不同** | **288 / 410 行换了位置** | 11.07s / 11.44s |
| **1**（新默认） | 完全一致 | 0 | 11.45s / 11.54s |

两片的状态全部是 `OPTIMAL`，`solved` 都是 171、行数都是 410 ——
**不是"没算完就返回"，是同一道题有大量等价最优解，每次挑到不同的那个。**

这就是产品问题的实质：同一份数据、同一个按钮，教秘 A 点出来第 1 周的课在周一、
教秘 B 点出来在周三，两个人的打印稿对不上；更麻烦的是"上次排的那份"再也拿不回来，
因为没有任何办法让它重新生成。

### 2.3 归因：不是时限，不是种子缺省值，是 worker 数

三个候选原因逐个排除：

| 候选 | 判定 |
|---|---|
| `max_time_in_seconds` 到点截断 | **不是**。两次 `status` 都是 `OPTIMAL`，耗时 11.07s / 11.44s，时限 7s/片且每片 4.2–4.4s |
| 没设 `random_seed` | **次要**。ortools 默认种子就是 1，缺省值恰好等于我们想设的值 ⇒ 单靠"补一行 seed"改不了任何东西 |
| `num_search_workers=8` | **主因**。并行搜索 + 工作窃取，谁先摸到哪个解取决于线程调度 |

所以修法不是"补一行 seed"，而是**把 worker 降到 1**；seed 只是把默认值显式写下来，
让以后想复现"某一个特定解"时有抓手。

## 三、改法

```python
DEFAULT_MAX_WORKERS = 1   # 原 8
DEFAULT_SEED = 1

def solver_workers() -> Optional[int]:
    raw = (os.getenv("SOLVER_WORKERS") or "").strip()
    if raw == "0":
        return None          # 交回 ortools（不可复现，仅供性能对照）
    if raw.isdigit():
        return max(1, int(raw))   # 压测时可放开并行
    return DEFAULT_MAX_WORKERS    # 写歪了也退回 1，不会变成"随便开满"

def solver_seed() -> int:
    raw = (os.getenv("SOLVER_SEED") or "").strip()
    return int(raw) if raw.isdigit() else DEFAULT_SEED
```

`new_solver()` 里新增一行 `s.parameters.random_seed = solver_seed()`。

**代价**：单次 `solve_all` 11.07s → 11.45s（**1.03x**）。60 个任务的片上，
8 worker 是 4.2s、1 worker 是 4.4s —— CP-SAT 在这个规模上并行收益本来就接近零，
而内存随 worker 线性增长（文件头 2026-10-29 那段实测：8 worker 峰值 +158MB）。
**定性和省内存是同一个方向，这不是权衡，是两边都赚。**

## 四、边界：到什么程度算"可复现"

只保证「**同数据 + 同配置 + 未触发时限**」时逐条一致。三条要说清：

1. **触发时限仍不确定**：`max_time_in_seconds` 到点被截断（`FEASIBLE`）时，
   结果取决于当时算到哪。真实 60 任务片 4.4s、时限 7s，余量够；机器极慢时会顶到。
   彻底确定得连时限一起去掉 —— 那会带来"卡住不返回"的风险，权衡后保留时限。
2. **`SOLVER_WORKERS=8` 时不可复现**，这是**预期行为**（压测要并行速度）。
3. **`num_search_workers` 不是唯一变量**：ORTools 升级、模型构造顺序变化都会改结果。
   能保证的是"同一版本、同一份代码"下可复现；跨版本对比要用 `SOLVER_SEED` 之外的基线。

## 五、测试：一组守配置，一组守行为

### 5.1 `test_solver_factory_contract.py`（9 条，毫秒级）

只碰参数、不跑求解，所以参数配错时**立刻**能定位，不必等二十秒才知道红了。

| 用例 | 守什么 |
|---|---|
| `test_default_workers_is_one` | 默认必须是 1 —— 改回 8 这条直接红 |
| `test_new_solver_applies_single_worker` | 契约在函数上成立、在对象上也得成立（读 `parameters`） |
| `test_worker_override_by_env` | `SOLVER_WORKERS=4` 生效（压测留的口子） |
| `test_worker_zero_means_let_ortools_decide` | `0` → `None`，且对象上不写该字段 |
| `test_worker_env_garbage_falls_back_to_default` | 环境变量写歪**不能**变成"随便开满" |
| `test_seed_default_and_override` | `SOLVER_SEED=7` 必须出现在 `parameters.random_seed` 上 |
| `test_seed_env_garbage_falls_back_to_default` | 同上，垃圾值退回 1 |
| `test_time_limit_passthrough` | 传入值原样设进去 |

⚠️ 为什么"种子"这条不能用"读出来是不是 1"来断言：**ortools 的默认种子本来就是 1**。
断言"等于默认值"的话，把 `random_seed = solver_seed()` 整行删掉也照样绿（V2 变异实测。
所以这条用例改用 `SOLVER_SEED=7` 覆盖来证伪 —— 删了那行，读到 1≠7，必红。

### 5.2 `test_solver_determinism.py`（1 条，约 23 秒）

真实表 `solve_all(chunk_size=60)` **连排两次**，归一化（week/weekday/time_slot/room/
teacher/class_name/experiment 排序）后逐条比对，要求完全一致。

- 连跑两次而不是三次：两次已能暴露（实测两次就不同），三次会把用例推到 35 秒，收益不抵成本。
- 加了一条防构造失效：`assert len(a) > 100` —— 演示表没加载成功时不能"空过"（R58 的教训）。
- 同时断言两次的 `solved` 相同，否则说明连排入数量都变了。

## 六、定向变异：新用例真的会红（不是跑了绿就算过）

| 变异 | 改动 | 结果 |
|---|---|---|
| **V1** | `DEFAULT_MAX_WORKERS = 1` → `8` | **3 failed / 7 passed**：契约 2 条红 + **行为用例红**（真实差异） |
| **V2** | 删掉 `s.parameters.random_seed = solver_seed()` | 1 failed / 8 passed：`test_seed_default_and_override` 红（`assert 1 == 7`） |
| **V3** | `solver_workers()` 去掉 `isdigit()` 覆盖分支 | 1 failed / 8 passed：`test_worker_override_by_env` 红（`assert 1 == 4`） |

V1 是这轮最要紧的一条：它同时证明**契约守得住**和**行为用例抓得到真缺陷**。

### 6.1 一个自己踩的坑：用例把守门人劝退了

第一版行为用例的跳过条件写的是：

```python
if solver_factory.solver_workers() != 1:
    pytest.skip("当前是并行配置，结果本就不可复现（压测场景）")
```

看着合理，实际是**自杀式设计**：把默认值改回 8 时，这条用例会安静地 `skip` —
它本该报"现在不可复现了"，却因为"现在不可复现"而拒绝发言。
V1 变异跑出 `3 failed, 6 passed, **1 skipped**` 才暴露：**跳过的是那条唯一能证明问题的用例**。

改成只认**显式设了环境变量**这一个条件：

```python
if os.getenv("SOLVER_WORKERS"):
    pytest.skip("显式指定了 worker 数（压测场景），结果不可复现是预期行为")
```

改完 V1 重跑：**3 failed / 7 passed，0 skipped**。
分工这才立住：契约用例守"默认值必须是 1"，行为用例守"默认值下必须可复现"，
两条各说各的话，谁都不许替对方闭嘴。

（顺带：第一次改的时候把 `delenv` 写在了 `getenv` 前面，导致 `getenv` 永远拿到 `None`、
skip 永不触发 —— 同一处改错两次，两次都是靠"跑一遍看数字"发现的，不是靠读代码。）

## 八、没做的事

- **没动 `max_time_in_seconds`**：它是"卡住不返回"的兜底，去掉风险更大。见第四节边界。
- **没给 `solve()` / `solve_all()` 加显式的 `seed` 参数**：环境变量已经够，
  加参数会改动两处函数签名和所有调用点，属于"顺手扩大改动面"，这轮不做。
- **没测跨机器可复现**：只在本机（20 核）验证。换 CPU 架构或核数后 `num_search_workers=1`
  仍是单线程，理论上可复现，但**没测过就不写"已验证"**。
- **没测 ORTools 版本升级的影响**：9.11.4210 锁定，升级属另一轮。
