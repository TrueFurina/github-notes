# 启动日志补完：让运维看得见口令状态

> 前几轮把口令策略改成了"分环境处理"，但有一个盲点：
> `ADMIN_PASS_IS_EPHEMERAL` 算出来了，**却从未被任何代码使用**。
> 运维启动服务时，看不到自己用的是固定口令还是随机口令。

---

## 一、发现的问题

`security.py` 里这个变量：

```python
ADMIN_PASS_IS_EPHEMERAL = True   # 开发环境随机生成时
```

全局搜索确认：**它只在赋值处出现，没有任何读取方**。

`main.py` 的 `lifespan` 启动钩子也没有引用它。

### 为什么这是个真问题

| 场景 | 运维看到 | 实际情况 |
|---|---|---|
| 生产：配了强口令 | 无输出 | 固定口令，重启后会话保持 |
| 生产：忘了配 | **服务正常启动**（走开发分支） | 每次重启换随机口令，所有人被登出 |
| 开发：没配 | 只有一条 Python warning | 随机口令 |

第二行最危险：**生产环境忘记设 `APP_ENV=production`，服务不会报错**，但每次重启都会换口令。管理员会发现"昨天还能登录，今天不行了"，却找不到原因——因为日志里什么都没写。

### 另一个细节

排查时发现 `main.py` 里根本没有 `logger` 这个变量，只有 `_http_log`。

我第一版补丁写的是 `log_admin_password_state(logger)`，**语法检查通过了**，但运行时会 `NameError`。

这类错误 `ast.parse()` 抓不到，必须真跑一次才会暴露。

## 二、补了什么

### 1. `security.py` 新增两个函数

```python
def describe_admin_password_state() -> str:
    """返回口令状态的一行摘要，供启动日志使用（绝不包含口令本身）。"""
    if ADMIN_PASS_IS_EPHEMERAL:
        return (f"ADMIN_PASS=ephemeral(随机生成, {len(ADMIN_PASS)} 字符, 重启即失效) "
                f"| APP_ENV={APP_ENV}")
    weak = "weak-demo" if ADMIN_PASS in _DEMO_PASSWORDS else "fixed"
    return f"ADMIN_PASS={weak}({len(ADMIN_PASS)} 字符) | APP_ENV={APP_ENV}"


def log_admin_password_state(logger=None) -> str:
    summary = describe_admin_password_state()
    if logger is not None:
        if ADMIN_PASS_IS_EPHEMERAL:
            logger.warning("[security] %s", summary)
        elif ADMIN_PASS in _DEMO_PASSWORDS:
            logger.warning("[security] %s —— 演示口令，不可用于公网", summary)
        else:
            logger.info("[security] %s", summary)
    return summary
```

**关键约束**：只输出长度和状态，**绝不输出口令本身**。

### 2. `main.py` 的 lifespan 接入

```python
async def lifespan(_app: FastAPI):
    from app.security import log_admin_password_state

    log_admin_password_state(logging.getLogger("app.security"))
    warmup.start_background()
    yield
```

放在 `lifespan` 而不是模块导入期，与原有设计一致——避免"导入 main"时产生副作用。

## 三、实测三种场景

通过真实的 `lifespan` 启动流程触发：

| 环境 | 启动日志 | 级别 |
|---|---|---|
| 生产 + 强口令 | `ADMIN_PASS=fixed(16 字符) \| APP_ENV=production` | INFO |
| 开发 + 演示口令 | `ADMIN_PASS=weak-demo(8 字符) \| APP_ENV=development —— 演示口令，不可用于公网` | WARNING |
| 开发 + 未设置 | `ADMIN_PASS=ephemeral(随机生成, 22 字符, 重启即失效) \| APP_ENV=development` | WARNING |

分级逻辑：正常固定口令用 INFO（不打扰），随机口令和演示口令用 WARNING（需要运维注意）。

## 四、新增 3 个测试并做了反向验证

| 测试 | 断言 |
|---|---|
| `test_startup_logs_ephemeral_state_in_dev` | 未配口令时日志含 `ADMIN_PASS=ephemeral` |
| `test_startup_logs_fixed_state_in_production` | 生产固定口令时含 `ADMIN_PASS=fixed`，**且日志不含口令明文** |
| `test_startup_logs_weak_demo_password` | 演示口令时含 `weak-demo`，**且日志不含口令明文** |

这两个"不含明文"的断言是核心——日志文件经常被收集、上传、转发，一旦泄露口令就会扩散。

## 七、这轮暴露的方法问题

我写的第一版补丁用了 `logger`，而 `main.py` 里只有 `_http_log`。

**`ast.parse()` 通过了，测试也没跑就推送前检查了语法。** 如果我没做"实测 lifespan 启动"这一步，这个 `NameError` 会直接进仓库——而且只在真正启动服务时暴露，`pytest` 也可能因为不触发 lifespan 而漏掉。

这次能抓到，是因为我坚持做了一次真实的启动验证：

```python
async with lifespan(app):
    pass
```

而不是只检查"函数定义是否存在"。

**这是同一类问题的第 N 次变体**：验证动作做了，但验证的不是运行时行为。语法正确 ≠ 能跑，能 import ≠ 能执行。

## 八、一个附带发现

`main.py` 里 `_http_log` 这个命名说明：这个项目的日志是按模块分的（`app.http`）。我接入时用了 `logging.getLogger("app.security")`，与原有风格一致，没有引入新的大写全局 logger。

小细节，但保持了代码风格的一致性。
