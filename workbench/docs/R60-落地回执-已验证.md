# R60 · 落地回执：八步里唯一不回人话的一步，现在会说话了

**状态：已落地并推送（commit `20489de30b`，父 `16e1a47de7`；CI `41349109110` 三 job 全绿）**

## 1. 一句话

`POST /parallel/land` 是整条链路里**唯一一个只回 diff 结构、不回一句人话**的写端点
（R50 断点②）。教秘点完"确认采纳"只看到一串数字，而"落地成功"和"落地没生效"在界面上
长得一模一样。现在它回一句能把四个差异账、长实验截短、时间与操作人、能不能撤销
一次说完的话 —— 并且前端**不再自己拼**。

## 2. 缺陷不是"少个字段"，是三种"看着成功其实不是"

R50 的八步实跑里，`/upload`、`/load-default`、`/master/*` 都回 `message`，
只有 `/parallel/land` 不回。看起来只是风格不统一，实际遮住三件事：

| # | 情形 | 没有 message 时，教秘看到什么 |
|---|---|---|
| 1 | 方案与安排表**完全一致**（又点了一次落地） | 200 + 一串全 0 的 diff。他以为又改了一轮 |
| 2 | 只有 `after_entries`（"410 条"） | 这 410 条可能是新排的，也可能是原封不动又落了一遍 |
| 3 | 长实验被**静默截短**（原表 2 行 → 方案 1 行） | 只在 `warnings` 数组里，列表会被人一眼跳过 |

第三种最贵：真实表里有 6 个单元是"同一天占 567+678"的长实验（如 24海资_1 全部实验），
方案每单元只排一个时段，落地就把 13:30-18:00 截成 13:30-15:00。**数据真的变了，
而回执里一个字都没有。**

前端当时的做法是自己拼（`LandPlanPanel.tsx:143`）：

```tsx
onMsg(`✅ 已落地为正式安排表：${r.data.plan_rows} 行写入，安排表 ${before} → ${after} 条。…`)
```

`has_changes=false` 时它照样说"2 行写入"，而那 2 行一个字都没改 —— 前后端口径分裂的
标准形态：后端改了语义，前端还在用旧假设拼句子。

三处措辞是有意为之：

- 场景 2 说"**已记录**一次落地……**没有任何变化**"，不说"已落地 N 条"—— 那 N 条正是它没做的事；
- 场景 2 无变化分支也报"另有 2 个单元不在方案里"：否则"没有变化"会被读成"方案覆盖了全部"；
- 场景 3 `安排表仍 7 条` 而不是 `7 → 7`：没发生迁移就不要写成迁移。

## 6. 新代码的四个定向变异（旧 56 条覆盖不到它们）

一条变异体一个进程，一条一次 shell 调用（R58/R59 三次踩过的仪器纪律）。

| 变异 | 改法 | 结果 |
|---|---|---|
| V1 | `reschedule.py` 把 `diff["message"]` 改名成 `message_r60`（字段消失） | **2/2 检出**：两条接线用例同时红 |
| V2 | `plan_landing.py` 把 `if diff.get("has_changes"):` 改成 `if True:` | **3/3 检出**：无变化两条 + 空 diff 一条 |
| V3 | 回执里长实验那段 `if long_sessions:` 改成 `if False:` | **1/1 检出**：只有"长实验必须点名"那条红 |
| V4b | 前端 `onMsg(r.data.message` 改成 `onMsg(''`（退回自拼） | **1/1 检出**：只有新加的第 7 条不变量红，旧 9 条仍绿 |

V4b 先试过一版 `onMsg(undefined as any || …)`：那是**语法破坏**，vitest 报
`no tests`（一条都没收集到）—— 这种"红"不算检出，凡是"0 条用例"的失败都要当无效处理。
换成空字符串后才是一次真正的语义回退。

## 7. 仪器：第四次，这次是"命令被重跑"

跑 V3 时出现一个会直接骗到人的现象：

```
$ python -c "…assert b.count(old)==1; write(); print('V3 applied')"
AssertionError          ← 看起来"没改成"
```

但文件其实**已经改了**（大小从 32286 变成 32278，正好是 `if long_sessions:` 与
`if False:` 的长度差 8）。原因是沙箱升级把同一条命令重跑了一次：第一次写入成功，
第二次 assert 自然失败，日志只留下第二次的报错。

⇒ 规矩：**带 `assert` 保护的编辑脚本被重跑时，"报错"不等于"没生效"。**
判据不能看日志，要看文件本身（大小 / md5 / 目标字节串）。这次是靠 `len` 差 8 字节
认出来的；如果只看 stderr，就会得出"文件没变"的反向结论，然后拿未变异的代码去
"验证"测试，得出"没检出"的假结论 —— 与脏 pyc 那次同一个闭环。
