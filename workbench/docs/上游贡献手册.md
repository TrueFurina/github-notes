## 二、找缺陷：先想 oracle，再看代码

**不要**先读代码找「可疑之处」——那会产出大量主观判断。**先**确定一个客观 oracle，让它去指位置。

### 有效的 oracle（按命中率排序）

| oracle | 怎么用 | 本工作区战果 |
|---|---|---|
| **往返一致性** | `parse(render(x)) == x`，x 取刁钻值 | 找到 2 个真 bug（frontmatter 换行截断、`#` 围栏误判） |
| **独立实现差分** | 自己按规格写一份，逐组合比对 | 点数表 2112 组零差异（证明库是对的） |
| **与标准库对照** | `tomlkit.parse(s).unwrap()` vs `tomllib.loads(s)` | 3000 份文档零分歧 |
| **不变式** | 「加宝牌点数不降」「chunk 拼回不丢行」「agari ⇔ shanten=-1」 | 全绿，也是结论 |
| **端到端复现** | 用 CLI/真实入口跑，不绕过校验层 | 抓出 `--agent` 注入（单测构造对象时绕过了 CLI） |

### 假阳性陷阱（我踩过的，每次都以为找到了 bug）

1. **参数格式**：`win_tile` 要 136 牌 ID，我传了 0–33 索引 → 1425 条假阳性。
2. **语义混淆**：结构成和 ≠ 有役，`no_yaku` 是正确返回 → 754 条假阳性。
3. **选项未传**：双役满复算没传 `is_yakuman=True`，被 kazoe 压成 13 番 → 22 条假阳性。
4. **路径不可达**：以为 `provenance` 是注入面，实际 store 在渲染前把它重写成归档路径。

**共同规律**：报错前先问「这会不会是我的 oracle 写错了」。上面 4 次，库全是对的。

### croniter 专属预言机陷阱（独立匹配器比对 `get_next` 序列时踩的）

7. **秒数截断**：croniter 5 字段表达式返回 `second=0`，我的匹配器保留了输入的秒 → 1568 条「不一致」全是秒差。**比对要降到分钟级**（只比 y/m/d/H/M）。
8. **DOW `7=0`**：cron 里 `0` 和 `7` 都表示周日；我的 `(isoweekday()%7)` 周日得 `0`，但 `7#1` 解析出 `want=7` → 假阳性。解析后先 `want %= 7`。
9. **OR 规则反写**：dom 与 dow 都非 `*` 时是 **OR**，不是 AND。我把 `(dom_star or dom_match) and (dow_star or dow_match)` 写成 AND，导致 `'* 4 18 * 0,6'` 这种「既是 18 号又是周末」的错解。正确实现见 `probes/croniter_bruteforce.py` 的 `my_match`。
10. **`N-N` 故意展开成整周期**：`20-20` 在 croniter 里被**故意**扩成全部 20 号所在维度（不是 bug，源码注释明说）。差异预言机要把 equal-range 当成「整周期」来对齐，否则假阳性。
11. **`L`/`W`/`#` 别碰**：这些是 croniter 的招牌异类 token，解析规则 quirky，自己写的独立匹配器极易写错 → 假阳性重灾区。只在「单限制 + 崩溃」层面做满足性检查（`probes/croniter_complex.py`），不做逐位序列比对。

**cron 的 OR 规则口诀**：dom、dow 二者之一为 `*` → 退化为 AND；二者都非 `*` → OR。

## 四、提 PR 的规格（这是「0/69 被跳过」的真正原因）

`octop-harness` 外部合并 4/4 带测试，我那 69 条 **0 条带测试**。规格：

1. **先写会红的测试**，确认红的原因是预期的那个（不是 import 错）。
2. **改动有边界**：一次只碰一个模块，≤3 文件。
3. **PR 说明三段**：症状（可复制）→ 根因（指向行号）→ 验证（红/绿数字）。

## 七、本地验证第三方仓库的测试（无 git 二进制 / 零依赖）

有些仓库的 CI 是首次贡献者门，提交后根本不会跑；本机也没有 git 二进制、`github.com:443` 被重置。
这时要验证自己 PR 的测试，**别等 CI**，直接本地跑：

### 方法（已验证：agent-memory 三分支 14 / 8 / 5 passed）
1. **拉源码**：用 `codeload.github.com` 下分支 tarball（不是 git clone，后者握手会被重置）：
   `curl -sL -o b.tar.gz https://codeload.github.com/<owner>/<repo>/tar.gz/refs/heads/<branch>`
2. **解包**：`tar -xzf b.tar.gz -C <dir> --strip-components=1`
3. **处理命名空间包**：若仓库是 workspace（如 `agent-memory` 把 `core`/`adapters` 拆成多个
   `src/agent_memory/...`，且都没有 `__init__.py`，属 PEP 420），把需要的几个
   `packages/*/src/agent_memory/<sub>` 合并到一个目录再指到 PYTHONPATH——否则先被找到的
   那个 `agent_memory` 会遮蔽其它子包，报 `ModuleNotFoundError`。
   ```
   mkdir -p _combined/agent_memory
   cp -r packages/core/src/agent_memory/core     _combined/agent_memory/
   cp -r packages/adapters/src/agent_memory/adapters _combined/agent_memory/
   ```
4. **跑测试**：`PYTHONPATH=_combined <venv>/python -m pytest tests/unit/<file>.py -q`
   - 零依赖的 core 包可直接这样跑，免装包、免联网。
   - 用到的 `store` fixture 若依赖别的子包（如 `adapters.capture`），把那个子包也合并进来即可。

### 注意
- Windows 上 `Store.init()` 可能触发 symlink 权限（winerror 1314）；仓库若用 `pytest_runtest_call`
  钩子会把它 `pytest.skip`——这是环境跳过，不是失败。
- `.pytest_cache` 写权限警告（WinError 5）可忽略，不影响判定。
- 跑通后把「本地 N passed」写进 PR 说明和复盘文档，把「书面正确」升级成「绿跑证明」。
