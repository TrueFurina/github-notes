## 三、四个发现的具体内容

### R1 · 令牌去重无测试保护

`_extract_tokens` 有段去重逻辑。删掉后，3 个相关测试**仍然全绿**——它们只验证"重复头能被解析"，没验证"重复头被去重"。

风险：同一 token 被验签 N 次；攻击者塞上千重复头可放大 CPU，而**限流按请求计不按头数计**。

补了 2 个测试（含 500 个重复头压成 1 个），变异回灌确认会红。

### R2 · 合并单元格表头崩溃

教秘习惯合并表头单元格。解析循环硬解包 `row[0..7]`，合并后数据行只剩 4 列 →

```
400  文件解析失败：tuple index out of range
```

**把 Python 内部错误直接泄漏给了用户。**

改为短行补齐到 8 列，并新增 `load_report.short_rows` 让用户知道"文件结构不规整"。

### R3 · 413 文案只改了一半

R0 修 413 时只改了**前端** `apiError.ts`（读 413 后重写文案），**后端的 `detail` 从未清理**：

```
detail: 文件超过上限（32 MB）。如确需上传更大的表格，请设置环境变量 MAX_UPLOAD_MB 后重启服务。
```

前端兜底让用户看到正确文案，问题看起来"已修"，但直接调 API 的脚本仍会看到运维话术。

顺带修了 4 类文案：登录失败、课程/教师/场地/班级空名、落地/导出空方案。

### R4 · 上传重载竞态

`load_from_excel` 是原地改写（先 `loaded=False`、`entries=[]`，再填充）。

在清空后注入延迟，4 个读线程：

```
21,572,523 次采样 → 100% 读到 0 条
真实全量解析约 157ms（433 行表）
```

修复后同一探针：**异常 0 次**。

## 四、R4 的两次自我纠正（最值得记的部分）

### 纠正 1：并发测试连错三版

新测试前两版都**抓不到变异体**：

1. 判定写成 `cur.loaded and n != 10` → 变异状态下读到的是 `(0, False)`，被全漏
2. 修了判定但**没先建基线** → 采样在上传前读到 0，正常状态反而失败
3. 先建基线再采样 → **终于检出**

**并发测试的"通过"极可能是假绿。**

### 纠正 2：第一版修复过度

`025ab9ee1b` 把两条加载路径都改成实例替换，4 个测试失败：

```
test_ensure_loaded_is_idempotent
test_landed_plan_survives_simulated_restart
test_replay_order_newer_event_wins
test_replay_order_landing_after_move_wins
```

它们持有 `_db` 的**实例引用**，替换后停在旧对象上。

**不是测试写错了，是我的修复方式过度了。** 正确分工：

| 路径 | 有锁吗 | 处理 |
|---|---|---|
| `upload_schedule` | 否（真竞态源） | 原子替换 |
| `_load_default_schedule` | 是（`_ensure_loaded` 双检锁） | 保持原地，只给路由补锁 |

`65704c8cba` 修正后恢复 416 passed。

**如果只跑 `test_api_auth.py`，这 4 个失败一个都不会暴露。**

## 六、Day 1 的观察

### 有效的方法

| 方法 | 命中的问题 |
|---|---|
| **变异测试** | R1（去重无保护）、R4（问题测试假绿） |
| **畸形输入探针** | R2（合并单元格崩溃） |
| **静态+运行时双扫描** | R3（413 运维话术） |
| **并发压测** | R4（重载竞态） |

四种方法各命中一个，没有一种是"重复劳动"。

### 反复出现的模式

四个发现里有三个是**同类问题的不同表现**：

- R3：前端修了，后端没修 → **只修了呈现层**
- R4 纠正 2：改两处，其中一处不需要改 → **一刀切**
- R1：测试存在但没测到点 → **覆盖≠有效**

共同点：**修复/验证动作做了，但没对准真正的问题所在。**

### 硬约束起作用的两次

1. R4 第一版破坏 4 个测试 → **全量回归**拦住（不是"改了就跑"）
2. R4 新测试假绿 → **变异回灌**拦住（不是"测试通过就算数"）

两条都是方案里写死的规则，这次真的救了场。
