## 二、python-multipart 0.0.20：可实测的 DoS

### 2.1 实测对照（同一份代码，只换依赖版本）

启动真实 uvicorn，用裸 socket 构造请求：

| 攻击输入 | 0.0.20（项目锁定） | 0.0.32（已修复） | 倍数 |
|---|---:|---:|---:|
| 1,000 个 part 头 | 5 ms | — | — |
| 5,000 个 | 18 ms | — | — |
| 20,000 个 | 73 ms | — | — |
| **50,000 个** | **197 ms** | **17 ms** | **11.6×** |
| **单个 header 值 10 MB** | **1,532 ms** | **3 ms** | **511×** |

**增长是线性的**：1,000 → 50,000 头，耗时 5ms → 197ms，约 40 倍输入对应 39 倍耗时。

### 2.2 最关键的一点：计算发生在鉴权之前

```
匿名上传 1KB  →  401（但拿到 401 之前已花 5ms 解析）
```

FastAPI 的依赖（`require_admin`）在 **Form/File 解析之后**才执行。所以：

- 攻击者**不需要任何令牌**
- 每个请求都强制服务端解析整个 multipart
- 10MB header × 并发 = CPU 快速饱和

**R6 加的 32MB 上传上限挡不住它**——那个上限在 `content = await _read_upload_limited(file)` 里，发生在解析**之后**。

### 2.3 7 个 CVE 的可达性逐一判定

| CVE / GHSA | 类型 | 本项目可达？ | 理由 |
|---|---|---|---|
| `GHSA-pp6c-gr5w-3c5g` | 无界 part 头 DoS | **✅ 可复现** | 见上表 |
| `GHSA-mj87-hwqh-73pj` | 大 preamble DoS | ❌ | 实测被 boundary 校验快速拒绝（2-3ms） |
| `GHSA-5rvq-cxj2-64vf` | 分号分隔符二次时间 DoS | ⚠️ 部分 | 仅影响 `x-www-form-urlencoded`，本项目只用 multipart |
| `GHSA-v9pg-7xvm-68hf` | 负 Content-Length 全量缓冲 | ⚠️ 未验证 | 需真实 HTTP 层伪造非法头；`TestClient` 构造不出 |
| `GHSA-wp53-j4wj-2cfg` | **任意文件写入** | ❌ | **需非默认配置** `UPLOAD_DIR` + `UPLOAD_KEEP_FILENAME=True`，本项目用 FastAPI `UploadFile`，未启用 |
| `GHSA-6jv3-5f52-599m` | 分号参数走私 | ⚠️ 部分 | 同第一条，仅 urlencoded |
| `GHSA-vffw-93wf-4j4q` | RFC 2231 参数走私 | ⚠️ 部分 | 影响 Content-Disposition 解析；本项目文件名会被 `_safe_upload_name` 二次净化 |

**"任意文件写入"虽然 CVSS 最高（I:H），但明确不可达**——这是最需要说清楚的一点，否则会引发不必要的恐慌。

### 2.4 修复版本要求

| CVE | 修复于 |
|---|---|
| 大 preamble DoS | 0.0.26 |
| 无界 part 头 DoS | 0.0.27 |
| 分号 DoS + 参数走私 | 0.0.30 |
| 负 Content-Length | 0.0.31 |

**要全绿，需升级到 ≥ 0.0.32。**

## 三、python-dotenv 1.2.1：不可达

| CVE | 类型 | 可达性 |
|---|---|---|
| `GHSA-mf9w-mj56-hr94` | `set_key` 跟随符号链接导致任意文件覆盖 | **不可达** |

**理由**：漏洞在 `set_key()` / `unset_key()`（写 `.env` 的 API）。本项目只用 `load_dotenv()` 读配置，从不写。

CVSS 是 `AV:L`（本地攻击者 + 需用户交互），即便可达威胁也有限。

**修复于 1.2.2**，升级成本极低，建议顺手升。

## 六、一个方法论教训（本轮最值得记的）

### 第一次实测结果是错的

我最初在自己环境上测 DoS，结果是**全部 1-3ms 拒绝**，看起来"项目很安全"。

差点据此下结论"漏洞不可达"。

然后查了一下装的版本：

```
已装 python-multipart: 0.0.32     ← 已修复
项目锁定 python-multipart: 0.0.20  ← 有漏洞
```

**我的测试环境和被测对象不是同一个版本。**

降到 0.0.20 后重测，立刻复现：50000 个头 197ms、10MB header **1532ms**。

### 教训

**依赖漏洞审计必须验证"测试环境 == 目标环境"。** 否则会得出"看起来很安全"的假阴性——而假阴性比假阳性更危险，因为它让人不去修。

这条和之前几轮的"测试假绿"是同一类问题：**验证动作做了，但验证的不是那个东西。**
