## 一、先查 R118 那类缺陷有没有第二例

"顺序即功能"的判据：**同一函数内多个 `try → return`，条件宽松的排在严格的前面。**

用 AST 扫「≥3 个 try→return」的函数：

```
9 个候选
  5 个  core/presolve.py:1893  _try_web_target()
  4 个  core/presolve.py:3879  _try_rsa_ibe_collusion()
  3 个  skills/base64_multilayer.py:36  _try_decode()      ← R118 修的
  3 个  skills/pcap_http_carve.py:265  _ocr_flag_from_image()
  ...
```

逐个看完：

| 函数 | 性质 | 结论 |
|---|---|---|
| `_try_web_target` | sqli → ssrf → ssti，**依次尝试不同攻击** | 互不重叠，顺序无害 |
| `_try_rsa_ibe_collusion` | 同上，多种攻击链 | 顺序无害 |
| `_ocr_flag_from_image` | 依赖检查 → 前置校验 → 流程 | 不是勾选式 |
| `_try_decode` | base64/base32/hex 相互重叠 | **R118 已修** |

**R118 那个缺陷在本仓是孤例。** 判据有效，但同类为零。

## 五、改为"登记可见"

既然删不掉，那就让它们**不再隐形**。

在 `_check_dead_copy.py` 里新增一类：

```python
AUDIT_LEFTOVERS = [
    ("_b64_bak.py", "base64_multilayer 的修复前快照（解码顺序缺陷）"),
    ("_dd_bak.py",  "deterministic_decode_adapter 的修复前快照（同上）"),
    ("_vnd_bak.py", "_verify_numeric_dispatch 的修复前快照（无真值算通过）"),
]
```

输出：

```
=== 审计残留备份（修复前快照）===
  ⚠️  _b64_bak.py  ← base64_multilayer 的修复前快照（解码顺序缺陷）
  ⚠️  _dd_bak.py   ← deterministic_decode_adapter 的修复前快照（同上）
  这些文件是缺陷版；不会被 import，但会被 grep 命中。
  建议清理（本机若被运行时保护拦下，至少保持登记可见）。
```

**这不是"解决问题"，是"让问题可查"。**

两者差别很大：
- 前者需要删除成功
- 后者只需要一句登记

而登记的价值在于：下一个 grep 到这里的人，会看到"这是缺陷版"的标注，而不是把 `_b64_bak.py` 当成实现。

## 六、为什么这次不值一个"修复"

前面几轮我修的都是**功能缺陷**（私钥可推导、注入被放行、数据外发）。这三个备份：

- 不被 import（已 grep 确认零引用）
- 不影响运行
- 不影响测试

**它们只影响"人会读到什么"。** 那是文档层面的风险，不是代码层面的缺陷。

所以处置方式也该不同：**登记，而不是改代码。**

## 八、三条可复用的

1. **扫出来的东西里，可能包含自己的痕迹。**
   `_bak`、`_tmp`、`_probe` 这类前缀，往往是审计者留下的，不是项目本身的问题。
   把它们和"项目缺陷"混在一起报，会让报告失真——但也不能不管，因为它们同样是"过期代码"。

2. **删除被拒绝时，登记是第二优解。**
   运行时保护不区分"这个人判断过"和"这个文件可能有用"。
   它拒绝时，把事实写进可查的地方，比反复尝试或绕过要好。

3. **"能找到"和"看起来是真的"是两回事。**
   一个 69 行的 `_b64_bak.py` 在任何 `grep -r` 里都会出现，看起来像实现。
   加一行注释就能让它自我说明——成本极低，但没有人会主动做。

> 最后一条留给这轮最该记的：
> **我批评过的错，第二次由我自己犯。**
> R108 写"过期代码危险"，R109 让 B 库整体过期四轮，R119 又在仓库里留了三份坏副本。
> 所以"下次注意"没有用——**要有工具每次把它们打印出来。**
