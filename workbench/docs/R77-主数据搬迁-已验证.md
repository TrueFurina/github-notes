# R77 — 主数据维护端点族搬到 `app/api/master.py`

> 一句话：把 15 条 `/master/**` 路由 + 5 个请求体模型从 3311 行的 `reschedule.py`
> 整块搬出，**行为零改动**；顺手抓到一件事 —— **三道已有的门在搬家时会静默缩小
> 覆盖面，其中两道当时是绿的**。本轮把它们改成"自己发现范围"，并给"变异清单的
> 锚点"补了一条守卫（它已经失配了 3 条）。

## 2. 本轮真正的收获：三道门在搬家时会静默缩小

搬完立刻跑了受影响的测试子集，第**一**条就红了：

### 2.1 上传受限读取守卫 —— 红得对，但根因是判据

`tests/test_api_auth.py::test_all_upload_endpoints_use_limited_reader` 原来这么写：

```python
src = inspect.getsource(reschedule)          # ← 只读一个文件
assert src.count("await _read_upload_limited(file)") >= 5
```

5 个上传端点搬走 3 个之后，同一个判据数出来是 **2**，用例直接红。
**这条守卫帮我们抓到了自己**（这条门是活的）。但红的原因不是端点出错，
而是判据把扫描范围写死在了一个文件上。

改成"逐个端点查、范围由 `app/api/*.py` 自己发现"：任何 api 模块里不许出现
`content = await file.read()`；凡是形参带 `file` 的 async 端点，函数体必须调用受限读取；
找到的上传端点**不少于 5 个**（这条防的正是"判据自己的覆盖面缩水"）。

### 2.2 自愈守卫 —— **不红**，静默失守

`tests/test_apply_match.py::test_every_data_reading_route_self_heals` 也是只读
`app/api/reschedule.py`。那 15 个端点搬走之后，它们**不再接受"必须自愈"的检查**，
而用例仍然绿 —— 因为对 `tree.body` 的遍历里少了一批函数，断言自然成立。

这条比 2.1 危险：2.1 是"红给你看"，2.2 是"绿着不管了"。改成扫所有含 `APIRouter(`
的模块（模块数由目录自己数，不写死），并断言 `len(modules) >= 3`。

### 2.3 审计门 —— R76 的修法被本轮推翻

R76 把"事件循环阻塞审计"从单文件改成 CI 里**两行 `run`**，并在脚本里写着
"一次只接受一个文件；多给会直接报错，不静默取第一个"。

R77 又搬出一个带 15 条路由的模块 —— 这正是"要记得加第三行"会失效的时刻。
所以本轮改成：**不给参数 = 扫整个 `backend/app/api/`**（目录展开成 `*.py`），
CI 只剩一行。

顺带纠正 R76 的一个**错误结论**：当时判断"基线是按单文件攒的，跨文件比会得到
假的'消除 N 个'"。看代码就知道基线键是 `f"{路由路径}  {函数名}"`（`_label`），
路径在 FastAPI 里全局唯一，**基线本来就能跨文件共用**。混合扫描的实测输出是

```
扫描 5 个文件：__init__.py, landing.py, master.py, reschedule.py, xlsx_helpers.py
共 53 个路由；零 await 的 async 路由 8 个；重活藏在辅助函数里的 async 路由 0 个：
✅ 零 await 轻查询与基线一致（8 个，不允许增加）
```

—— 是"与基线一致"，不是"消除了 8 个"。R76 那句判断只对"单独扫一个新文件"成立，
不是基线本身的性质。

### 2.4 变异清单的锚点 —— 已经失配了 3 条，而且没人知道

`tests/mutation_check.py` 的 56 条变异是按 `(文件, 原文片段)` 定位的。
搬完主数据后逐条核对锚点：

| 变异体 | 问题 |
|---|---|
| M38 导入只报数量不点名新增实体 | 锚点在旧文件里，命中 0 次 |
| M47 导入不说明「预览之后数据变了」 | 同上 |
| M54 清单预览不报现有清单条数 | 文件改了**且**原文片段变了（`len(_master_tasks)` → `len(_api._master_tasks)`） |

失配的表现是跑批时"**跳过**"（skipped）—— 不计入通过，但只有真跑一遍 56 条
才会发现，而变异跑批并不在 CI 里。所以本轮加了
`test_every_mutation_anchor_still_matches_its_file`：56 次字符串计数、0.02 秒，
每次 pytest 都查，锚点一失配立刻红。

## 6. 仪器教训（第 13 条）

**锚点行尾必须跟目标文件走。** 第一版定向变异里 V6 报"锚点命中 0 次"：
`reschedule.py` 是 **CRLF**，`master.py` / 审计脚本 / 变异清单是 **LF**，
而执行器把锚点统一写成了 `\n`。表现是"锚点失效"而不是"变异生效"，
非常容易被误读成"守卫不灵敏"。修法：读文件后按 `"\r\n" in before` 取该文件自己的
行尾，再把锚点里的 `\n` 展开成它。修完 V6 立刻 1 failed / 11。

（这一条与 R75 的"`finally` 不保证执行"、R76 的"保存下来的变异态"同族：
**仪器的错会被读成被测对象的错**。）

## 7. 边界与遗留

* 本轮只搬 `app/api/master.py` 这一族；`reschedule.py` 仍 2998 行（主数据初始化与
  反推、导出族、工单、聊天、上传仍在里面）。

  `app/state.py` 会牵动所有 patch 点，另开一轮）。
* 审计脚本仍看不见"等锁"（`HEAVY` 刻意排除 `sqlite execute`，R75 的结论未变）。
* 端点层真锁 HTTP 用例、线程池 40 token 被"等锁请求"占满的风险、跨机器可复现 —— 均未做。
* `scripts/audit_async_blocking.py` 里的 `_label()` 目前无人调用（历史遗留死代码），
  本轮没动它。
