# 上传体积上限：补上一个真实可用的 DoS 缺口

> 前几轮花大量时间验证"已有防护是否被测试守住"。
> 这一轮换了个方向：**有没有防护根本不存在？**
> 结果找到一处——5 个上传端点全部无大小限制。

---

## 一、发现的缺口

`app/api/reschedule.py` 里有 5 个上传端点：

```
POST /api/reschedule/upload
POST /api/reschedule/upload-master
POST /api/reschedule/master/import-preview
POST /api/reschedule/master/tasks-preview
POST /api/reschedule/master/import
```

**全部**是这一行：

```python
content = await file.read()      # 一次读全量进内存
```

没有 `MAX_UPLOAD`、没有 `Content-Length` 校验、没有分块。

### 实际验证

构造一个 50MB 的上传：

```
构造上传体积: 50.0 MB
状态码: 400
响应: {"detail":"文件解析失败：File is not a zip file"}
```

注意几个细节：

- 状态码是 **400（解析失败）**，不是 413（太大）
- 说明**整个 50MB 已经被读进内存**，之后才在 zipfile 解析阶段失败
- 耗时 200ms —— 这 200ms 里内存在承担 50MB

换句话说：**"文件格式校验"这道关起不到保护作用**，因为伤害在它之前就已经发生了。

### 影响

| 场景 | 后果 |
|---|---|
| 攻击者发 10 个 500MB 请求 | 5GB 内存被占，进程 OOM |
| 正常用户误传大文件 | 同样拖垮服务 |
| 内网误操作 | 无意识触发 |

虽然这些端点在 `_ADMIN_ONLY` 后面（需要管理员令牌），但：

1. 令牌泄露后攻击者第一件事就是打这里
2. 管理员误操作同样会触发
3. 限流规则里这几个 bucket 的阈值并不低

## 二、修复

### 核心：在读取过程中判断，不是读完再判断

```python
MAX_UPLOAD_BYTES = int(os.getenv("MAX_UPLOAD_MB", "32")) * 1024 * 1024
_UPLOAD_CHUNK = 1024 * 1024  # 1MB


async def _read_upload_limited(file: UploadFile, limit: int = None) -> bytes:
    """分块读取上传内容，超过上限立即 413，不做完整读入。"""
    cap = MAX_UPLOAD_BYTES if limit is None else limit
    buf = bytearray()
    while True:
        chunk = await file.read(_UPLOAD_CHUNK)
        if not chunk:
            break
        buf.extend(chunk)
        if len(buf) > cap:
            raise HTTPException(
                status_code=413,
                detail=f"文件超过上限（{cap // (1024*1024)} MB）。...",
                headers={"X-Max-Upload-Bytes": str(cap)},
            )
    return bytes(buf)
```

**关键区别**：

| 写法 | 内存峰值 | 何时拒绝 |
|---|---|---|
| `await file.read()` + 后判大小 | 完整文件大小 | 读完之后 |
| **分块累加 + 过程中判** | cap + 1 块 | 越过 cap 立刻 |

### 5 个端点全部替换

```diff
- content = await file.read()
+ content = await _read_upload_limited(file)
```

同时加了**守卫测试**，防止将来有人改回去：

```python
def test_all_upload_endpoints_use_limited_reader():
    src = inspect.getsource(rs)
    assert "content = await file.read()" not in src, (
        "仍有上传端点用裸 file.read() 全量读入，超大文件会顶爆内存"
    )
    assert src.count("await _read_upload_limited(file)") >= 5
```

## 三、实测效果

| 场景 | 修复前 | 修复后 |
|---|---|---|
| 50MB 上传 | 400（读完才拒），~200ms | **413**，155ms |
| 1MB 正常上传 | 400（解析失败） | 400（解析失败）✓ 不误伤 |

响应体：

```json
{"detail":"文件超过上限（32 MB）。如确需上传更大的表格，请设置环境变量 MAX_UPLOAD_MB 后重启服务。"}
```

头部：`X-Max-Upload-Bytes: 33554432`

**默认 32MB 的理由**：一份几百行的排课表 Excel 通常 < 2MB，32MB 留了 16 倍余量。需要更大时用环境变量覆盖，不用改代码。

## 四、全量回归抓到一个连带问题

改完后跑全量，出现 1 个失败：

```
FAILED tests/test_master_input.py::test_upload_master_endpoint_stores_tasks
TypeError: _Up.read() takes 1 positional argument but 2 were given
```

测试里有个假的文件对象：

```python
class _Up:
    filename = "m.xlsx"

    async def read(self):          # ← 不接受 size 参数
        return p.read_bytes()
```

而真实 `UploadFile.read(size=-1)` 是支持带参的。**我的实现没错，是桩与真实接口不一致。**

修法是让桩实现 `read(size)` 的真实语义（含游标），而不是改我的实现迁就桩。

```python
async def read(self, size: int = -1):
    data = p.read_bytes()
    if size is None or size < 0:
        return data
    if not hasattr(self, "_pos"):
        self._pos = 0
    chunk = data[self._pos:self._pos + size]
    self._pos += len(chunk)
    return chunk
```

**这个失败很有价值**：它证明全量回归真的在起作用。如果只跑 `test_api_auth.py`（我新测试所在文件），这个破坏完全不会被发现。

## 八、这轮方法和之前几轮的区别

| 轮次 | 方向 | 产出 |
|---|---|---|
| 之前 | 验证**已有**防护是否被测试守住 | 变异测试 7/7 |
| **这轮** | 找**不存在**的防护 | 上传大小限制（缺失） |

前几轮把"已有防护的测试有效性"做到了 7/7。但 **7/7 只说明"有的都被测住了"，不说明"该有的都有"。**

这轮换角度才找到这一处：不是测试不够，是防护本身没有。

### 判断方法

拿到一个上传端点，问三个问题：

1. 文件名安全吗？→ 有 `_safe_upload_name` ✓
2. 后缀白名单吗？→ 有 `_EXCEL_SUFFIXES` ✓
3. **大小有限制吗？**→ **没有** ✗

前两个都有测试覆盖，第三个连防护都没有——所以变异测试也发现不了它（没有代码可删）。

## 十、一个过程记录

这轮我在修改 `mutation_check.py` 时把文件写坏了两次（字符串里的 `\n` 被当成真换行），加上网络受限无法从远端恢复，最后靠完整重写才修复。

**教训**：用 `python -c` 拼多行字符串做文件编辑，转义层数一多就不可靠。涉及多行文本修改，应该直接用文件写入，而不是命令行内联。

这属于操作层面的失误，不影响最终结果——但确实多花了几次往返。
