## 二、三条主线

### 主线 A：教师端归属（R50 → R51）

`GET /teachers/{name}/courses` 是教师看到"我教了什么"的唯一入口，也是调课申请的起点。
两个缺陷叠在一起：

1. **课程归属整条链路没接**。`course_bridge.resolve_course` 早就会算、
   `ScheduleEntry.course` 外键早在，但分组键只有 `(实验项目, 班级)` ——
   同一项目跨两门课会塌缩成一张卡片，教师看不到自己上的是哪门课。
2. **`week_range` 编数字**。`[3, 5, 9, 11]` → `"3-11周"`，而这个字段就渲染在界面上
   （`CoursesView.tsx:60`）。教师只会理解成"每周都有课"或"连续 9 周"，两种都多 5 次课。

改法：卡片新增 `course`/`courses`/`course_ambiguous`/`weeks`；`week_range` 改"连续才用区间"。
**刻意不把课程加进分组键** —— `apply-move` 按实验名匹配，拆卡片会让所有历史申请单失配。

### 主线 B：错误路径的可观测性（R52 → R53 → R54）

这一条是连锁的，从一个探针推出来：

- R52 本想查"500 有没有留痕"，结果 **`GET /__boom__` 返回 200 + index.html** ——
  异常根本没进那条路由，SPA 兜底先接住了。顺藤摸下去：任何 `/api` 下的未知路径
  （拼错的、只支持 POST 的写接口、`/master/init`）都是 200 + HTML。
  前端 `r.json()` 抛 `Unexpected token '<'`，监控里 `status:200`、`errors` 不增。
- R53 接着量真实 500：**计数器 0→0、日志一行都没有、没有耗时头、没有地址、没有栈**。
  根因是中间件的计数与日志写在 `await` 之后 —— 可观测性代码天然在请求之后，
  而"之后"在异常路径里等于"不执行"。改法：搬进 `finally` + 8 位 `x-request-id`
  + `Exception` 处理器显式 `exc_info` 打栈，对外只回 `{detail, error_id}`。
- R54 补最后一公里：后端给了编号，前端 `describeApiError` 只读 `detail`，
  用户看到的仍是通用文案。改法：`error_id` 或 `x-request-id` 任一取到就拼进提示，
  且 5xx 带编号时不再劝"稍后重试"（代码 bug 重试一百次也一样）。

### 主线 C：落地审计（R55 → R56）

`landed_plans` 表本来就是个不错的审计设计（方案 + 落地前快照 + 时间）。但撤销是
`DELETE`：教秘点一次"撤销"，这次落地在库里一根毛都不剩；`actor` 从来没记过 ——
`require_admin` 一直有返回值，落地时只写 `note`（可留空）。

改法：`revoke()` 打 `revoked_at`/`revoked_by` 不删行；`save` 记 `actor`；
`latest()`/`all()` 只认未撤销的；新增 `/parallel/land/history`。
**最危险的一处单独立了用例**：`all()` 若不过滤已撤销，重启重放会让撤销过的方案
自己回到课表上，而没人点过任何按钮。R56 把历史接进了落地面板。

## 三、这两个模型上的共同根因

### 「静默成功」家族（第 4、5、6 次了）

| 现象 | 轮次 |
|---|---|
| 删默认课程：返回成功，什么都没删 | R39 |
| `/api` 未知路径：返回 200 + 前端页面 | **R52** |
| 500：不计数、不打日志，运维侧"什么都没发生" | **R53** |
| 周次区间：不连续的周写成 `3-11周` | **R50** |
| 落地：撤销后记录消失，"曾经发生过"无从查起 | **R55** |

共同点：**没有报错、没有空值、没有红色**，只有一个看起来正常的返回值。
这类缺陷的共同判据可以写成一句话：

> **一个"没查/没做/没记"的结果，和"查了、做了、记了且确实为零"的结果，
> 在输出上必须长得不一样。** 长得一样，就等于没做。

### 「后端给了、界面没接」（4 次）

R50→R51、R53→R54、R55→R56，外加更早的 `note` 字段只写不读。
每次都是后端全绿、接口文档更新、测试覆盖，而用户眼前一个字都没变。

**本轮已把它固化成流程**：每轮收尾必须回答"这一轮的改动，用户在哪一屏能看到？"
答不上来就在台账里明写"本轮只到接口层，界面在 Rxx"。见 R56 的教训一节。

## 四、这一窗口固化了三条检查（都救过场）

1. **推送前：从远端原文打补丁，再 diff 一次，只允许出现自己那一处。**
   两次拦住整文件覆盖：R50 的 `reschedule.py`（本地 CRLF 3311 行 / 远端 LF 3298 行）、
   R56 的 `types.ts`（本地 CRLF / 远端 LF）。直接推上去，真正的几行修改会埋在
   几千行"改动"里，谁也看不见 —— 而"我明明只改了几行"恰恰会让人跳过核对。
2. **全量测试必须在隔离副本上跑。** 工作副本同时被另一个会话的 `mutation_check.py`
   改动（它会把 `security.py` 改成 `if False:` 再跑测试）。第一次撞见时表现为
   8 条鉴权用例失败，看起来像自己改坏了鉴权。**结论不是"我的改动没问题"，
   而是"这份工作副本此刻不是可信基线"。**
3. **探针优先于读代码。** R52 的走廊是"查 A 撞见 B"：读代码能确认"作者想让它发生"，
   只有打一次真实请求才能确认"它真的发生"。这一窗口里 R52/R53 两个最值钱的发现，
   都是探针撞出来的，不是读出来的。
