## 二、备份：动手前的唯一前提

脚本：`scripts/backup-mars408.sh`（只读，不改远端）

```bash
bash scripts/backup-mars408.sh ./backup-mars408
```

它做四件事：

1. `git clone --mirror` 完整镜像（含所有分支与 tag）
2. 记录 `SNAPSHOT.txt`（ref 列表 + HEAD SHA），供回滚定位
3. 导出 `.env.test` 的 HEAD 版与历史版原文到 `evidence/`
4. 输出当前体积构成基线

### 已验证的部分

| 检查 | 结果 |
|---|---|
| 脚本语法 `bash -n` | ✅ 通过 |
| 体积统计 awk 逻辑 | ✅ 用本地测试仓库验证，含空格路径正确归组 |
| 镜像克隆 | ⚠️ 本机无法直连 github.com（TLS 被重置），未实测 |

### 一个必须说明的技术细节

体积统计原本用 `git ls-tree -r -l | awk` 按空格切列。这个写法在路径含空格时会**列错位**——而 `MARS-408` 恰好有 `deliverables/MARS-408 考研多智能体个性化学习系统/` 这样的路径，**必然触发**。

实测对比：

```
错误版（空格切分）:  a 目录被算成 2 bytes，实际统计错位
正确版（-z NUL 分隔）: a=2, b=3, c 有空格=4  ← 正确
```

已改用 `-z` + `RS='\0'`。这类错误不会报错，只会静默给出错误数字——如果不测试就交付，你看到的体积基线全是错的。

## 三、回滚：三种兜底，按可靠度排序

### 兜底 1 · 本地镜像（最可靠）

```bash
cd backup-mars408/MARS-408.git
git remote set-url --push origin https://github.com/TrueFurina/MARS-408.git
git push --mirror
```

⚠️ `--mirror` 会覆盖远端**所有 ref**，包括删掉远端新增的分支。只在确认误操作时用。

### 兜底 2 · GitHub 服务端残留

被 force push 覆盖的 commit **通常仍可通过已知 SHA 访问**一段时间（可能长达数月，取决于是否被 GC）。

所以操作前**务必记下操作前的 HEAD SHA**（脚本的 `SNAPSHOT.txt` 已包含）。有这个 SHA 就能：

```
https://github.com/TrueFurina/MARS-408/commit/<旧SHA>
https://github.com/TrueFurina/MARS-408/archive/<旧SHA>.zip
```

### 兜底 3 · 本地 reflog（90 天内）

如果你在本地仓库直接做 filter-repo，操作前的状态仍在 reflog：

```bash
git reflog --all | head -20
git reset --hard <操作前SHA>
```

**这是最快的一条，但只在本地有效**，push 之后无法用 reflog 恢复远端。

## 四、两个操作的正确执行顺序

如果将来决定执行，**必须按这个顺序**，否则会制造二次损失：

```
1. 备份（镜像克隆 + SNAPSHOT）
2. 本地 clone 一份工作副本
3. 本地执行 filter-repo
4. 本地跑一遍验证（见第五章）
5. 确认无误后 force push
6. 推送后再验证一次
```

**最容易做错的第 5 步**：不要在没验证的情况下直接推。filter-repo 一旦推送，回滚要靠 `--mirror`，而 `--mirror` 本身也会覆盖你推送后做的一切。

### 合并执行的命令（一次完成两件事）

```bash
git filter-repo \
  --path py-server/iq_run_tmp/.env.test \
  --path "deliverables/MARS-408 考研多智能体个性化学习系统/源码/py-server" \
  --path "submission/04_源码/MARS-408_source/py-server" \
  --invert-paths

# filter-repo 会移除 remote，需要重新添加
git remote add origin https://github.com/TrueFurina/MARS-408.git
```

## 五、推送前验证清单

在本地执行完 filter-repo，**push 之前**逐项确认：

```bash
# 1. 敏感文件是否从所有历史消失
git log --all --oneline -- py-server/iq_run_tmp/.env.test
# 期望：无输出

# 2. 是否还能搜到该文件对象
git rev-list --all --objects | grep "iq_run_tmp/.env.test"
# 期望：无输出（除 .env.test.example）

# 3. 副本目录是否清空
git ls-files | grep -c "deliverables/.*源码/py-server"
git ls-files | grep -c "submission/04_源码/.*py-server"
# 期望：都是 0

# 4. 主源码是否完好
git ls-files | grep -c "^py-server/"
# 期望：与操作前一致（约 800+）

# 5. 关键入口文件是否还在
ls py-server/main.py py-server/pyproject.toml Dockerfile
# 期望：都存在

# 6. 文档与图表是否保留（这是不能丢的部分）
git ls-files | grep -c "deliverables/"
# 期望：> 0（文档保留，只删了源码副本）

# 7. 仓库体积
du -sh .git
# 期望：约 30 MB（原 111 MB）
```

**第 6 项最容易漏检**：如果 `deliverables/` 计数变成 0，说明删过头了，把文档也删了。

## 六、如果决定"永远不做"，也需要做一件事

即使你决定不重写历史，`.env.test` 的历史内容**永久可读**。那么对应的义务是：

- [ ] **确保 `admin****` 这类口令惯例不会被复用到真实环境**（这是唯一实质风险）
- [ ] 在仓库 README 或 SECURITY.md 注明该文件为测试配置，非生产凭据

第二条是给未来的读者（包括面试官、同行、你自己）看的。一个安全方向的项目，主动标注一处历史遗留问题，比藏起来更能建立信任——这和你在 `SecAutoMind` 落地页主动区分"真题 34.5% / 自产题 60.7%"是同一个逻辑。

## 七、为什么我没有替你执行

两次询问执行方式都没有返回选择，我按最保守路径处理：**不执行不可逆操作**。

理由不是犹豫，而是这三个问题只有你知道：

1. 赛事材料里是否引用了具体 commit 链接（决定重写代价）
2. 评审是否要求 `submission/` 保持原目录结构（决定能否删副本）
3. 是否还有其他机器/协作者依赖当前历史

**前两项如果判断错，代价是评审拿到 404 链接或缺失材料**——这类损失在赛程中无法挽回。
