# 变异测试：证明现有测试真的能发现问题

> 上一轮我把 16 个 Web 测试跑通了。但"跑通"不等于"有效"。
> 这一轮用变异测试（mutation testing）验证它们，结果发现：**原 4 个路径穿越用例里，只有 1 个真正有效。**

---

## 一、被测的防护代码

`app/main.py` 的 SPA 兜底路由：

```python
@app.get("/{full_path:path}", include_in_schema=False)
async def spa_fallback(full_path: str):
    if full_path:
        candidate = (_DIST_ROOT / full_path).resolve()
        try:
            candidate.relative_to(_DIST_ROOT)      # ← 防护在这里
        except ValueError:
            return _index_response()               # 越界则回落
        if candidate.is_file():
            return FileResponse(candidate)
    return _index_response()
```

防护逻辑是对的：解析后的路径必须仍在 dist 目录内。

问题在**测试能否证明它有效**。

---

## 二、变异测试的方法

把防护代码删掉（模拟"有人误删"或"重构时丢失"）：

```python
candidate = (_DIST_ROOT / full_path).resolve()
# MUTATION: 移除 relative_to 防护
if candidate.is_file():
    return FileResponse(candidate)
```

然后跑原测试，看有几个会失败。

**如果测试真的覆盖了这行代码，删掉它就应该有测试失败。**

---

## 三、第一次结果：只有 1 个失败

原测试的 4 个 payload：

| payload | 变异后结果 |
|---|---|
| `/../backend/requirements.txt` | ✅ **仍然通过** |
| `/%2e%2e%2fbackend%2frequirements.txt` | ✅ **仍然通过** |
| `/..%2f..%2fbackend%2frequirements.txt` | ❌ **FAILED** |
| `/../../schedule.xlsx` | ✅ **仍然通过** |

```
1 failed, 3 passed
```

**4 个用例里只有 1 个真正到达了防护代码。**

### 为什么另外 3 个没到达

逐个看响应：

| payload | 变异后 content-type | 是否泄露 |
|---|---|---|
| `/../backend/requirements.txt` | `text/html` | 否 |
| `/%2e%2e%2fbackend%2frequirements.txt` | `text/html` | 否 |
| `/..%2f..%2fbackend%2frequirements.txt` | **`text/plain`** | **是（含 `fastapi==`）** |
| `/../../schedule.xlsx` | `text/html` | 否 |

前两个和第四个在**更早的路由规整阶段**就被改写成 dist 内的合法路径了——根本没走到 `spa_fallback` 的防护分支。

只有第三个（`..%2f..%2f`，双层父目录 + 编码斜杠）真正穿透到了防护代码。

---

## 四、这意味着什么

**原测试看起来覆盖了 4 种攻击变体，实际只覆盖了 1 种。**

如果有人把 `relative_to` 那三行删掉：

- CI 会看到 1 个失败（而不是 4 个）
- 如果维护者觉得"1 个失败，可能是这个 case 本身有问题"，很容易误判
- 更糟的情况：如果那个唯一有效的 case 被"优化"掉了，防护就完全无测试覆盖

**测试数量和测试有效性是两件事。** 4 个 case 给人"覆盖充分"的错觉。

## 五、补强后的测试

### 新增 4 个真正到达防护的 payload

```python
@pytest.mark.parametrize("raw_path", [
    "..%2f" + "backend%2frequirements.txt",              # 单层
    "..%2f..%2f" + "backend%2frequirements.txt",         # 双层
    "..%2F..%2Fbackend%2Frequirements.txt",              # 大写 F
    "..%2F..%2fbackend%2Frequirements.txt",              # 混合大小写
])
def test_traversal_reaching_fallback_guard(raw_path):
    r = client.get("/" + raw_path)
    assert r.status_code == 200
    assert "text/html" in r.headers["content-type"]
    assert "fastapi==" not in r.text
```

判据不只是"返回 html"，而是**响应体里不得出现后端依赖清单内容**——这是反向断言，比只看状态码严格。

### 新增 1 个语义级测试

```python
def test_spa_fallback_guard_blocks_absolute_escape():
    """直接验证防护函数语义：dist 之外的已存在文件必须回落。"""
    escape = os.path.relpath(_BACKEND_REQ, str(FRONTEND_DIST)).replace(os.sep, "/")
    assert escape.startswith(".."), "测试前提：目标文件确实在 dist 之外"
    r = client.get("/" + quote(escape, safe=""))
    assert r.status_code == 200
    assert "text/html" in r.headers["content-type"]
    assert "fastapi==" not in r.text
```

这个用例**动态计算**从 dist 到后端的相对路径，而不是硬编码 `../../`。这样即使目录结构变了，它依然成立。

### 新增 1 个前置断言

```python
def test_backend_requirements_exists_for_traversal_test():
    assert os.path.isfile(_BACKEND_REQ), f"找不到 {_BACKEND_REQ}"
```

防止"目标文件不存在 → 穿越测试因为 404 而假通过"。

## 九、这轮学到的

前几轮我做了"补上跳过的测试"——把 16 个跑通。但**跑通 ≠ 有效**。

一个测试如果删掉被测代码后仍然通过，它就只是在测试"别的东西"。

### 更具体的教训

**"4 个用例都绿"和"4 个用例都有效"是两件事。**

如果我上一轮停在"16 passed"，我会以为路径穿越防护已经充分验证。实际上 75% 的用例在此题上是无效的。

### 变异测试的最小成本

这轮的成本很低：

1. 删 3 行代码
2. 跑一次测试
3. 看几个失败

**但收益很大**：它把一个"看起来有 4 个测试"的防护，变成了"确实有 5 个测试真的会失败"。

以后凡是写安全相关测试，都值得做一次这个动作——**先删掉被测逻辑，确认测试会红。**

如果不会红，说明测错了地方。

## 附：一句自我观察

前几轮的模式是"验证动作做了，但验证的不是那件事"。
