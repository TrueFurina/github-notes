## 4. 本轮推翻 / 纠正的五条（含推翻我自己）

### 4.1 `grep -c $'\r'` 会假报 CRLF —— 差点让我推翻一个正确结论

我先用 `grep -c $'\r'` 统计，得到 `112/112`、`181/181`、`3472/3472`，看起来"全是 CRLF"，与任务书"纯 LF"矛盾，**差一点据此改写任务书**。

真实原因是：在 Git Bash 下 `$'\r'` 一旦展开失败就退化成空模式，`grep -c ''` **把每一行都算作匹配**，输出恰好等于总行数。

用二进制统计才拿到真相：

```python
d = open(p, 'rb').read(); d.count(b'\r\n'), d.count(b'\n')
# xlsx_helpers.py              CRLF=0    LF=112   ← 任务书对
# test_xlsx_helpers_contract.py CRLF=0   LF=181   ← 任务书对
# reschedule.py                CRLF=3472 LF=3472  ← 纯 CRLF，任务书也对
```

**结论：任务书第 26–27 行没错，错的是我的检测命令。** 行尾判据一律改用 Python 二进制统计。

### 4.4 变异脚本的「脏 pyc」陷阱 —— 这才是"56/56 从来不稳定"的真正机制

这一条推翻的是**我自己在 R44/R57 里的归因**（当时记成"CP-SAT 多线程不确定 / 顺序依赖"）。

现场：`tests/mutation_check.py` 在一个进程里连跑 56 条，**前 5–8 条正常，之后每条都是**

```
pytest 退出码 1: ?        ← 拿不到 "N failed" 统计行
```

用 subprocess 内窥后看到：失败条目的 **stdout 只有 79 字节**（一行 `FFFF… [100%]` 进度条），**详细报告整段消失**，stderr 从 633 涨到 880。

根因链：

1. `main()` 恢复源文件用 `shutil.copy2(backup, path)`，**copy2 保留 mtime**；
2. CPython 的 pyc 校验只看 **源文件 mtime（秒级）+ size**；
3. 同一秒内对同一文件做「等长变异 → 恢复」，恢复后的 `(mtime, size)` 可能与某次变异版本**完全一致** ⇒ 子进程直接加载**变异版 pyc**；
4. 于是 import 进来的模块行为错乱，pytest 在半路崩掉，统计行丢失 ⇒ `_run_tests` 判"无效"。

三个旁证：
- 单独跑一条（有秒级间隔）→ 永远正常；
- 一个进程里第 6/7 条之后必崩；
- 同一个源文件被多个变异体连续动（M1–M4 都动 `security.py`）→ 崩得更早。

已实测有效的修法（`_mut_one.py`，临时工具，不进仓库）：**一条变异体一个 python 进程**，并把变异版的 mtime 钉到 `原始 mtime + 5 + IDX`（带 IDX 保证**每条唯一**，防止跨变异体复用），恢复时钉回原 mtime。

## 5. 变异梯队的口径（必须连带这句一起看）

**结果是 56/56 检出、0 存活、0 SKIP**，但**不是一条命令跑出来的**：

- 一条变异体一个独立 python 进程（`_mut_one.py`），

另：`_mut_R54_all2.log` 里有 10 行 `???? …[attempts=3]`，那是**早期交错运行**残留的失败行（如 M14–M16 各出现一行 BAD 和一行 PASS）。统计按"每个 M 编号至少一次检出"计。
