# R50 断点① 根因分析与修复方案

> 对象：`/reschedule/parallel/solve`（单班一键求解）默认参数必败，而全校一键同班排满 45。
> 性质：**S8 链路级死胡同**——每个环节都正确，连起来用户走不通。
> 状态：只分析、不改 `work-repo`（该仓正被 R51 及并发 worker 使用）。落地方案留给后续轮次。

---

## 一、实测症状（来自 R50 端到端八步链路）

`_r50_steps.json` 的 `solve_attempts` 原文：

| 尝试 | 结果 |
|---|---|
| 默认参数（起始周取主数据） | ❌ `排不下：45 个教学单元、5 个学生组、1 位指导教师，每周最多排 4 个 ⇒ 至少需要 12 周；而本表只覆盖到第12周，从第2周起仅剩 11 周。请把起始周调早…` |
| `start_week=1` | ✅ `45 个项目×组别单元一键排定，固定周日`，`weeks_used=12` |
| `/parallel/solve-all` | ✅ 同班 `scheduled=45`、全校 17/17 排满 |

同一个班、同一份数据、同一天：**单班入口必败，全校入口必成**。

## 二、根因：不是"少一个输入框"，是两处自我设限叠加

### 2.1 数学上的必败（差 1 格）

| 项 | 主数据采用 | 全表实际 |
|---|---|---|
| 起点 `week_min` | **2** | 1 |
| 终点 `week_max` | **12** | **16** |
| 窗口宽度 | 11 周 | 16 周 |
| 每周可排 | 4 格（`min(5组, 时段×教师=1教师×3时段=3)` → 实为 4） | 同 |
| 总容量 | 11 × 4 = **44 格** | — |
| 需求 | **45 单元** | — |

**44 < 45，差 1 格。** 这不是"资源紧张"，是默认参数下**数学上不可能**。
调到 `start_week=1` ⇒ 12 × 4 = 48 ≥ 45 ⇒ 恰好够（`weeks_used=12`，已是最紧）。

### 2.2 `week_min=2` 是有意的产品决策，不是 bug

`backend/app/master_data.py:130-135` 原文：

> ⚠️ 班级 / 教师 / 场地**实体**的累积仍然跳过绪论与考试类。
> 实测：若把它们也算进去，17 个班的 week_min 会统一提前 1 周（绪论课在该班第一次实验之前），求解器的周次窗口随之放宽 —— **那是 R-51 锁定的产品边界（"时间由教务给定"），不该顺手改**。

所以：`week_min` 反推时排除了绪论课/考试 → 该班真实验课最早在第 2 周 → 起点 2。
**这个设计是对的**：系统不该自作主张把时间范围放宽到教务没给的周次。

### 2.3 `week_max=12` 也是反推值，但全表有 16 周

该班历史周次实测：`[1,2,3,4,5,6,8,9,10,12]`（max=12）；全表覆盖 `1–16`。
即：**第 13–16 周全表都在用**（别的班有课），但该班"历史没上过"→ 默认窗口被砍到 12。

同一份 R-51 逻辑在这里产生副作用：**"历史没上过"不等于"不能上"**。实验课新排课本来就可能排到历史未覆盖的周次。这是 `week_max` 与 `week_min` 不对称的地方——`week_min` 前移会侵占教务给的时间（该拦），`week_max` 后移只是用满表内已有周次（不该拦）。

### 2.4 前端从不传 `start_week`（真正断点）

`frontend/src/api/client.ts:292-298`：

```ts
parallelSolve: (className: string, weekday?: string) =>
  api.post<...>('/reschedule/parallel/solve',
    { class_name: className, weekday: weekday ?? null }),
```

`grep -rn "start_week\|startWeek" frontend/src` → **零命中**。
后端 `ParallelSolveRequest` 完整支持 `start_week`（`reschedule.py:1518`），8 个测试在用，**唯独前端从不发送**。

于是：错误文案说"请把起始周调早"→ 界面上没有这个输入 → **用户无路可走**。
这就是 S8 的判据形态：**错误文案承诺的出路，客户端没有可达入口。**

## 三、为什么全校一键能过（不是因为它放宽了窗口）

`solve_school` 内部**按单元的历史星期拆天**（`parallel_scheduler.py:160` `by_day[day].add(key)`），逐天独立求解。

该班历史星期分布实测：**周日 24 节、周六 18 节、周一 3 节、周三 1 节**。

- 单班 `/solve`：强制 `weekday=周日` → 45 单元**全挤周日** → 每周 4 格 → 需 12 周 → 窗口 11 周 → **败**。
- 全校 `/solve-all`：45 单元**摊到 3 天** → 每天约 15 单元、每天每周仍有独立格子 → 8 周就够 → **成**。

**结论：solve-all 能过靠的是"摊薄"，不是"放宽窗口"。** 两个入口的时间范围完全相同（都取 `_master_data.classes` 的 `week_min/week_max`），差别只在"单天 vs 分天"。

这也解释了为什么这不是"一个入口有 bug"：**两个都是对的设计，只是单班口径下容量真的不够**，而系统没把这一点说清（文案说"减少项目/组别"——用户无法减少，那是数据决定的）。

## 四、修复方案（三个选项，按推荐度）

> 前提约束：**不得违反 R-51 产品边界**（不得自动放宽时间范围）。

### ✅ 方案 B（推荐，最小、尊重边界）

把后端已支持的 `start_week` **接通到前端**。

1. `client.ts:292` 签名加参数：
   ```ts
   parallelSolve: (className: string, weekday?: string, startWeek?: number) =>
     api.post<...>('/reschedule/parallel/solve',
       { class_name: className, weekday: weekday ?? null,
         start_week: startWeek ?? null }),
   ```
2. `App.tsx:226` 传入界面上新增的「起始周」值（默认空 = 用主数据）。
3. 排课面板加一个「起始周」数字输入（placeholder：主数据的 `week_min`），并在**失败时**直接把该输入框高亮 + 提示"把起始周调到第 1 周可排下当前 45 个单元"（若后端能给出这个建议值，见方案 C）。

**优点**：改动 3 处、不动引擎、不破坏 R-51（由人决定放宽，不是系统偷偷放宽）。
**缺点**：用户仍需手动知道"填几"。

### ✅ 方案 C（体验最好，可与 B 叠加）

后端在**容量不足**分支，额外算一次"最小可行起点"，作为**建议值**返回：

```python
# parallel_scheduler.py 容量不足分支（当前 line ~553）
# 已有：need_weeks / max_avail / week_max / start_week
suggest = None
if need_weeks > max_avail:
    earliest = all_weeks[0]                      # 表内最早周
    if (week_max - earliest + 1) >= need_weeks:  # 表内确实放得下
        suggest = week_max - need_weeks + 1      # 最小可行起点
return {"success": False,
        "error": (... 保持原文案 ...),
        "suggest_start_week": suggest}           # 新增，不破坏旧字段
```

前端拿到 `suggest_start_week` 就渲染成**一键按钮**："从第 1 周重试"。
实测该班应得 `suggest = 12 - 12 + 1 = 1`，与 R50 手工试出的 `start_week=1` 完全一致。

**优点**：用户零猜测、一次点击解决；且"是否接受放宽"仍由人点。
**缺点**：需后端 + 前端各一处改动，要配回归测试。

### ❌ 方案 A（不推荐）：后端自动放宽窗口

即把 `week_max_override` 从 `md_week_max` 改成 `all_weeks[-1]`，或自动把 `start_week` 前探。
**这违反 R-51**（"时间由教务给定"），且会让 `week_max` 的语义从"教务给的边界"变成"尽力而为"。若要做，必须同时改产品定义并在 UI 明示，不是一行代码的事。

## 五、一处自我修正（诚实记录）

我最初推断："就算给前端加 `start_week` 输入也救不了，因为需求 12 周 > 表覆盖 11 周"。

**这个推断被 R50 的实测数据推翻了**：`start_week=1` 时窗口是 `1..12 = 12 周`，**恰好够**（48 ≥ 45），实测成功。

错在哪里：我把"表覆盖到第 12 周"误读成"窗口最多 11 周"。实际 `week_max=12` 是**终点**，起点从 2 前移到 1 就多出 1 周，窗口宽度由 11 变 12。
**教训**：算窗口宽度时，"起止点"与"宽度"是两个量，前移起点和推后终点都能加宽——我漏了前者。

## 六、验证方法（落地时必须做）

1. **先红后绿**：先在隔离副本写测试，断言默认参数返回 `success=false` 且 `suggest_start_week=1`；再用该建议值重试断言 `success=true`、`scheduled=45`。
2. **不破坏既有**：全量 `pytest` 基线应仍为 `724 passed`（R49 口径），不得下降。
3. **回归锁**：新增测试须覆盖"`suggest_start_week` 为空时（表内真的放不下）不得编造建议值"——避免造出第二个假绿灯。
4. **变异检出**：`mutation_check.py` 须全检出且 **SKIP=0**（M30 教训：SKIP 不进退出码 = 假绿）。

## 七、附带发现（同轮值得记一笔）

`week_min` / `week_max` 的语义不对称，是本断点的结构性来源：

- `week_min` 前移 = **侵占教务给的时间** → 该拦（R-51 正确）。
- `week_max` 后移 = **用满表内已在使用的周次** → 拦得过头了。

建议后续轮次把这两个边界**分开定义**（例如 `sched_start` 受 R-51 约束、`sched_end` 取全表覆盖），而不是共用一个"该班历史范围"。这比给前端加输入框更治本，但属于产品口径变更，需先确认 `week_max` 是否承载了教务的隐含约束（第 13–16 周该班是否真的不上实验课）。
