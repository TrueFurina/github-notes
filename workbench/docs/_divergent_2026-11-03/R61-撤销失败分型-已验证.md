# R61 · 撤销失败的两种结局，不该共用一个状态码

> 对应遗留项：`undo` 失败映射 404→500（D2 §8 第 6 条，自 R45 `d83845b3` 挂起）
> 落点：`app/api/reschedule.py::land_undo`、`app/plan_landing.py::undo`、
> `frontend/src/components/LandPlanPanel.tsx::doUndo`

## 1. 一句话

撤销失败有两个**完全不同的结局**，以前都报 404：一个是什么都没发生（该报 404），
一个是**课表已经退回去了、只是撤销标记没写进库**（该报 500）。后者被报成 404 时，
界面写"没有可撤销的记录"，而安排表其实已经变了 —— 教秘会以为撤销没生效，
转头去"重新落地"，把刚退掉的方案又落回去。

## 2. 缺陷：一个动作，两种结局，一个状态码

`plan_landing.undo()` 的两条失败返回，语义完全不同：

| 分支 | 内存里的课表 | sqlite 里的记录 | 正确状态码 |
|---|---|---|---|
| 没有可撤销的记录 | 没动 | 没有 | **404**（资源不存在） |
| 课表已回滚、`revoke` 两次失败 | **已退回落地前** | 仍为「已落地」 | **500**（服务端没做完） |

端点此前写的是：

```python
if not out.get("success"):
    raise HTTPException(status_code=404, detail=out["error"])
```

三种代价同时发生：

1. **界面撒谎**：教秘看到的是「没有可撤销的记录」，而安排表已经退回落地前。
2. **事实被丢弃**：`rolled_back: true`、`restored_entries: N` 这些**已经发生的事**
   随 `HTTPException` 一起没了。前端无从判断"该不该再点一次撤销"（该），
   只会弹一句通用报错。
3. **动作走反**：以为撤销失败 → 去"重新落地" → 把刚退掉的方案又落回去。
   而这条正确的下一步（**再点一次撤销**把标记补上）没有任何地方说过。

第 2 条尤其隐蔽：它不是文案问题，是**结构信息在错误路径上被静默丢弃**。
R59 刚把"两次失败原因都报出来"做进 `error` 字符串，但那个字符串在端点上被塞进
`detail`，其余字段全丢。

关键那五行：

```python
if out.get("success"):
    return out
if out.get("error_kind") == "no_record":
    raise HTTPException(status_code=404, detail=out["error"])
return JSONResponse(status_code=500, content={**out, "detail": out["error"]})
```

为什么不用 `HTTPException(500, detail=...)`：那样结构体又只剩一个字符串，第 2 条代价
原样保留。为什么还补 `detail`：前端通用的 `describeApiError` 只认 `detail: string`，
补一个不是妥协，是让**不认结构**的调用方也能拿到人话。

前端那边：

```ts
if (err?.response?.data?.rolled_back === true) {
  setDiff(null);
  await loadStatus();          // 不刷新的话，面板还挂着"已落地 / 可撤销"
  onMsg('⚠️ 撤销只做了一半：安排表已回滚到落地前，但撤销记录没写进库 —— '
      + '请再点一次「↩️ 撤销落地」把记录补上。');
}
```

刷新后撤销入口**仍会在**（库里那条还是未撤销）—— 这正是想要的：再点一次就能补齐标记。

## 4. 四种情形的界面口径（改前 / 改后）

| 情形 | 改前 | 改后 |
|---|---|---|
| 没有可撤销的记录 | 404「没有可撤销的记录」 | 404，**不变**（本来就对） |
| 撤销成功 | 200 + 恢复条数 | 200，**不变** |
| 课表已退、标记写失败 | 404「没有可撤销的记录」 | **500** + 横幅「撤销只做了一半…请再点一次」+ 状态重拉 |
| 课表已退、标记写失败，前端只看 detail | 通用「撤销失败」 | 两次失败原因（首次 / 重试）照样透到面板 |

## 7. 仪器：第五次事故 —— `restore` 把本轮改动一起回滚了

`_r61_mut.py` 第一版这样写备份：

```python
BAK = {APP_API: r"_r61_pre_reschedule.py", ...}   # ← "pre" = 本轮改之前
```

跑完 V1 需要恢复源码，`restore` 就把它写回了 **pre** 备份。于是：

- `reschedule.py` md5 从 `b8d4f8621b3b` 退回 `49136b6f693b`；
- `plan_landing.py` 的 `error_kind` 命中数 0；
- 前端 `LandPlanPanel.tsx` 里「只做了一半」也是 0。

V2 一跑就撞出 `hits=0 ABORT: anchor not unique` —— 不是锚点写错，是**改动没了**。
发现用时约 2 分钟，代价是重做三处 Edit。

修法：备份指到 `_r61_src_*`（**本轮改完后的工作区版本**），并在脚本头部把这个坑写成注释。

这条和 R60 那两次是同一族：**判据必须是文件本身（md5 / 目标字节串 / 命中数），
不能是脚本自己说"我改好了"**。`restore` 的语义尤其要写清 —— 是"回到工作区状态"，
不是"回到改动前"。

## 8. 没做

- `/parallel/land/undo` **仍无 `message`**：成功路径前端自拼的两个数字（恢复条数、
  回滚调课数）取自响应字段，是准的，不失真。R60 给 `/land` 加 message 是因为那里
  前端拼的数字在 `has_changes=false` 时是**假的**；这里没有同类问题。
- **没有把 `error_kind` 做成枚举类/常量表**：目前只有两个取值，两处字符串字面量
  都能被用例覆盖；抽常量会让这轮 diff 变大而不增信息。
- **没有动 `undo` 的顺序**（先 restore、后 revoke）：那是 R59 用
  `test_restore_failure_leaves_record_unrevoked` 钉住的，本轮只改失败后的**报法**。
- **没有验证真实 sqlite 锁**：用例是 monkeypatch `revoke` 抛 `RuntimeError`，
  不是真的把库锁住。真锁的行为（`database is locked` 的字符串、重试能否自愈）
  在 CI 上不可控，故不测；本轮的断言只针对"失败之后怎么报"。

## 9. 三句话

1. 一个动作有两种结局，就必须有两个状态码；共用 404 的代价不是文案难看，是**动作走反**。
2. 错误路径也要保住结构 —— `HTTPException` 只带一个字符串，而"课表已经退了"是个事实，
   不该随异常一起蒸发。
3. `restore` 写错方向，比不恢复更危险：它会把刚做完的活儿安静地抹掉，还留一份
   "已恢复"的日志。
