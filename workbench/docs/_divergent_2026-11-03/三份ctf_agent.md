## 三、但 C 有一处比 A/B 更好

`_docker_keepalive.py`：A/B 131 行，C 139 行。剥掉注释后代码完全一致，
**C 的注释更完整**：

```python
# A/B 的注释（3 行）
# ⚠️ 不能叫 `_stop`：threading.Thread 把 `_stop` 定义成**方法**
# （join() → _wait_for_tstate_lock() → self._stop()），属性覆盖它
# 会让 join() 抛 `TypeError: 'Event' object is not callable`。

# C 的注释（11 行，多了三条关键信息）
# start/run/stop 全都正常，只有 join() 会炸 —— 所以这个 bug 能活很久。
# 同类私有名：`_started`、`_tstate_lock`。
```

C 多出来的那句「**所以这个 bug 能活很久**」是这个缺陷最本质的解释；
「同类私有名：`_started`、`_tstate_lock`」则是给后来人的搜索线索。

**我 R59 写的注释不如它。** 所以我把 C 的版本反向同步到了 A 和 B。

这印证了 R109 的结论：**同步不是覆盖，是判断。** 上次是 B 更好，这次是 C 更好。

## 四、检测器：`tools/check_multi_version.py`

### 双指纹

| 指纹 | 算法 | 回答 |
|---|---|---|
| **内容指纹** | 归一行尾后 sha256 | 字节上一样吗 |
| **代码指纹** | 剥 docstring + 剥 `#` 注释 + 去空行后 sha256 | **行为**上一样吗 |

只有双指纹才能区分「实质分叉」和「仅注释不同」。

第一版我只用了内容指纹，结果是 `_audit_truth_consistency.py` 被报"差 334 行"——
两边其实都是 167 行、逐字相同，只是 CRLF vs LF。

### 只读快照必须单列

第一版把 C 也算进"必须同步"，结果 7 个文件全是红灯。

**永久红灯的守卫会被关掉。** 所以加 `readonly` 概念：只读副本不同 → 标 📌 而非 ❌。

这个设计有个意外收获：📌 那一栏**恰好是最有用的信息**——它一眼证明
"这些修复是后来才有的"。

### 自检（5 项）

```
[PASS] T1 CRLF/LF 归一化
[PASS] T2 仅注释不同 → 代码指纹相同
[PASS] T3 变异：实质差异 → 代码指纹不同
[PASS] T4 只读快照不同 → 标 RO，不判分叉
[PASS] T5 变异：不标只读 → 判实质分叉
```

T4 与 T5 是配对的：只有 T5 的话，"一律标 RO" 能全过；只有 T4 的话，
"RO 永远不报" 也能全过。

## 五、这一轮真正学到的东西

R109 我以为问题是「**A 和 B 两个仓库**要同步」。

R110 才发现问题是「**我在同一份代码上留了几个不同版本**」——
A、B、C、死副本，四个。而我只记得其中两个。

这不是"仓库管理"问题，是**我的记忆比实际状态少**。

所以结论和 R109 一样，但更强：

> **凡是我改过的东西，都要问一句"它还有几份"。**
> 这句话不该由记忆执行，该由工具执行。

## 七、三条可复用的

1. **"副本"和"证据"在我心里是两回事，在文件系统里不是。**
   C 是我解包来做审计的，从没想过它也需要被看待。
   凡是磁盘上存在的代码，都会被搜到、被 grep 到、被误改到。

2. **只读副本要单列，但别隐藏。**
   把它算进"必须同步"→ 永久红灯；把它藏起来 → 失去历史对照的价值。
   标 📌 是两者之间唯一有用的位置。

3. **注释差异值得反向同步。**
   这次 C 的注释比 A/B 好。如果不做这个检测，我会一直以为自己写的是最优版本。
