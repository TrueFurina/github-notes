# 行数超限的文案：同一类错误，修了两遍

> 上一轮修了 413（文件太大）。这一轮发现：**20,000 行的限制犯了完全一样的错**，
> 而且更糟——它连错误类型都说错了。

---

## 一、问题

上一轮加的行数守卫，超限时抛 `SheetTooLargeError`。但 API 层的处理是：

```python
try:
    _db.load_from_excel(save_path)
    ...
except Exception as e:
    raise HTTPException(status_code=400, detail=f"文件解析失败：{e!s}")
```

`SheetTooLargeError` 继承自 `ValueError`，被这个 `except Exception` 一把兜住。

于是教秘看到：

> **文件解析失败**：安排表「大学物理实验安排表 (周)」行数 50000 超过上限 20000。
> 如确需处理更大的表，**请设置环境变量 MAX_SHEET_ROWS 后重启服务**。**（请稍后重试或刷新页面）**

### 四个错误

| # | 问题 | 为什么错 |
|---|---|---|
| 1 | 前缀"文件解析失败" | **根本没有开始解析**，是解析前的规模检查拒绝了它 |
| 2 | "设置环境变量 MAX_SHEET_ROWS" | 教秘不该也不会去改服务器的环境变量 |
| 3 | "（请稍后重试或刷新页面）" | 同一个文件重试一万次还是被拒 |
| 4 | 用户不知道该怎么办 | 真正该做的是：精简表格或拆分 |

**比 413 那个更糟**：413 至少状态码是对的（413 本身就是"太大"），这里连语义都错成了"解析失败"。

---

## 二、根因

两个问题叠在一起：

**1. 异常没有独立分支**

`SheetTooLargeError` 和真正的解析错误（坏文件、缺列）走同一条 `except`，共享"解析失败"的措辞。

**2. 异常消息里写死了运维话术**

```python
raise SheetTooLargeError(
    f"{what}行数 {n} 超过上限 {MAX_SHEET_ROWS}。"
    "如确需处理更大的表，请设置环境变量 MAX_SHEET_ROWS 后重启服务。"
)
```

异常消息本该只描述"违反了哪条约束"，不该包含"运维怎么调参数"。那段话属于部署文档，不属于用户界面。

---

## 三、修复

### 1. 异常携带结构化字段

```python
class SheetTooLargeError(ValueError):
    def __init__(self, message: str, limit: int = 0, actual: int = 0):
        super().__init__(message)
        self.limit = limit
        self.actual = actual
```

有了 `limit`，API 层就能通过响应头暴露限额，**不必从异常字符串里正则抠数字**。

### 2. 异常消息去掉运维话术

```python
# 改前
f"{what}行数 {n} 超过上限 {MAX_SHEET_ROWS}。如确需处理更大的表，请设置环境变量 MAX_SHEET_ROWS 后重启服务。"

# 改后
f"{what}行数 {n} 超过上限 {MAX_SHEET_ROWS}"
```

只保留"违反了哪条约束"。

### 3. API 层独立分支 + 可操作建议

```python
except SheetTooLargeError as e:
    # 规模超限不是"解析失败"，是主动拒绝：别用"文件解析失败"当前缀，
    # 也别把 "设置环境变量 MAX_SHEET_ROWS" 这类运维话术塞给教秘。
    raise HTTPException(
        status_code=400,
        detail=f"{e!s}。请精简表格（只保留需要的周次/班级）或拆分成多个文件后重新上传。",
        headers={"X-Max-Sheet-Rows": str(e.limit)},
    )
except Exception as e:
    raise HTTPException(status_code=400, detail=f"文件解析失败：{e!s}")
```

## 八、为什么这类问题会重复出现

上一轮修 413 时，我改的是**前端**（把 413 翻译成人话）。
这一轮修行数超限，改的是**后端**（让 detail 别带运维话术）。

**两次的错不在同一个地方，但错的性质完全一样。**

这暴露了一个模式：**新增一个限制时，最容易漏掉的不是限制本身，是"被拦下的人看到什么"。**

写限制的时候，注意力全在"怎么拦"：
- 阈值怎么定
- 在哪一层拦
- 边界怎么判

而"拦下来之后说什么"往往是顺手写的，用的是**写代码的人**的视角（怎么调参数），不是**用户**的视角（我该怎么办）。

### 一个可操作的自检

以后每加一条限制，问一句：

> **如果这条限制被触发，用户看到的那句话，他自己能照着做吗？**

- 如果答案是"需要改配置文件/环境变量"→ 用户做不到
- 如果答案是"重试"→ 同一个输入重试无效
- 如果答案是"联系管理员"→ 可以，但先想想有没有用户自己能做的

对行数超限，用户能做的是：删掉不需要的周次、只保留需要的班级、或者拆成两个文件。这才是该说的话。
