## 三、四个发现

### R6 · F6 审批闭环零业务覆盖

`reschedule.py` 覆盖率 86%，缺失集中在 F6。现有 `test_api_auth.py` 只验证**鉴权**（401），业务分支全没测。

最关键的是这段整段未执行：

```python
if _db.loaded:
    apply_result = _apply_reschedule(record_dict)
```

**这是"点同意之后排课数据真的变了"的关键。** 写错了教秘不会发现，沙盘也不会报错。

补 11 个测试，覆盖同意/驳回/重复审批/404/自动应用的三种结果。`reschedule.py` 覆盖率 **86% → 90%**。

### R7 · 边界行为确认（0 缺陷）

35 个边界用例逐条对照 `time_model.py` 注释里的承诺，**全部成立**。

中途出现一次"疑似缺陷"：`span_labels("567")` 返回 `[]`，我以为有 bug。查调用方才明白是**两路分支**设计——`span_labels` 只管时间区间，节次码走查表。**API 语义要看调用方，不能只看函数名。**

### R8 · MasterDataView 5 个 catch 用反模式

```tsx
setError(err?.response?.data?.detail || '加载主数据失败');
```

四种错误实测：

| 错误 | 用户看到 |
|---|---|
| 500 | 加载主数据失败 |
| 网络断开 | 加载主数据失败 |
| 60s 超时 | 加载主数据失败 |
| 503 | 加载主数据失败 |

**错误原因完全丢失**，教秘不知道该重试、该查网络、还是该找管理员。

改为 `describeApiError`，并加静态守卫防止回退。

### R9 · README 三处偏差

| `python-constraint` | `ortools` CP-SAT |

## 四、D2 的两次设计教训

### 教训 1：静态守卫规则不能一刀切（R8）

守卫第一版："禁止任何 `err?.response?.data?.detail`"。

结果连 `App.tsx` 的 401 分支也报了——但那处**是合理的**：后端 401 的 detail 是「用户名或密码错误，请重新输入；多次失败请稍后再试或联系系统管理员」，已含完整指引，直取它比前端兜底更准。

修正为：只禁止 `detail || 固定文案` 的**塌缩**写法，且对 `status === 401` 上下文豁免。第二版精确命中 `MasterDataView.tsx:60`。

**一刀切的规则会逼人加无谓的 `eslint-disable`。**

### 教训 2：守卫应该发现方向性错误，不是精确到个位（R9）

守卫第一版用**严格相等**。写完就翻车：新增 4 个守卫本身让用例数 478→482，README 又过时了。

**严格相等会让人"为了过闸而改数字"，而不是审视声明本身。**

改为下限 + 10% 容差。副作用：不再每次全量 collect，耗时 **120s → 4.5s**。
