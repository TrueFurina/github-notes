# 产品化与分发诊断（本轮新增）

> 前几轮聚焦「代码质量」与「安全」。继续下钻后发现一个更根本的问题：
> **你已经做完了产品化最难的部分，却把分发做断了。**
>
> 数据日期：2026-10-28 · 数据源：Releases API + Traffic API + 仓库内容比对

---

## 一、最重要的发现：SecAutoMind 是唯一真正"产品化"的项目

### 1.1 它的实际形态

`SecAutoMind` 只有 **3 个文件**（LICENSE / index.html / robots.txt），151 KB。但 `index.html` 是一个完整的**产品落地页**：

- 23,030 字符，自带深色主题、CSS 变量、响应式布局
- 页面标题：**"SecAutoMind · 自主决策通用网络安全智能体"**
- 直接分发 **4 个平台**的二进制：

```
SecAutoMind-Setup-1.7.28-x64.exe      ← Windows 安装包
secautomind-ai.exe                     ← Windows 便携版
secautomind-ai-linux-amd64             ← Linux
secautomind-ai-macos-arm64             ← macOS ARM
secautomind-ai-macos-amd64             ← macOS Intel
```

**这是一个真实的、可分发的桌面安全产品**，不是 demo，不是 notebook，不是"参赛作品"。

### 1.2 它是全账号流量最高的仓库

Traffic API 实测（14 天）：

| 仓库 | 浏览 | 独立访客 | 占全账号 |
|---|---:|---:|---:|
| **`SecAutoMind`** | **78** | **23** | **46%** |
| `TrueFurina` (profile) | 31 | 30 | 18% |
| `passive-recon` | 22 | 11 | 13% |
| 其余 19 个仓库合计 | 37 | — | 23% |

而且流量集中在正确的页面：

```
/releases/tag/v1.7.28    → 13 次浏览 / 7 独立访客
/releases                 →  9 次浏览 / 6 独立访客
/                         → 33 次浏览 / 13 独立访客
```

**访客是冲着下载来的，不是来读 README 的。**

### 1.3 但落地页没有链接到源码

`index.html` 的所有出站链接：

```
https://github.com/TrueFurina/SecAutoMind            ← 落地页自身
https://github.com/TrueFurina/SecAutoMind/issues
https://github.com/TrueFurina/SecAutoMind/releases
  └─ 4 个 release 二进制下载链接
```

**关键缺陷**：页面中 `SecAutoMind-src` 出现次数 = **0**。

也就是说：23 个独立访客下载了二进制，**没有一个被引导到那个有 3,532 个文件、1,072 个 Python 文件的源码仓库**。

而 `SecAutoMind-src` 的星数是 **0**。

### 1.4 结论

你已经在做「产品」了——有落地页、有多平台二进制、有版本号、有安装包。这在 GitHub 上的独立开发者里属于少数。

问题只有一个：**产品和源码是两个互不相连的仓库，流量全部止于下载页。**

## 二、Release 管道被复制成了两份

### 2.1 实测数据

两个仓库各自维护一套 Release，**版本号几乎完全镜像**：

| 版本 | `SecAutoMind` 下载 | `SecAutoMind-src` 下载 |
|---|---:|---:|
| v1.7.28 | **35** | **4** |
| v1.7.27 | — | 0 |
| v1.7.26 | — | 0 |
| v1.7.25 | 6 | 5 |
| v1.7.24 | 1 | 11 |
| v1.7.23 | 2 | 11 |
| v1.7.22 | 3 | 8 |
| v1.7.21 | 4 | 5 |
| v1.7.20 | 0 | — |
| v1.7.19 | 1 | — |
| v1.7.18 | 6 | — |
| v1.7.17 | 6 | — |
| **合计** | **64** | **44** |

同一批二进制文件被上传到两个仓库、两套 tag、两个 release 页面。

### 2.2 三个直接后果

**1. 下载量统计失真**
真实下载是 64 + 44 = **108 次**，但在任何一个仓库页面看到的都只有一半。你自己也无法判断真实用户规模。

**2. 用户会下到旧版本**
`SecAutoMind-src` 的 `v1.7.28` 发布于 **2026-09-30**，而 `SecAutoMind` 的同名版本发布于 **2026-10-10**。同一个版本号，发布时间差 10 天，内容可能不同。访问 `-src` 的用户拿到的是过期构建。

**3. 搜索权重被稀释**
两个仓库描述几乎相同、homepage 指向同一个 URL（`app-a7lm1eejtypt.appmiaoda.com`），GitHub 搜索和 Google 索引会互相竞争。

### 2.3 全账号 Release 全景（这是真实影响力的硬指标）

| 仓库 | Release 数 | 总下载 |
|---|---:|---:|
| `SecAutoMind` | 10 | **64** |
| `SecAutoMind-src` | 9 | 44 |
| `marl-ecdsa` | 2 | **32** |
| `comment-distillery` | 5 | **19** |
| `passive-recon` | 1 | **0** |
| **全账号合计** | **27** | **159** |

**159 次下载 vs 92 个 Star，比值 1.7×。**

这个比值说明一件事：**有人在真的用你的东西，但极少数人愿意给 Star**。

正常开源项目的下载/Star 比通常在 3–10×（星数是下载的 1/3 到 1/10）。你的 1.7× 偏低，意味着用户下载后**没有产生"值得点赞"的认同感**——通常是缺 README 里的价值主张、缺截图、或者不知道怎么反馈。

另外注意 `marl-ecdsa`：32 次下载（27 次是 Windows exe），2 个 release，但只有 1 个 star。这个项目的 CCF 投稿版本有真实下载，同样没有被转化成社区认同。

## 三、六个项目族谱：同一项目被拆成多个仓库

按仓库名前缀聚合，识别出 6 组「同一项目的多个仓库」：

| 族谱 | 仓库数 | 明细 |
|---|---:|---|
| `SecAutoMind` | 2 | `SecAutoMind`(151KB, 落地页) + `SecAutoMind-src`(90MB, 源码) |
| `MangDe*` | 3 | `MangDeHenZhi`(8.8MB) + `MangDeHenZhi-materials`(8.1MB, private) + `MangDeZhiXun`(7.0MB) |
| `xihu*` | 2 | `xihu-sword-ctf-agent`(6.3MB) + `xihu-ctf-deliverables`(1.1MB, private) |
| `marl-ecdsa*` | 2 | `marl-ecdsa`(4.0MB) + `marl-ecdsa-competition-materials`(0.3MB, private) |
| `2026-Challenge*` | 2 | 两个不同赛事，命名却同前缀 |
| `sage-paper*` | 2 | `sage-paper`(2.85MB, 185 文件) + `sage-paper-public`(0.52MB, 24 文件) |

### 3.1 分裂模式有两种

**模式 A：源码/交付物分离（`-src` / `-materials` / `-deliverables` 后缀）**

这一模式**本身是对的**，符合"源码仓库只放源码"的原则。问题在于**没有互链**：

- `SecAutoMind` 落地页 → 无链接到 `-src`
- `SecAutoMind-src` README → 需确认是否回链落地页
- `xihu-sword-ctf-agent` → 无链接到 `-deliverables`（后者是 private，链接会 404，但也该在 README 说明）

**模式 B：真的重复（`sage-paper` vs `sage-paper-public`）**

这两个是**同一份论文的不同版本**：

| 仓库 | 文件数 | 体积 | 特征 |
|---|---:|---:|---|
| `sage-paper` | 185 | 2.85 MB | 含 `.workbuddy/memory/` 会话记忆目录 |
| `sage-paper-public` | 24 | 0.52 MB | 只有论文正文 `01_theoretical_framework_en.md` 等 |

`sage-paper` 里混进了 `.workbuddy/memory/2026-09-21.md` 这类**AI 会话记忆文件**——这是过程物，不应进公开仓库。

**建议**：`sage-paper` 转 private（保留工作区），`sage-paper-public` 作为唯一公开出口。

### 3.2 `MangDe*` 三兄弟的危险关系

```
MangDeHenZhi            8.8MB  public   芒得职训（另一条产品线）
MangDeHenZhi-materials  8.1MB  private  交付材料
MangDeZhiXun            7.0MB  public   ← 微信支付凭据泄露在这里
```

`MangDeZhiXun` 的描述是"芒得职训·AI产教实训工坊 - 秒搭平台源码"。它与 `MangDeHenZhi` 是**同一产品线的不同项目**，但命名只差两个字（`MangDeZhiXun` vs `MangDeHenZhi`），极易混淆。

**这也是安全事件容易被漏掉的原因**：你可能有 3 个相关仓库，但只记得其中 1–2 个，泄露的那个恰好是被遗忘的。

**建议**：统一命名前缀，如 `mangde-henzhi` / `mangde-zhixun` / `mangde-materials`，全部小写加连字符。

## 四、这轮修正了之前的判断

前几轮我说"投入量与影响力脱钩，`MARS-408` 白做了"。这轮数据要求更精确的表述：

| 项目 | 投入 | 真实下载 | Star | 判断 |
|---|---:|---:|---:|---|
| `MARS-408` | 2,058 文件 / 111MB | 无 Release | 6 | **确实没有产出** |
| `SecAutoMind` | 3 文件（落地页） | **64** | 1 | **有用户，但没沉淀** |
| `SecAutoMind-src` | 3,532 文件 / 67MB | 44 | **0** | **有代码，但没曝光** |
| `marl-ecdsa` | 4MB | **32** | 1 | 有用户，没沉淀 |
| `comment-distillery` | 1.8MB | **19** | 1 | 有用户，没沉淀 |
| `passive-recon` | 202 文件 | 0 | 7 | 有星，没用户 |

**新的判断**：你不是"没做出东西"，而是**做出的东西没有形成闭环**。

- `SecAutoMind` 有产品、有用户、有下载 → 但源码仓库 0 星
- `passive-recon` 有代码、有星 → 但没有 Release 下载（v0.1.0 下载数为 0）
- `MARS-408` 有代码量 → 但没有分发形态

三个项目各缺一环，没有一个是完整的。

## 五、具体动作（按投入产出排序）

### 动作 1 · 打通 SecAutoMind 的双仓链路（最高优先，1 小时）

改 `index.html`，在下载按钮旁加一行：

```html
<a href="https://github.com/TrueFurina/SecAutoMind-src"
   class="btn-ghost" target="_blank" rel="noopener">
  View Source on GitHub →
</a>
```

在页面底部加：

```html
<p class="foot-note">
  SecAutoMind 是开源项目 ·
  <a href="https://github.com/TrueFurina/SecAutoMind-src">源码</a> ·
  <a href="https://github.com/TrueFurina/SecAutoMind-src/blob/main/LICENSE">MIT License</a>
</p>
```

**为什么值得做**：23 个独立访客已经证明有人对产品感兴趣。把其中一部分导向源码仓，是这个账号里转化路径最短的一步。

同时改 `SecAutoMind-src` 的 README 顶部，加一句：

```markdown
> 📦 **下载安装包**：[v1.7.28 Release](https://github.com/TrueFurina/SecAutoMind/releases/latest)
> 🌐 **产品主页**：https://app-a7lm1eejtypt.appmiaoda.com
```

### 动作 2 · 合并 Release 管道（2 小时）

**只保留 `SecAutoMind` 作为发布出口**（它是访客入口，有流量）。`SecAutoMind-src` 的 Release 全部删除，改为在 README 指向落地页。

理由：
- 下载量统计归一到一处，才能判断真实用户规模
- 避免同名版本发布时间不一致导致用户下到旧构建
- 减少维护成本（每次发版要传两遍）

操作：`SecAutoMind-src` → Releases → 逐个 Delete。历史 tag 保留（不影响代码）。

### 动作 3 · 把 108 次下载转成 Star（持续）

当前 1.7× 的下载/Star 比偏低。三个改法：

1. **落地页加 Star 按钮**（页面上已有 `star` 关键词，需确认是否是有效引导）
2. **安装包里放 `README.txt`**，第一行写"如果这个工具对你有用，给个 Star：<链接>"
3. **`SecAutoMind-src` 的 README 顶部加 badgestrip**：Star / Release / Downloads / License

### 动作 4 · 统一仓库命名（1 小时）

```
MangDeHenZhi          → mangde-henzhi
MangDeHenZhi-materials → mangde-materials
MangDeZhiXun          → mangde-zhixun      ← 安全事件就在这个，改名时顺手处理
sage-paper            → 转 private
sage-paper-public     → 保留（唯一公开出口）
```

小写 + 连字符是 GitHub 社区惯例，也避免 `MangDeZhiXun` / `MangDeHenZhi` 这种肉眼难分的命名事故。

### 动作 5 · `passive-recon` 补 Release 说明（30 分钟）

它有 `v0.1.0`，但下载数 0。原因很可能是 Release 里只有源码 zip（GitHub 自动生成），没有说明。

**改法**：写 Release notes，包含：
- 一句话说明这是什么
- 安装命令（`pip install -e .` 或 `docker compose up`）
- 截图

**零下载不等于没人感兴趣，等于没人知道下载后干什么。**

## 六、一句话总结

> **你缺的不是产品，是产品与社区之间的那段链路。**

`SecAutoMind` 是全账号唯一有真实用户的产品（108 次下载、23 个独立访客），但它的落地页不链接源码，源码仓库 0 星，Release 还分裂在两个仓库里统计。

**先修这一段链路（约 3 小时），比再写一个新项目有价值得多。**
