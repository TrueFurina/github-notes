## 一、风险定级修正：从 P0 升为 P0-紧急

### 1.1 `MangDeZhiXun` 实际暴露了三类凭据

GitHub Secret Scanning 在该仓库标记 **2 条开放告警**（`state=open`，从未处理）：

| 告警类型 | 文件 | 首次发现 | 状态 |
|---|---|---|---|
| Tencent WeChat Pay Token | `WECHAT_PAY_CONFIG.md` | 2026-09-12 | **open** |
| Tencent WeChat API App ID | `WECHAT_PAY_CONFIG.md` | 2026-09-12 | **open** |

而 `WECHAT_PAY_CONFIG.md` 是**公开可读**的，共 198 行，其中 5 条 `supabase secrets set` 命令携带真实值：

| 键名 | 值长度 | 判断 |
|---|---:|---|
| `WECHAT_APPID` | 18 | 真实 AppID 格式 |
| `WECHAT_MCHID` | 10 | 真实商户号格式（微信商户号为 10 位） |
| `WECHAT_API_V3_KEY` | **32** | **微信支付 APIv3 密钥标准长度，精确匹配** |
| `WECHAT_SERIAL_NO` | 40 | 商户 API 证书序列号格式 |
| `WECHAT_PRIVATE_KEY` | 11 | 看似占位符（可能指向外部文件） |

加上此前发现的 `.env`（Supabase URL + anon JWT + App ID），该仓库总计 **3 类凭据 / 5 个变量** 处于公开状态。

### 1.2 为什么这次比 Supabase 严重

Supabase `anon` key 设计上可公开，风险取决于 RLS 配置。但 **微信支付 APIv3 密钥是服务端密钥**：

`APPID` + `MCHID` + `API_V3_KEY` + `SERIAL_NO` 这四项组合，是调用微信支付 APIv3 的完整凭据集，可用于：

- 查询订单、退款、下载对账单
- 发起退款（若证书私钥同时泄露）
- 验证并伪造回调签名

**关键点**：微信支付 APIv3 的请求签名需要商户私钥，回调查验需要 APIv3 密钥。如果 `WECHAT_PRIVATE_KEY` 只是占位符（11 字符确实不像真私钥），那么**签名能力受限，但回调解密与验签能力仍然具备**——攻击者可以伪造支付成功回调，让你的业务系统误判为已付款。

对一个"AI 产教实训工坊秒搭平台"来说，这是可直接造成资金损失的路径。

### 1.3 处置顺序（必须严格按此顺序）

**第一步：微信支付商户平台撤销与重置**

1. 登录 [微信支付商户平台](https://pay.weixin.qq.com) → 账户中心 → API 安全
2. **重置 APIv3 密钥**（新密钥 32 位，立即生效，旧密钥失效）
3. **作废当前 API 证书**，重新申请（这会同时更换 `SERIAL_NO` 与私钥）
4. 核对近 30 天交易流水与退款记录，确认无异常订单

> ⚠️ 顺序很重要：**先撤销、后清理代码**。若先清理 git 历史再重置密钥，中间窗口期旧密钥仍有效。

**第二步：Supabase 侧**

1. Dashboard → Project Settings → API → Roll anon key
2. 检查 RLS 策略：`supabase/secrets/required.json` 显示还需要 `DEEPSEEK_API_KEY`，确认该 key 是否也在别处硬编码
3. 检查 `supabase/functions/` 下 4 个 Edge Function 是否在代码中硬编码了密钥
   （`_shared/wechat-pay.ts`、`wechat_payment_webhook/index.ts`、`wechat_refund_webhook/index.ts`）

**第三步：仓库清理**

```bash
# 1. 补 .gitignore
cat >> .gitignore <<'EOF'
.env
.env.*
!.env.example
*.pem
*.p12
WECHAT_PAY_CONFIG.md
EOF

# 2. 从索引移除但保留本地
git rm --cached .env WECHAT_PAY_CONFIG.md

# 3. 提交
git commit -m "security: remove exposed credentials and add gitignore rules"
git push
```

**第四步：处理 Secret Scanning 告警**

在 GitHub 仓库 → Security → Secret scanning → 对 2 条告警点击 **"Revoked"**（前提是已完成第一步重置）。标记为 Revoked 后 GitHub 会记录处置闭环。

**第五步（可选）：重写历史**

密钥已轮换后，历史中的旧值已失效，重写历史不再是必需。若仍要清理：

```bash
pip install git-filter-repo
git filter-repo --path .env --path WECHAT_PAY_CONFIG.md --invert-paths
```

代价：所有 fork/clone 失效，需重新推送。**建议跳过此步**，因为密钥已失效，收益不抵成本。

14 天（2026-10-14 至 10-27）实测流量：

| 仓库 | 浏览 | 独立访客 | 克隆 | 独立克隆 |
|---|---:|---:|---:|---:|
| SecAutoMind | 78 | 23 | 14 | 14 |
| TrueFurina (profile) | 31 | 30 | 65 | 36 |
| passive-recon | 22 | 11 | 20 | 19 |
| AGI-Distiller | 6 | 2 | 35 | 23 |

**总计：168 次浏览 vs 8,713 次克隆。**

### 4.1 克隆数远大于浏览数 = 自动化流量

正常人类行为是"先看再克隆"。`MARS-408` 4 次浏览配 6,577 次克隆，`MangDeHenZhi` 0 次浏览配 1,324 次克隆——这不可能来自真人。

可能来源：
- 你在 CI / 定时任务里反复 clone（`SecAutoMind-src` 有 3.5k commits，可能是自动化提交）
- 爬虫扫描（GitHub 上大量爬虫会 clone 公开仓库）
- 你自己的开发环境反复拉取

**关键结论**：这些克隆数**不构成任何影响力证据**，不应计入自我评估。

### 4.2 真实流量极低

`passive-recon` 是你工程质量最好的项目，14 天只有 **11 个独立访客**。

`MARS-408` 有 6,577 次克隆，但只有 **4 个独立访客**——说明它被自动化碰过，但**没有一个真人想打开看**。

### 4.3 `SecAutoMind` 的 Release 页面是唯一亮点

路径数据显示，`SecAutoMind`（非 `-src`）的流量集中在：

```
/TrueFurina/SecAutoMind/releases/tag/v1.7.28     → 13 次浏览 / 7 独立
/TrueFurina/SecAutoMind/releases                  → 9 次浏览 / 6 独立
```

**这说明 Release 页面确实在带来真实访问**。`SecAutoMind` 已发到 `v1.7.28` 版本，这个版本号策略是对的——频发版能让项目反复出现在关注者的时间线。

**可复用的做法**：`AGI-Distiller`、`MARS-408`、`passive-recon` 都应该建立版本节奏（哪怕是 `v0.1.x` 小步走）。

## 五、修正后的整体结论

前一版说"问题不在能力，在分发"。加上流量数据后，这个判断需要更精确：

> **问题不在能力，也不完全在分发——在于"没有可被传播的入口"。**

证据链：

1. 代码质量够（`passive-recon` 五项全绿，219 个测试的 CTF agent）
2. 但 14 天只有 11 个独立访客看到它
3. 有流量的地方是 Release 页面（SecAutoMind v1.7.28），不是 README
4. 唯一高流量仓库（MARS-408 6577 克隆）是自动化，零真人浏览

**所以优先级要调整**：

| 原计划 | 修正后 | 理由 |
|---|---|---|
| 先做 fork 清理 | **先做安全处置** | 微信支付凭据是真实资金风险 |
| 先改 README | **先发 Release** | 数据显示 Release 页有真实流量 |
| 主推 AGI-Distiller | **主推 passive-recon** | 工程质量最好，只缺曝光 |
| 关注 Star 数 | **关注 Release 下载 + 独立访客** | Star 可刷，访客不可刷 |

**最反直觉的一条**：`MARS-408` 花最多精力（2,058 文件、111MB、225 测试），14 天只有 4 个真人访问。而 `AGI-Distiller`（258 文件、26 py）有 9 Star。**投入量和影响力完全脱钩**。

原因很可能是：MARS-408 是"给评委看的参赛作品"，AGI-Distiller 是"给同行用的工具"。前者完成后就没人再看，后者会被人反复访问。

**这条如果只记住一句话**：优先做**别人会重复使用的东西**，而不是**能证明自己努力的东西**。
