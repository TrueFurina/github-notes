| 实验 | 条件 | 结果 |

```

```

**为什么**：`app/engine/auto_scheduler.py:362` 的 `solver.Solve(model)` **没有设 `max_time_in_seconds`，
也没有设 `num_search_workers`** ⇒ CP-SAT 默认多线程并行，同等最优解之间哪一份被返回是不确定的。

换一份同样合法、同样最优的方案，冲突就不出现，测试自然绿。

⇒ 这不是「防护缺失」，是**检测器在赌概率**。三条推论：

1. `56/56` **从来不是稳定事实**。R44/R46/R47/R51/R57 那几次「56/56」是运气好；本轮就是 55/56。
2. 台账里那条「怀疑 cache 跨次残留」是**错的**，应改用本节的归因。
3. 修法有两条，都不在本轮范围内（本轮只写文档）：
   - 把检测点从「事后碰撞」改成「机制本身」（断言 `class_busy` 真被传进分片求解参数），

### 4.2 两类问题的分布说明什么

D1 的四个缺陷，**三个是"判据不一致"**（同一概念两套实现：`==` vs 子串、内存 vs sqlite、生产对但测试抓不住）。
D2 的四个缺陷，**四个都是"说全/说清"缺失**（字段齐但漏维度、数字对但不说代价、返回体缺 `message`、异常被渲染成成功）。

⇒ **这个项目的问题已经从"写错"迁移到"说漏"。** 早期的坑是算法算错（能靠对拍发现），
现在剩下的坑几乎全部是：**行为正确、返回值合法、文案通顺，但少了一句该说的话。**
这类缺陷没有一条能被「跑一遍看是否报错」抓到 —— 只能靠**换一个人按真实工作流读一遍输出**。

R50 那一整轮的价值就在这里：它是八步里唯一「以用户视角读输出」的格，
结果八步里四步的输出都缺东西。

## 12. 后续：R61 把「`undo` 失败映射 404」关掉了（2026-11-02 05:14，commit `c5cfb84899`）

§8 遗留清单第 6 条「`undo` 失败映射 404→500」—— 它从 **R45**（`d83845b3`，修快照/恢复那一轮）
起就挂在表里，理由写的是"改状态码会影响调用方，需决策"。一直没动，是因为它看着只是"状态码不够精确"。
R61 实测发现不是：

`plan_landing.undo()` 有两条失败返回，**内存里的事实完全不同**：

| 分支 | 课表 | sqlite 记录 | 该报 |
|---|---|---|---|
| `no_record` | 没动 | 没有 | 404 |
| `revoke_failed` | **已退回落地前** | 仍为「已落地」 | 500 |

端点此前一律 `raise HTTPException(404, out["error"])`，代价三连：

1. 界面写「没有可撤销的记录」，而安排表**已经退了**；
2. `rolled_back` / `restored_entries` 这些已发生事实随异常蒸发，前端无从判断"该不该重试撤销"（该）；
3. 教秘以为撤销没生效 → 去"重新落地" → 把刚退掉的方案又落回去。

改法：`undo()` 两条失败各带 `error_kind`；`land_undo` 按 kind 分 404 / 500，500 用
`JSONResponse(500, {**out, "detail": ...})` 保住结构（不用 `HTTPException(500, ...)`，
那样结构又只剩字符串）；前端 `doUndo` 见 `rolled_back === true` 就清 diff、**重拉状态**、
横幅说「撤销只做了一半……请再点一次」—— 刷新后撤销入口仍在（库里那条还是未撤销），
再点一次正好补齐标记。

**"会影响调用方"这个顾虑是怎么落地的**（§8 那条遗留的理由）：
`no_record` 仍返回 **404**，原来"没有可撤销的记录"的语义和状态码一个字没变；
只有"服务端自己没写完"那一型从 404 改成 500 —— 那一型本来就不该是 404。
前端同批改；500 的响应体额外补 `detail` 字符串，所以不认结构的调用方（`describeApiError`）
照样拿得到人话。没有出现"改了状态码、调用方集体失灵"的情况。

实测：pytest **758/32/0**、前端 **21 文件 / 156 全绿**、变异 **56/56**、ruff 全仓 0（含 unsafe 0）；
4 个定向变异全检出（V1 一律 404、V2 丢结构、V3 不标 `no_record`、V4 前端删分支），
每条都是"只新用例红、其余全绿"。

## 15. 后续：R74 用真锁把"撤销重试"测了一遍 —— 补出 11 秒（2026-11-02 21:50）

§14 结尾挂的那条遗留：「真实 sqlite 锁下撤销重试仍只有 monkeypatch 版」。本以为是补个覆盖，
测完发现三件事都被这句"补个用例"挡住了。

**取证**（`R74-new/probe_lock.py`，另一条连接 `BEGIN IMMEDIATE` 持锁，生产连接 5 s）：

```
正常撤销            0.008 s
持锁期间 latest()   0.001 s   ← 只读不受 RESERVED 影响，undo 才会走到 revoke
单次 revoke         5.50 s   ← sqlite3.OperationalError: database is locked
一次完整 undo      11.04 s    success=False、rolled_back=True、error 里该原话出现 2 次
释放锁后再撤        0.017 s   success=True
```

**发现①：那句"重试一次通常就能自愈"基本是错的。**
sqlite 自带 `busy_timeout=5s`：锁在 5 秒内消失，根本进不了 except；能进 except 的锁，
意味着它已经撑过 5 秒。两次尝试之间没有任何间隔（背靠背立刻重打），锁不可能在几微秒里消失 ——
重试的实际效果只是把 5.5 s 的等待变成 **11 s**。**自愈的是 busy handler，不是那个 `try` 第二次。**

**发现②：一次被锁的撤销会按住整个事件循环 11.08 s。**

| 组 | undo 耗时 | 50 ms 心跳最大滞后 |
|---|---|---|
| 不持锁 / 同步 | 0.01 s | 13 ms |
| **真锁 / 同步（当前生产形状）** | 11.08 s | **11076 ms** |
| 真锁 / `to_thread` | 11.08 s | 14 ms（184 拍） |

`land_undo` 是 `async def`，`with _land_lock:`（`threading.Lock`）里同步调 `undo` ——
这 11 秒里并发请求、健康检查、SSE 心跳全部排队。

**发现③：抓事件循环阻塞的那道 CI 门，看不见这一型。**
`audit_async_blocking.HEAVY` 刻意不收 `sqlite execute`，理由写得很清楚："单条 insert <1 ms"。
这个前提在**锁竞争**下不成立：同一条 UPDATE，没人持锁 0.4 ms，被锁 5.5 s。

## 16. 后续：R75 把「11 秒按住整站」关掉了 —— 顺手改法会死锁（2026-11-02 22:20）

§15 结尾建议的下一步：把 `land_undo` 里那段 `with _land_lock: undo(...)` 丢进线程池。
做完了，但真正值得记的不是"改成线程池"，而是**改错的那个版本会死锁**。

**A/B 取证**（`R75-new/probe_endpoint_loop.py`，两组的业务代码逐行相同，只改跑在哪条线程）：

| 组 | 形状 | undo 耗时 | 心跳最大滞后 |
|---|---|---|---|
| A | `async def` 里同步 `with _land_lock:`（改前） | 0.469 s | **459.0 ms** |
| B | `await run_in_threadpool(_locked_land_undo, ...)` | 0.484 s | **6.0 ms** |
| B′ | 同上，busy_timeout 生产值 5 s | **11.047 s** | **22.0 ms**（714 拍） |

**耗时一点没变**。该等的 sqlite 还是等 11 秒，变的是这 11 秒里别人还能不能动。

**为什么"把 undo 包进线程池"是错的。** 锁竞争有**两个**面：

```python
# ✗ 只治了「锁内的活」，等锁仍在事件循环线程上
with _land_lock:
    out = await run_in_threadpool(plan_landing.undo, _db, _landings())

# ✓ 锁与活一起进工作线程
out = await run_in_threadpool(_locked_land_undo, actor)   # 里面才是 with _land_lock:
```

`_land_lock` 同时是 `_db.entries` 的写锁（`_DB_WRITE_LOCK`，R28）。一次慢落地持锁 11 秒期间，
所有落地/撤销入口都要在事件循环上原地排队 —— 第一种写法对这一半完全无效。

**变异体 V4 就是第一种写法，结果不是变慢，是死锁：**

```text
== V4: 顺手改法：锁留在事件循环、只把 undo 丢线程池 ==
  ⚠️ 整文件 90 s 未跑完 —— 用例挂死
    🔴 test_land_undo_waiting_on_write_lock_does_not_stall_heartbeat（红）
    🔴 test_two_concurrent_undos_still_serialize（挂死）
```

两个撤销并发：第一个在事件循环线程拿到锁、`await` 出去；第二个在**同一条线程**上等这把锁
⇒ 循环停死 ⇒ 第一个永远回不来。**"看起来更安全"的改法把停摆升级成死锁。**

**改了什么**：`backend/app/api/reschedule.py` 新增两个同步主体
`_locked_land_commit` / `_locked_land_undo`，`with _land_lock:` 连同 `diff → snapshot →
apply → save`（失败 `restore` 再抛）整段搬进工作线程；两个端点改
`await run_in_threadpool(...)`。R73 的 `undo_receipt` 要在**锁内**读 `latest()` ——
整段一起搬，顺带保住了；404/500 分型一字未动，`test_land_rollback.py` 现在自动走
"`HTTPException` 跨线程抛"这条路（anyio 同进程传对象引用，不 pickle）。

**测试 +5**（全部追加在 `test_event_loop_blocking.py`，不新增文件）：撤销线程、落地线程、
锁内等待心跳（真锁 0.15 s）、**等锁心跳**（另一线程持锁 0.35 s）、并发峰值 = 1。
两条心跳用例都写成两半一起断言 ——

```python
assert dur >= 0.3      # 它确实等了（否则"没卡"是假的）
assert lag_ms < 150    # 但它等着的时候事件循环还在转
```

只断言"滞后小"：用例提前返回也能过；只断言"等了"：旧形状也等了，那正是病。

一条判据值得抄：**"把阻塞活丢线程池"这句口诀漏了锁 —— 凡是"先拿锁再干活"的路径，
要把"拿锁"也算进阻塞活里。**

实测：pytest **787/32/0**（819 tests，175.04 s）、测试文件 81、前端 21/157（未动）、
变异 **56/56**、定向变异 4/4（V1 3 red；V2 2 red；V3 1 red；V4 1 red + 1 挂死）、
ruff 两版 0、审计门 exit 0。
