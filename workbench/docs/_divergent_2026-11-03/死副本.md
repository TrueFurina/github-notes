# 死副本：一份看起来存在的旧代码

- 日期：2026-11-01（R108）
- 起点：R107 的结论是「同一指标多处实现 → 口径分叉」，顺着这条线扫全仓的重复实现
- 结果：找到 `tools/tools/` —— 21 个文件 / 150 KB 的**整目录旧副本**

---

## 一、怎么发现的

R107 修完 flag 正则后，我想看看还有多少"同一逻辑多处实现"。用 AST 对全仓
387 个文件做函数体指纹（去掉函数名与 docstring，只看结构）：

```
函数体完全相同的组：123
```

123 组太多，其中大部分是无害的工具函数（`sha256()` 写了 12 遍）。

于是收窄到**判定类**函数（名字或体里含 `match/check/validate/verify/classify/...`）：

```
判定类重复组：7
```

7 组里有 5 组的路径长这样：

```
tools/verify_discipline.py:16        validate_improvement()
tools/tools/verify_discipline.py:16  validate_improvement()
```

**不是函数重复，是整个目录被复制了一份。**

---

## 二、这份副本是什么状态

| 项 | 值 |
|---|---|
| 规模 | 21 个 `.py` / 150 KB |
| 真身 | `tools/` |
| 全仓 import | **零**（只有 `core/mcp_adapter.py` 的一行 docstring 提到它） |
| 与真身差异 | 7 处 |

差异方向：**副本是旧的**。

| 文件 | 副本 | 真身 | 差在哪 |
|---|---:|---:|---|
| `adapters/flag_scan_adapter.py` | 120 行 | 136 行 | 缺 `HTB{}` 通用前缀、body 排除 NUL 等 4 项修复 |
| `base.py` | 63 行 | 71 行 | 少 8 行 |
| `adapters/bkcrack_adapter.py` | 214 行 | 216 行 | 少 `import shutil` 与 `shutil.which("bkcrack")` |
| `flag_extract_guard.py` | 95 行 | 94 行 | **副本多一行** `low = text.lower()`——死变量，真身已清理 |

最后一行是这一轮最典型的一笔：**副本里还留着真身已经删掉的死代码。**

---

## 三、仓库其实知道这件事

`pyproject.toml`：

```toml
#   tools/tools/ 整目录排除 —— 历史遗留的重复副本（21 个文件），无人 import
#                （`import tools.registry` 解析到 tools/registry.py 真身），且副本内部
#                自己也是 `from tools.base import ...` 引用真身。待人工确认后清理，
#                本次只排除不删除。
extend-exclude = ["tools/tools", "_archive_defense"]
```

`scripts/_gate_static.py` 也复述了一遍：「`tools/tools/`：历史遗留重复副本，整目录排除」。

**这段注释写得相当负责**：说明了它是什么、为什么无人 import、为什么这次不删。

问题在于最后一句——**"待人工确认后清理"没有承接人。**

- 没有 issue
- 没有 TODO 编号
- 没有任何测试会因为"它还留着"而报警

于是它会一直留着。这不是作者的疏忽，而是所有"临时豁免 + 待办"的通病：
**豁免被记录下来了，待办没有被跟踪。**

---

## 四、真正的风险不是 150 KB

它不占空间、不影响运行、不参与构建。风险在于：

> 有人搜 `flag_scan_adapter` 会找到两份。
> 改错那份**也能跑通**（因为它自己也是 `from tools.base import ...` 引用真身），
> 但改的是**已经过期的代码**。

对比一下两种坏：

| 坏法 | 会不会被发现 |
|---|---|
| 代码不存在 | 会——ImportError 立刻暴露 |
| 代码存在但过期 | **不会**——看起来完全正常 |

**过期代码比没有代码更危险，因为它看起来是存在的。**

再加一层：`flag_scan_adapter` 副本缺的正是 `HTB{...}` 通用前缀。
如果有人在这个副本里排查"为什么 HTB 的题扫不出 flag"，他会得到
"逻辑就是这样"的结论，而真身早就修好了。

---

## 五、处理：不删，但让它不能再害人

删除是不可逆操作，且 `pyproject.toml` 明确说"待人工确认"。所以我不动它，改为**固化现状**：

### `scripts/_check_dead_copy.py`

| 判据 | 内容 |
|---|---|
| **C1** | 全仓**不得 import** 死副本（一旦有人开始用，立刻红） |
| **C2** | 死副本与真身的**差异清单必须可枚举**（不判红，但随时可算出） |

C1 是关键：副本"闲着"无害，一旦被启用就变成"改的是过期代码"。

C2 的理由来自那句"待人工确认后清理"——**可确认的前提是知道差在哪**，
而不是靠人肉 diff。

### 自检（3 项）

```
[PASS] T1 无 import → 无告警
[PASS] T2 变异：import 死副本 → 告警
[PASS] T3 变异：内容分叉 → 检出
```

### 守卫（`tests/test_dead_copy_guard.py`，4 条）

- 全仓无 import（**核心**）
- 副本还在时必须仍被登记
- 差异必须可枚举，且 `flag_scan_adapter` 仍应落后于真身
- `report()` 无 import 时返回 0（不误判）

### 变异验证

在 `core/mcp_adapter.py` 里插一行 `from tools.tools import base`：

```
FAILED test_no_code_imports_dead_copy
FAILED test_report_exit_zero_when_no_imports
2 failed, 2 passed
```

恢复后 4 passed。

## 七、顺手修的一处

`tools/fix_ledger.py` 里有三处 `'\{...\}'` 普通字符串导致的 `SyntaxWarning`。
改成 raw string，现在 `python -W error::SyntaxWarning` 干净。

## 九、三条可复用的

1. **"整目录被复制"的识别信号是路径，不是内容。**
   我在 123 组重复函数里找不出重点，直到看见同一文件名出现在 `X/` 与 `X/X/` 下。

2. **豁免要登记，待办要跟踪。**
   `pyproject.toml` 那段注释是负责的，但它只完成了"登记"，没完成"跟踪"。
   加一个门禁等于补上跟踪——而且是可执行的跟踪，不是再写一句 TODO。

3. **判断"死代码"够不够，要看它会不会被误改。**
   无人 import 只说明它现在不影响运行，不说明它无害。
   只要它还在搜索结果里、还能被 grep 到，就有人可能改到它。
