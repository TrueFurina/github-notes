后端核心改动：

```python
if need_weeks > max_avail:
    # 只在**表内确实放得下**时才给建议：表里就是没有那么多周次时返回 None，
    # 不编造一个照样排不下的起点（那等于把人从一条死路指到另一条）。
    # 注意这**不会自动放宽**窗口 —— 是否接受建议由人点，R-51「时间由教务给定」。
    earliest = all_weeks[0] if all_weeks else start_week
    suggest_start_week = None
    if week_max - earliest + 1 >= need_weeks:
        suggest_start_week = max(earliest, week_max - need_weeks + 1)
    return {"success": False,
            "error": (...原文案一字未动...),
            "need_weeks": need_weeks,
            "suggest_start_week": suggest_start_week}
```

**行为边界（重要）**：报错路径**不自动重试、不自动放宽**。窗口仍然由 `week_min/week_max` 决定（R-51），系统只是把"要调到第几周才够"算出来摆给人看。采用与否由人点。

## 三、过程中被推翻的三个判断（诚实记录）

### 3.1 我的第一次复现是错的 —— 漏传了 `time_slots`

第一次用 `time_slots=None` 复现，得到"每周最多 3 个、需 15 周、连 `start_week=1` 都失败"，与 R50 的"每周 4 个、需 12 周、`start_week=1` 成功"**不一致**。

原因：真实主数据该班 `time_slots = ['567','678','91011','MORNING']`（4 段），
而 `None` 会回退到 `TIME_SLOTS = ['567','678','91011']`（3 段）。
`per_week = min(groups_n, len(slots) * teachers_n)` ⇒ 4 vs 3，需求周数 12 vs 15。

**教训**：复现失败现象时，必须用**与生产完全相同的入参**，否则复现的是另一个 bug。
顺带发现一个可疑数据：`time_slots` 里有个 `'MORNING'`（非 `567/678/91011` 编码），来源与影响未查，留作后续线索。

### 3.2 我的改动一度**加剧了既有红灯**

第一次改完 `App.tsx` 是 1514 行（原件 1509），体量守卫从"既有红"变成"更红"。
已压回 **1509 行，净增 0**（把失败分支压成一行 `setMsg(...)`，注释移到 `client.ts`）。
现状：守卫仍红，但**与原件状态完全一致**，本方案未加剧。

### 3.3 我的改动破坏了 2 个既有前端测试

`views.test.tsx` 断言 `onSolve` 被调用时**只带一个参数**；我把调用改成 `onSolve(cn, startWeekNum)` 后，
留空时会传第二个参数 `undefined`，导致 `toHaveBeenCalledWith('2024级')` 失败。

修法选择：**改代码而不是改测试** —— 留空时走 `onSolve(cn)` 分支（`solveWith` 辅助函数），
保持"不传"与"传 undefined"的语义区别，也守住既有测试。

## 四、为什么建议值必须"只在真能排时才给"

`test_no_suggestion_when_table_really_cannot_fit` 锁的是这条：
表覆盖只有 1..6 周、需要 12 周时，必须返回 `None`。

如果无脑写 `suggest = week_max - need_weeks + 1`，会算出 `6 - 12 + 1 = -5`（负数起点），
前端拿去做一次重试 ⇒ 用户从一条死路被指到另一条死路，且这次连错误文案都是错的。

这与本仓《隐形失效形态归纳》里的 **S9（判据自身腐烂）** 同族：
**一个永远给数字的建议，比不给建议更危险**——因为它看起来像承诺。
