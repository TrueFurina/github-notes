## R52 · 2026-10-31 · API 命名空间被前端兜底吞掉：拼错的接口返回 200 HTML

### 怎么发现的（不是设计出来的）

本轮原定查"500 错误路径有没有留痕"。第一步当然要先看一条真实 500 长什么样，
于是加一条临时路由让它抛异常 —— 打出去，返回的是 **200 + index.html**。

异常没有发生，因为它根本没进那条路由：`@app.get("/{full_path:path}")` 的 SPA
兜底先接住了这个 GET。**要查的是"错误留没留痕"，撞见的是"错误根本没被当成错误"。**

### 缺陷：`/api/**` 的未知路径一律 200 + HTML

实测（修复前，四个路径全部落在兜底路由里）：

| 请求 | 状态 | Content-Type | 实际是什么 |
|---|---|---|---|
| `GET /api/reschedule/parallel/ladn` | **200** | text/html | 拼错的 land |
| `GET /api/reschedule/not-a-real-endpoint` | **200** | text/html | 不存在 |
| `GET /api/reschedule/upload` | **200** | text/html | 只支持 POST 的写接口 |
| `GET /api/reschedule/master/init` | **200** | text/html | **管理员写接口** |
| `GET /api` | **200** | text/html | 命名空间本身 |

三层后果，一层比一层难查：

1. **排查方向被带偏。** 前端 `r.json()` 抛 `Unexpected token '<'`。看到这个报错，
   第一反应是"代理配错了/响应被污染了"，而真相是"这个路径不存在"。
2. **监控看不见。** 日志 `"status":200`、`_COUNTERS["errors"]` 不增、
   `app.http` 也不打日志（它只记 4xx/5xx 与慢请求）。这批请求对运维完全隐形 ——
   与 R35「时段看不懂就整行静默丢弃」、R39「删默认课程返回成功但什么都没删」同族。
3. **写接口被误读成成功。** `GET /master/init` 回 200，抓包看到的人会以为
   初始化执行了。实际什么都没发生。

### 为什么既有测试没抓到

`tests/test_web_serving.py` 文件头第 7 行明明白白写着：

```
- /health、/api/**、/docs、/openapi.json → 不被兜底路由吞掉
```

而对应的用例只测了 `/api/reschedule/status` —— **一条已注册的路径**。

它锁的是"已注册的接口能正常返回"，不是"API 命名空间不吞请求"。这两句话读起来
几乎一样，实际差着一个集合：前者只约束一条路径，后者约束整个前缀。
缺口就在这个差集里，而它恰好是**出错时**才会落进去的地方。

### 改动（`backend/app/main.py`，+17/−1）

`spa_fallback` 里先判命名空间：

```python
if full_path == "api" or full_path.startswith("api/"):
    return JSONResponse(status_code=404,
                        content={"detail": f"接口不存在：/{full_path}"})
```

非 `/api` 的深链接、真实静态文件、路径穿越回落，全部保持原样 —— 一个字节没动。

### 验证

- 后端 **640 passed** / 31 skipped / 0 failed（远端基线 630，+10）
- 手工变异（把守卫改成 `if False:  # MUTANT`）：**6 红 / 4 绿**
  —— 红的 6 条是缺陷本身；绿的 4 条是**反向保护**用例（SPA 深链接、`/`、
  `/index.html`、已注册接口），它们必须在任何情况下都是绿的。
  这条对照很重要：改兜底路由最容易顺手把兜底一起收掉，表现为刷新页面白屏 ——
  线上比原缺陷严重得多。

### 遗留

1. **500 仍然没有异常留痕**（本轮原定主题，被兜底缺陷挤到下一轮）。实测：
   全仓 `exception_handler` / `add_exception_handler` **0 处**，
   `logger.exception` / `exc_info` **0 处**。未捕获异常进 500 时，日志只有
   `{"method","path","status":500,"ms"}` —— 没有异常类型、没有栈，
   响应体是 Starlette 默认的 `Internal Server Error`。
   **"出错了"能知道，"为什么错"完全不知道。** 这是下一轮的正题（含请求 id，
   让前端报的编号能和日志对上）。
2. 17 处 `print()` 仍在用（`⚠️ 主数据落盘失败` 这类运维信号没有级别/时间/上下文，
   也采集不进结构化日志）。
3. 落地/撤销没有审计留痕：教秘问"这个班的课怎么变了"目前答不上来。

### 本轮的教训（两条）

**一、兜底路由是错误路径的隐形杀手，而它的测试最容易写成同义反复。**

`test_web_serving.py` 把"/api/** 不被吞掉"写成了设计意图，用例却只覆盖一条
已注册路径。**测试如果是从"我希望它怎样"翻译来的，而不是从"它在什么情况下会错"
构造来的，就会恰好漏掉那个情况。** 判据要写成可证伪的形式：
不是"status 接口返回 JSON"，而是"**任何** `/api` 前缀的未知路径都不得返回 html"。

**二、查 A 撞见 B，是因为探针问的是"实际发生了什么"。**

本轮要查 500 的留痕，探针却先撞见了"500 根本没发生"。如果我按计划直接读代码、
写一个 exception handler 的用例、跑绿、收工 —— 这个缺陷会原地不动。
**探针的价值不在于验证假设，在于有机会推翻假设。**
