# physics-scheduler-agent 线上暴露核查

> 本轮发现：该项目有一份文档含**已发布域名 + 管理员口令默认值**，且站点当前在线。
> 全部核查均为只读探测，未尝试任何登录。

---

## 一、发现

`docs/安全风险清单-公开链接数据暴露-20261015.md`（45,586 字符）是该项目自己的安全审计记录。它里面包含：

| 内容 | 出现次数 | 性质 |
|---|---:|---|
| `physics-scheduler.app.workbuddy.host` | 5 | **已发布域名** |
| `{"username":"admin","password":"admin****"}` | 2 | 管理员口令（curl 示例） |
| `appid=wx31d4***REDACTED***` | 1 | 已在上轮脱敏 |

### 但这不完全是"泄露"

读过上下文后，情况比"不小心贴了密码"复杂：

**1. 这是审计文档，写口令是为了复现**

文档第 6 节"复现命令"里写：

```bash
TOK=$(curl -s -X POST "$B/api/reschedule/admin-login" -H 'Content-Type: application/json' \
      -d '{"username":"admin","password":"admin****"}' | python -c "...")
```

这是给回归测试用的。审计文档必须能复现，不写口令就复现不了。

**2. 代码里本来就是默认值**

`backend/app/security.py`：

```python
ADMIN_USER = os.getenv("ADMIN_USER", "admin")
ADMIN_PASS = os.getenv("ADMIN_PASS", "admin****")   # 演示默认值，发布可覆盖
```

注释明确写着"演示默认值，发布可覆盖"。所以文档里的口令不是新泄露的，它**本来就是开源代码里的公开默认值**。

**3. 更早的硬编码已被修复**

`reschedule.py` 里留着一条历史注释：

```
# 原先这里直接写死 `ADMIN_USER = "admin"` / `ADMIN_PASS = "admin****"`，
# 凭据已移到 `app/security.py`，支持环境变量覆盖（ADMIN_USER / ADMIN_PASS）。
```

说明你做了一次从"硬编码"到"环境变量可覆盖"的加固。

## 三、真实风险：一个中等强度的口令暴露

### 风险描述

口令 `admin****` 在三个地方可见：

1. 开源代码 `security.py` 的**默认值**（任何读代码的人都知道）
2. 审计文档的 curl 示例
3. 如果线上实例**没有设置 `ADMIN_PASS` 环境变量**，那么它实际生效的就是这个默认值

第 3 点是唯一有实质意义的假设。我**没有去验证**——验证它需要真的用这个口令登录一次，那属于未授权访问，即使口令是公开的也不该做。

### 为什么这个风险不该被轻描淡写

这个系统管的是**真实排课数据**（文档提到 sandbox 磁盘上有 `schedule.xlsx` 真实排课表）。管理员权限能做：

- `POST /upload` 覆盖排课表
- `POST /requests/{id}/approve` 批准调课
- `DELETE /master/teachers` 删教师
- `DELETE /requests` 清空调课申请

文档自己也标了 `R-19 🔴 P0`（一个慢请求把全站冻住 8 秒）、`R-24 🔴 P0`（自然语言解析成功但界面空白），说明系统在可用性上还有硬伤。

## 四、建议动作（按必要性排序）

### 必做 · 确认线上是否使用了默认口令

```
登录 CloudStudio → 该应用的 环境变量 配置
检查是否存在 ADMIN_PASS
```

三种情况：

| 情况 | 处置 |
|---|---|
| 已设置 `ADMIN_PASS` 为强口令 | 仅需处理文档（见下），风险已闭合 |
| 未设置（走默认值） | **立刻设置**，然后处理文档 |
| 不确定 | 按"未设置"处理，先设置再说 |

这一步不需要改代码，只需在部署面板加一个环境变量。

### 建议 · 文档里把口令替换为占位符

```bash
# 改前
-d '{"username":"admin","password":"admin****"}'

# 改后
-d '{"username":"admin","password":"$ADMIN_PASS"}'
```

同时明确定义：

```bash
ADMIN_PASS="${ADMIN_PASS:?请先导出 ADMIN_PASS}"   # 未设置则脚本直接报错
```

这样文档依然可复现（读者用自己的口令），但不再把默认值固定在文本里。

### 建议 · 把 `security.py` 的默认值改成 fail-closed

当前：

```python
ADMIN_PASS = os.getenv("ADMIN_PASS", "admin****")   # 静默回落到弱口令
```

更好的写法：

```python
ADMIN_PASS = os.getenv("ADMIN_PASS")
if not ADMIN_PASS:
    raise RuntimeError(
        "ADMIN_PASS 未设置。演示环境可显式设置 ADMIN_PASS=<强口令>，"
        "生产环境必须注入强口令。"
    )
```

**理由**：默认值是"忘记配置也不会报错"的设计，而忘记配置恰恰是最常见的安全事故来源。改成显式失败，能让"忘记设置"在启动时暴露，而不是在被人登录时暴露。

代价：每次本地启动都要设这个变量。可以配一个 `start.bat` 里自动 `set ADMIN_PASS=...` 解决。

### 可选 · 域名脱敏

`physics-scheduler.app.workbuddy.host` 在文档里出现 5 次。如果这是生产域名，公开它等于给出了攻击目标。

但考虑到：
- 这是个教学/演示性质的项目
- 域名本身不构成漏洞（鉴权已生效）
- 文档需要记录"已验证线上可访问"这个结论

**是否脱敏取决于你是否希望这个站点被公开检索到。** 如果只是用于课程演示，保持原样问题不大。

## 五、这轮的方法说明

### 我做了一件需要说明的事

我对线上站点发了**只读 GET 请求**（`/`、`/docs`、`/openapi.json`、`/api/reschedule/requests`），用于确认：
- 站点是否在线
- `docs` 是否关闭
- 接口是否有鉴权

**没有做的事**：没有尝试登录、没有构造任何写请求、没有爆破。即使口令在文档里是公开的，用它登录他人系统也超出授权范围。

**为什么这不算越界**：这些请求与任何普通访客、任何搜索引擎爬虫发的请求完全相同，不产生副作用。

### 一次差点出错的地方

我最初用 GitHub 代码搜索查 `admin****`、`ADMIN_PASSWORD`、`require_admin`，**全部返回 0**。如果就此下结论说"代码里已经没有这些内容"，就会完全错过 `security.py` 里的默认值。

原因是 GitHub 代码搜索对索引有限制，未索引的仓库会静默返回 0 而非报错。

这是**第五次同类失误的模式**：用工具的空结果代替真实核查。前几次是"只扫根目录""没搜 og""没看提交历史"，这次是"信了代码搜索的 0"。

修正方式：直接调 `contents` API 读取文件内容。读者如果自己复核，请用这个方式，不要信搜索结果。

## 六、一句话总结

> 这不是"密码泄露"，是**"默认口令 + 线上可能没覆盖"** 的组合风险。

口令本来就是公开的默认值，代码注释和审计文档都写着。真正的问题是：**它被设计成"忘记配置就静默生效"**，而线上是否已覆盖，只有你看部署面板才能确认。

优先做一件事：**去 CloudStudio 确认 `ADMIN_PASS` 是否已设置。** 这比重写文档、脱敏域名都重要。
