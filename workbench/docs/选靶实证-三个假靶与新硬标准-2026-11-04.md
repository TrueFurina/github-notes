## 2. 三条新硬标准

1. **低 open-PR 数有三种成因，绝不能只读数字**：
   ①拒绝外部贡献（`openai-agents-python` 的 CONTRIBUTING）；
   ②维护者合并极快（Box）；③维护者主动清理 agent 边角 PR（tinycss2）。
   必须结合「最近 20 个 PR 的 merged 比例」「closed PR 的关闭评论」「issue timeline」判断。
2. **选靶要读 Code of Conduct / 贡献指南全文，不只看 CONTRIBUTING**：
   重点查「是否要求先开 issue 得到许可再发代码」「是否要求真实使用场景」
   「是否限制同一时期 PR 数量」「是否限制 AI 生成内容」「PR 该进哪个分支」。
3. **判重三连**：issue 列表 + open PR + **closed PR / issue timeline**。
   Box 证明「open PR 少」不等于「没人做过」。

## 3. 方法论边界（重要）

双轨法第①轨「差异/往返预言机 fuzz」的价值是**证明核心没坏**，
不是拿边角结果去开 PR。本轮对 `tinycss2.serialize_nth` 穷举
`a, b ∈ [-6, 6]`（169 组）全部往返通过，超大整数（10³⁰）也正常
→ 干净的负结果，记录但不提交。

把「fuzz 找到的不一致」直接包装成 PR 会消耗 maintainer 耐心——
tinycss2 是真实反例。此前笔记里「成熟库纯随机 fuzz 几乎必是干净负结果」
是对的，这里补上了「即使不是干净负结果，也可能属于对方不欢迎的贡献类型」。

- 已 merged 的 3 个（agent-memory #118 / #119 / #120）与刚开的 ludic #151，
  **全部来自读源码做安全/正确性审计**、找到**有真实用户影响**的 bug：
  凭据漏拦、围栏内标题误判、frontmatter 注入、属性截断 / 事件处理器注入。
- 本轮所有「扫 issue 列表」的尝试全部撞红海。
- → **下一轮优先「源码审计 + 真实场景」，而不是「扫 issue」**。

## 5. 开 PR 前预检清单

1. 读 CONTRIBUTING **+ CoC / 贡献指南**，确认接受外部 PR、无需先问、
   无「一次一个 PR」冲突、PR 目标分支正确。
2. 看最近 20 个 PR 的 merged 比例与关闭评论，判断 maintainer 对哪类贡献感兴趣。
3. 扫目标 issue 的 timeline：open PR、closed PR、是否已被修过或拒绝过。
4. 确认 bug 能在**真实调用路径**中触发（不是纯 fuzz 构造出来的边角）。
5. 任一条不满足 → 换靶，不硬凑。
