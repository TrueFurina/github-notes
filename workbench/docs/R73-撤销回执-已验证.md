# R73 · 撤销回执：撤的是哪一次、撤销之后还剩什么（已验证）

> 轮次：R73（第二期自动化链，接在 R62 之后）
> 起点基线：pytest 768 / 32 / 0、测试文件 80、变异 56/56、前端 21 文件 156 条、ruff 0
> 结论：**已修**，`/parallel/land/undo` 成功分支现在回 `message`（`plan_landing.undo_receipt`），
> 前端改为原样透传。commit `2a93cc20ed`（父 `20315dabff`），CI run `41447736891`。

## 一、这轮修的是哪条缝

R60 给 `/parallel/land` 补了 `landing_receipt`，R61 给撤销失败补了两型分型。**但撤销成功
那一步一直是"字段裸奔"**：端点只回一堆数字，界面自己拼一句话。这句话漏掉的东西，
在真实操作序列下会直接骗人。

这不是"文案不够漂亮"，是**同一屏出现两句互相打脸的真话**。

## 二、取证（先跑出来，再动手）

用 `D:\github\R73-new\probe_undo.py`（不进仓库，全程临时 sqlite）：

```
第一次落地 A → 200，keys 里有 message
第二次落地 B → 200，message = "✅ 已落地 1 条方案行…🕒 20:22:52，由 admin 落地"
插一条 landed_at 之后的 applied_moves
撤销一次      → 200，keys = [landed_actor, landed_at, restored_entries, revoked,
                             revoked_at, revoked_by, revoked_id, rolled_back_moves, success]
                has message? False        ← 缺口①
撤销之后 /land/status → {'landed': True, 'landed_at': '20:22:52.745900', ...}
                                          ← 缺口②：更早那次仍在生效
库里剩两条：id=2 revoked=True（刚撤的）、id=1 revoked=False（更早那次）
界面此刻只会说：↩️ 已撤销落地，安排表恢复到 2 条；一并回滚了…1 条调课（需重新审批）
```

三个缺口，按代价排序：

1. **不说撤的是哪一次**。连着落两次之后，教秘要确认的恰恰是"我撤掉的是不是刚才那次"。
   `landed_at` / `landed_actor` 就在响应里，界面一个都没念。
2. **不说撤销之后还剩什么**。撤销是"弹一条"，不是"清空"：更早那次落地仍然生效，
   `status.landed` 依旧 `True`，面板下半部分照旧显示"当前安排表已是落地方案（更早那次的时刻）"。
   横幅说"已撤销"、状态栏说"已落地"，两句都真 —— 教秘的结论会是"回到了原始状态"，
   然后照着这个错误前提去重新落地。
3. **不说回滚掉的调课要怎么办**。"需重新审批"四个字是前端硬编码的，字段一改名就静默消失。

## 三、改法

### 1）新增纯函数 `plan_landing.undo_receipt(out, remaining=None)`

与 `landing_receipt` 对称，只读入参、不碰 db：

- 首句点名：`↩️ 已撤销 2026-11-02 20:22:52 那次落地，由 admin 落地`；操作人缺失时写
  `（该记录没有留操作人）`，不留一个"由  落地"的空洞。
- **有更早落地时不许说"已回到落地前"**：改说
  `安排表现 N 条 —— 更早那次的落地结果，不是原始状态`；没有时才说
  `安排表已回到落地前的状态（现 N 条）`。
- `rolled_back_moves > 0` 才点名：`⚠️ 一并回滚了落地后生效的 M 条调课 —— 这些申请需要重新审批，
  不会自动重放`。0 条时一个字都不提（"回滚了 0 条"是噪声，还会让人以为出过事）。
- 还有更早落地时补一行 `ℹ️ 更早的一次落地（时刻，由 X 落地）仍然生效：撤销入口还在，
  要回到更早的状态就再撤一次`。
- 收尾 `🕒 撤销时刻，由 X 撤销`；`revoked_at` 缺失就不画时钟行。

### 2）端点把它挂上（`land_undo`）

```python
with _land_lock:
    out = plan_landing.undo(_db, _landings(), actor=actor or "")
    if out.get("success"):
        out["message"] = plan_landing.undo_receipt(out, remaining=_landings().latest())
```

`remaining` **在锁内读**：锁外读会被并发落地插队，回执说的就不是"这次撤销之后"的状态。
失败分支（404 / 500）原样不动，R61 的分型不受影响。

### 3）前端不再自拼

`LandPlanPanel.doUndo` 改成 `onMsg(r.data.message || 兜底文案)`，兜底保留原来那句
（老后端没有 `message` 时不会更差）。`types.ts` 的 `LandUndoResult` 新增可选 `message`。

## 六、全量变异 56/56（以及这轮踩的两个仪器坑）

- **56/56 检出**（7 批 × 8，每批独立一次 shell 调用）。
- 🔴 **第 8 次仪器教训（自伤式"复原"）**：`_r73_mutrun.py` 收尾的"复原"复用了
  `sys.argv` 里的 `V1`，于是那句 restore 其实是**再打一次变异**：锚点已不存在 ⇒ 打印
  `ABORT hits=0`，而文件**仍带着变异**。我只看 `tail -4` 那一行 ABORT，以为没事；
  直到后面所有锚点都 hits=0 才发现树被污染。现在：收尾显式设 `restore`，
  前后各打一次 md5，复原后强制核对 `pl_matches_backup`。
- 🔴 **第 9 次仪器教训（统计行被环境吃掉）**：批量跑时 4 个变异体被判
  `无效 · pytest 退出码 1: ?`。手工单跑同一个 M1 立刻拿到
  `8 failed, 1 passed, 76 deselected`。根因不是测试，是**pytest 的临时目录垃圾累积**
  （`pytest-of-Administrator/garbage-*` 超过 50 个）触发本机清理钩子，子进程在打印汇总行
  之前被杀 ⇒ 抓不到 `N failed` ⇒ 框架按"退出码非 0 且无统计行"判无效。
  解法：每批给一个**独立的 `TEMP`/`TMP` 目录**，8/8 立刻恢复。
  → 推论：**本机任何"pytest 统计行缺失/rc=1 但 junit 0 failed"都不是测试失败**，
  一律先查这个，别去怀疑用例。

## 八、边界与没做的事

- 只修**撤销成功**这一支；失败两型（R61 的 404 / 500）没动。
- 回执只描述"撤掉了哪一条、现在剩什么"，**不解释为什么会有更早的落地**（那是操作历史，`/land/history` 的事）。
- 没有把 `remaining` 塞进 `undo()` 的返回值，而是在端点里另读一次 `latest()`：
  `undo()` 的契约不动，避免连带影响 R55/R61 的用例。
- **真实 sqlite 锁**（重试那一支）仍未用真锁验证，目前只有 monkeypatch 版本 —— 遗留项。
- 未测跨机器可复现（与 R62 同一边界）。
