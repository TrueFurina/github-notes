## 一、代码规模实测

| 仓库 | 总文件 | Python 文件 | 测试文件 | docs 文件 | 真实体量 |
|---|---:|---:|---:|---:|---|
| `SecAutoMind-src` | 3,914 | 1,072 | 217 | 328 | 最大，Go + Python 双栈 |
| `MARS-408` | 2,058 | 943 | 225 | 100 | 次大，Vue3 + Python |
| `xihu-sword-ctf-agent` | 1,067 | 605 | 220 | 5 | CTF 专用，测试密度最高 |
| `AGI-Distiller` | 258 | 26 | 1 | 0 | **最小，但 Star 最高（9）** |
| `passive-recon` | 202 | 127 | 26 | 11 | 工程质量最均衡 |

**一个反直觉但重要的观察**：Star 数与代码量**负相关**。

- `AGI-Distiller`：26 个 py 文件 → 9 Star
- `SecAutoMind-src`：1,072 个 py 文件 → 1 Star

这不是巧合。`AGI-Distiller` 之所以能拿到最高 Star，是因为它**讲了一个别人能一句话复述的故事**（"自进化的知识蒸馏系统"），且体量小到可以被读完。`SecAutoMind-src` 有 3,914 个文件，访客打开就关掉了。

**结论**：Star 不奖励代码量，奖励**可理解性**。这条直接决定了下一步该做什么。

## 二、MARS-408：三份完全相同的代码副本

用 git blob SHA 做内容级比对，结果很明确：

- Python 文件总数 943
- **内容完全相同的重复组：283 组**
- **涉及文件：817 个（占 87%）**
- **跨顶层目录重复：283 组（全部）**

三份副本分别是：

```
py-server/                                          ← 主开发目录
deliverables/MARS-408 考研多智能体个性化学习系统/源码/py-server/   ← 交付物副本
submission/04_源码/MARS-408_source/py-server/        ← 提交物副本
```

体积分布也印证了这一点：

| 目录 | 体积 | 性质 |
|---|---:|---|
| `deliverables/` | 56.3 MB | 交付物副本 |
| `submission/` | 54.6 MB | 提交物副本 |
| `py-server/` | 13.0 MB | **真实源码** |
| `references/` | 12.9 MB | 参考资料 |

**真实源码只有 13 MB，另外 111 MB 是同一份代码的两份拷贝。** 仓库 111 MB 中约 87% 是冗余。

这带来三个具体后果：

1. **克隆成本**：任何人 `git clone` 要拉 111 MB，只为看 13 MB 的代码
2. **改代码会改错地方**：三份副本内容相同但路径不同，新人（或三个月后的你）不知道该改哪个
3. **测试会被误导**：225 个测试文件中，72 个在 `deliverables/`、72 个在 `submission/`、80 个在 `py-server/`——同一批测试跑三遍

**`SecAutoMind-src` 有同样问题**：1,072 个 py 文件中有 270 个处于 135 组重复中，`CTF-Agent_融合/` 与 `Security-Agent_融合/` 是两条并行副本线。

## 三、`AGI-Distiller` 为什么值得优先做

它是 Star 最高的项目，但结构上**不是软件项目，是 Claude Skill/Plugin 包**：

```
.claude-plugin/     hooks/      rules/      skills/
skills-drafts/      skills-drafts-archive/   templates/   tools/
golden/             notes/      sources/
```

- 无 `pyproject.toml` / `setup.py` / `README` 安装段
- 无入口脚本（`main.py` / `cli.py` / `__main__.py` 全无）
- 26 个 Python 文件全是辅助脚本（`golden/call_model.py`、`hooks/commit_gate.py` 等）
- `skills-drafts/` 与 `skills-drafts-archive/` 并存

**它的真实定位**：一个可被 Claude Code 加载的 Skill 集合 + 自评测框架（`golden/` 下有 `compare.py`、`graders.py`、`semantic_judge.py`）。

这个定位**其实很好**，比"又一个 RAG 项目"稀缺得多。问题只是**没有按这个定位来包装**：

- README 讲的是"活的知识蒸馏系统"，而不是"一个可安装的 Claude Skill 包"
- 没有 `install` 指引（应该是 `git clone` 到 `~/.claude/skills/` 或插件市场）
- 没有一张截图展示"装上之后能干什么"

**这是投入产出比最高的一件事**：不用写新代码，只需重写 README 顶部 30 行 + 加 2 张截图 + 删掉 `skills-drafts-archive/`。

## 四、`passive-recon` 是最被低估的项目

对比来看，它是**唯一一个五项全绿**的仓库：

| 维度 | 状态 |
|---|---|
| 结构 | `passive_agent/` 分包清晰（ai/ api/ gateway/ collector/） |
| 测试 | 26 个测试文件，按模块分布（`tests/api`、`tests/gateway`） |
| 文档 | 11 个 docs 文件 + 双语 README |
| 部署 | Dockerfile + docker-compose + CI |
| 发布 | 有 Release + Tag + homepage |
| 定位 | OSINT/EASM/CTEM，15+ 数据源，与你的安全主业强相关 |

它的问题**不是工程质量，是曝光**：7 Star。作为一个"纯被动 OSINT 平台"，这个品类在 GitHub 上有稳定需求（参考 `smicallef/spiderfoot` 23.9k Star，而你恰好给 spiderfoot 提过 7 个 PR）。

**建议**：`passive-recon` 应该是你的主推项目，而不是 `AGI-Distiller`。理由：它有真实使用场景、有部署路径、有对标物（spiderfoot）、且能承接你在 spiderfoot 上的贡献者身份。

## 六、一个贯穿性判断

你的仓库有一个共同的模式：**把"过程"和"产品"放在同一个仓库里**。

- `MARS-408`：源码 + 交付物 + 提交物 + 参考资料 混在一起
- `SecAutoMind-src`：CTF-Agent + Security-Agent + PPT + data 混在一起
- `AGI-Distiller`：正式 skills + `skills-drafts` + `skills-drafts-archive` 混在一起
- `xihu-sword-ctf-agent`：`ctf_agent/` + `deliverables/` + `plans/` + `idea-stage/` + `2027-prep/` 混在一起

这是**做项目**的思维（一个项目一个文件夹，什么都往里放），不是**做产品**的思维（一个仓库一件事，过程物走 CI artifact 或独立归档仓）。

这个习惯的直接代价就是上面所有数字：87% 的重复代码、111MB 的克隆成本、访客的困惑。

**改法只有一条**：源码仓库只放源码。交付物（docx/pdf/PPT/截图）走 Release 附件，过程物（plans/idea-stage/drafts）走独立私有归档仓。这一条如果贯彻，前面列的多数问题会自动消失。
