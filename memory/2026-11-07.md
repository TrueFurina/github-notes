**本轮 3 次 oracle 假阳性（再次印证「先怀疑 oracle」）：**
1. 初版 harness 用 `F.packb`/`F.unpackb`——fallback **无模块级 packb/unpackb**（只有 `Packer`/`Unpacker` 类）+ 误传 `strict=` kwarg 不被接受 → `fails=20000` 整场误报。改走类 API + 去 `strict` 后 0。
2. 边缘 harness 把「两侧同抛异常」也算 fail——越界整数（`2**64`）、孤代理、datetime(无 `datetime=True`) 本应**两侧同拒**，却被记成发散。改 exc_agree（同异常类=一致）后 0。
3. 流式 harness 误调 `F.loads`（fallback **无 loads**）→ AttributeError，冒充「fallback 抛 AttributeError vs C 抛 ValueError」的发散。实根因是 oracle 调了不存在的函数；`F.Unpacker` 实际抛与 C 同义的 `ValueError`("int is not allowed for map key")。改走 `F.Unpacker` 后 0。

**教训加固**：差异 fuzz 的 oracle 必须**精确匹配被测库的 API 形态**（fallback 是类式、C 是模块式；两者公开函数名不同）。任何「发散」先确认 oracle 不是因 API 误用/异常类差异而误报——累计已十余次。
