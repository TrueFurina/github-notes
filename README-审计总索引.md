**这是我在该账号下见过的工程纪律最强的仓库**：它已经把「判据自身必须能被变异打穿」

## 九、marl-ecdsa 深度审计（2026-11-01）

详见 **`marl审计报告.md`**。审计方向：**密码学实现**（出错代价最高处）。

| 维度 | 结论 |
|---|---|
| 数字登记与复算口径 | ★★★★★ 189 条目，指纹自校验（复算一致） |
| 历史口径诚实度 | ★★★★★ 保留作废数字，注明「改历史数字等于伪造历史」 |
| 自我批判文化 | ★★★★★ 注释里明写「会造成虚假安全感」 |
| **密码学守卫强度** | ★★☆☆☆ **k 重用检测有三个可绕过点** |

### 核心发现：同一个函数里的三条失效路径

ECDSA 中同私钥重用 k → r 相同 → **私钥可代数推导**。这个检测是整个模块存在的理由。

1. **淘汰后重用被放行**（最严重）：`MAX_R_ENTRIES=1000` 满后 FIFO 挤掉最旧的 r，
   被挤出的 r 再也想不起来。实测 `MAX_R_ENTRIES=3` 时 `0→1→2→3→0` 第二次 r=0 **放行**。
   修复：淘汰入摘要档案，再次出现照样拦下。
2. **全局淘汰可被灌包利用**：另一份同名 `_trim_r_registry` 按**全局配额**从「条目最多

3. **签名包缺 r 即绕过**：`if r is None: return True`。按用户决策改为**分场景**：
   带 `signature_hex`/`s` 拒绝，无签名包放行。

**新增设计判断**：安全守卫的"可选字段"不能由**被检查方**单方面声明。
r 是否必填取决于这个包是否声称被签过——判定只看包自身字段，不看全局开关。

2. 协议靠换行分帧却无长度上限 —— 客户端持续发无 `\n` 数据即可无限撑大 buffer。

3. `set_config` 接受任意 key —— `get_config` 刻意排除 `github_token` 却允许**写入**它，
   形成"能写不能读"。修复：白名单，只放偏好项，不放监听面/请求端点/凭据。

第一版 5 条测试全绿，但变异验证时**解码和上限两个变异都没被抓到**——因为那 5 条
只测了"解码算法的等价复刻"和"常量存在性"，绕开了 `_handle_client`。
**我在前几轮反复批评的「空转守卫」，自己又犯了一次。**
补 2 条真走调用链的端到端测试后，三个变异体全部精确捕获。

**教训固化：测试必须打在调用链入口上；等价复刻只能证明算法对，不能证明接进去是对的。**

| 文档诚实度 | ★★★☆☆ 注释详实，但网络这一层完全没提 |

`build_bwrap_argv()` 只 unshare pid/ipc/uts，**没有 `--unshare-net`**，

最值得注意的细节：`test_bwrap_shell.py:153-155` **逐条断言了三种 unshare，

| 方案 | 后果 |
|---|---|
| 默认改断网 | 既有 skill（git clone/pip/curl）**静默失效** |
| 默认不变 + 显式开关 + 告警 | 行为不变，风险被暴露 |

选后者。把默认改成断网会制造另一种"看起来正常"的坏：命令跑了、退出码 0、
但没网络所以什么都没拉到——比"沙箱不隔离网络"更难排查。

三态实现：`None`(旧行为+告警) / `True`(联网) / `False`(断网)。

`__init__` 里最初写 `self._allow_network = bool(allow_network)`，
会把 `None` 压成 `False` —— **所有既有调用悄悄从联网变断网**。

8 条测试 + 3 变异体全捕获。

## 十七、方法论交付：隐形失效的七种形态（2026-11-01）

详见 **`隐形失效形态归纳.md`** + 工具 **`tools/audit_probe.py`**。

**为什么换个做法**：前十一轮在同一批仓库里反复撞见同样的失效模式。
与其继续逐个仓库报，不如把形态归纳出来、做成能复用的判据。

### 一句话

**这些缺陷的共同点：代码能跑、测试能过、CI 是绿的，但守卫其实没在守。**
它们不会被普通测试发现——因为"测试通过"就是它们伪装成的状态。

### 七种形态

| 形态 | 一句话 | 代表案例 |
|---|---|---|
| S1 静默降级 | 失败与正常走同一条路 | xihu：静默降级 + 空转守卫 = 事故不可见 |
| S2 空跑即通过 | `空` 有歧义：真没问题 vs 根本没验 | distillery：三处，且三个消费方都渲染成绿灯 |
| S3 守卫空转 | 存在、能跑、是绿的，但判别力为零 | xihu：那条回归锁**永远不可能通过** |
| S4 默认值无出处 | 常数没人知道为什么是这个值 | aerorider `alpha=10` vs `PENALTY=2` |
| S5 隔离不完整 | 测了三种 unshare，第四种没有 | octop：文件关了，网络开着 |
| S6 文档落后 | docstring 说的代码没做 | mcphub：声称写 README，实际只写 registry |
| S7 边界缺口 | 流式 I/O 的切分与上限 | devradar：跨 chunk 丢消息 + 无上限 |

**S4 的共同点值得单列**：这三种都是"**默认值从未被审视过**"，而不是"故意选错"。

## 二十、自测覆盖率门禁：守所有门禁的存在性（2026-11-01）

详见 **`自测覆盖率门禁.md`**。起因是 R104 提出"应该把自测覆盖率做成门禁"。

### 为什么这条比别的门禁值钱

其他门禁守**代码对不对**；这条守**守卫还在不在**。

一个仓库可以有 60 个门禁全绿，但其中一半判据没人验证过它会不会失败——
那 60 个门禁和 60 行注释没有区别。

### 设计：三选一，都必须表态

**A** 有 `_test.py` ｜ **B** 自带 `--self-test` ｜ **C** 豁免表登记 **+ 写明理由**

三者都不是 → 红。豁免理由有长度下限，防"跳过"两字了事。
另有反向检查：豁免表里有已不存在的脚本名 → 红（防表腐朽）。

**为什么不用机器猜"它需不需要测试"**：`verify_demo_readiness` 要连真服务器、
`check_dual_repo_coherence` 要两个仓库同时在场——这些只有人知道。
**让门禁去猜，不如让人来签字。**

### 两个仓库的实测

| 仓库 | 校验脚本 | A | B | C | D缺口 |
|---|---:|---:|---:|---:|---:|
| SecAutoMind | 36 | 27 | 4 | 5 | **0** |
| xihu（移植后） | 31 | 12 | 1 | 18 | **0** |

xihu 那 18 条豁免里，**3 条写的是 `TODO 应补自测`** ——
这是它与普通"跳过"最大的区别：**明确标出"我知道该补，还没补"。**
一份全绿的豁免表反而是可疑的。

### 实际补上一个

`_verify_presolve_truth` 的判读逻辑原埋在三目嵌套里，无法单独测。
抽成 `classify()` 后四类边界成为可断言的：

| 类别 | 为什么必须分开 |
|---|---|
| `MATCH` | 唯一"可验证解出" |
| `NO_GROUND` | **不能算解出**，只能算待核验 |
| `EXTRACT_BAD` | 最危险：给出了**错答案**，不是解不出 |
| `MISS` | 需要 LLM 或独立攻击链 |

**`NO_GROUND` 与 `MATCH` 合并计数，正是口径虚高的来源**——
"题库没真值所以无法反驳"被算成"解出来了"。

6 条守卫；变异验证：`NO_GROUND→MATCH` 弄红 3 条，`EXTRACT_BAD→MISS` 弄红 2 条。

### 规律

有自测覆盖的仓库（SecAutoMind / distillery / AGI），我找到的缺陷都在
**"判据没想到的角落"**；没有自测覆盖的 9 个仓库，缺陷往往是
**"判据本身错了"**。前者可以修，后者得先让人知道它在哪。

## 二十二、口径分歧：同一个 flag，两套正则，两种结论（2026-11-01）

详见 **`口径分歧.md`**。

### R106 与 R107 是同一枚硬币的两面

| | R106 | R107 |
|---|---|---|
| 形态 | 无真值时 `return True` | `\{(.+)\}` 贪婪匹配 |
| 后果 | **高估**解题率 | **低估**解题率 |
| 机理 | "没法反驳"算成"答对了" | "答对了"判成"答错了" |

### 全仓 9 处同样的提取逻辑，5 处贪婪 4 处非贪婪

候选 `the answer is flag{correct_one} (hint: {not_this})`：

| 实现 | 提取的内文 | 判定 |
|---|---|---|
| 贪婪 | `correct_one} (hint: {not_this` | 判**错** |
| 非贪婪 | `correct_one` | 判对 |

**答对的题被判成答错。**

最尴尬的一条证据：`_audit_truth_consistency` 的 docstring 写着
「与 `_stratify_external_benchmark` **完全同口径**（直接复用），避免判决漂移」，
而它自己用非贪婪、"被复用的那个"用贪婪——**它自己就是漂移源**。
（意图完全正确，但实际是复制粘贴后改了一个字符。）

### 为什么贪婪一定错

flag 内文不含花括号——`flag_checker.validate` 里就写着 `f.count("{") != 1 → 拒绝`。
既然内文不可能含 `}`，非贪婪是唯一正确解。

**例外**：`ctfplatform/dasctf.py` 的 `^...\{(.+)\}$` 是**全串锚定**，
贪婪不会跨出结尾 `}`，行为正确、不改。测试专门为它写了一条反向断言：
哪天有人去掉 `^...$`，那条测试会红。

### 修复与守卫

4 处改非贪婪；9 条守卫（5 参数化 + 1 反向自检 + 3 行为级）。
变异：三处各自改回贪婪，分别弄红 1 / 1 / **2** 条。

### 排除的两个假象

1. 定向扫描命中 5 处，逐条读后**全是误报**（都是 `return False`）。
2. 全量回归 1 个失败（`test_xor_bruteforce_fallback`）：单独跑 5/5 绿，
   且与我改的文件**零交集**——判为既有资源竞争波动，不算回归。

### 最想留下的不是那 4 个字符

而是这两条检查：

```python
def test_both_scripts_agree_on_no_truth_semantics()
def test_no_greedy_inner_brace_in_verdict_paths(rel)
```

**它们不验证"某个实现对不对"，而是验证"多个实现彼此一致"。**
后者是单点测试永远覆盖不到的一层。

## 三十二、同一个 CRT，三种脾气（2026-11-01）

详见 **`同一个CRT三种脾气.md`**。R116 只查了 3 个概念，这轮改成**自动提取**。

### 两种自动方法，只有一种有效

| 方法 | 结果 |
|---|---|
| A：跨文件**同名**函数 | 111 个，`classify` 7 处——但**语义全不同**，假设不成立 |
| B：**函数体指纹**（异名同体） | 6 组，`crt`/`_crt` 才是真的复制 |

> **同名不同义很常见，异名同义才是复制粘贴的指纹。**

### 三处 CRT 的语义对照

| 实现 | 模数个数 | 非互素 | 无解 |
|---|---|---|---|
| `crypto_hastad_broadcast._crt` | **任意** | gcd 降模 | 返回 `None` |
| `_solve_10733.crt` | 2 | **抛 ValueError** | 抛异常 |
| `crypto_high_exponent._crt` | 2 | **抛 ValueError** | 抛异常 |

实测 `crt(2,6,5,9)`（gcd=3 但有解）：两模数版**抛异常**，通用版返回 `(14,18)`。

### 当前安全，但只是"碰巧"

两处两模数版本的调用方都是 RSA 的 `(p,q)`——不同素数必然互素。
但这是**调用方的保证，不是函数的保证**：签名没说、docstring 是空的、
报错是 `pow()` 抛的 `base is not invertible`，**看不出跟 CRT 前提有关**。

修复：写明 `**前提：gcd(m1, m2) == 1**`，非互素时报错**指向出路**
（`请用 crypto_hastad_broadcast._crt`）。

> **报错要指向出路。只说"必须互素"不够——用户想知道"那我该用什么"。**

### 我的测试第四次空转

`with pytest.raises(ValueError)` —— 去掉我的检查后，`pow()` **自己也会抛 ValueError**，
测试照样绿。它分辨不出"我们的守卫"和"底层的偶发错误"。

改成断言错误消息特征（含「互素」且指向 `crypto_hastad_broadcast`）后：`1 failed, 6 passed` ✅

## 三十三、顺序即功能：hex 被 base64 抢先解码（2026-11-01）

详见 **`顺序即功能.md`**。R117 的"异名同体"判据做成检测器后，扫出真实缺陷。

### 找到 3 处同功能实现

```
_try_decode         skills/base64_multilayer.py:36          ← CTF 解题链路
_try_base_decode    tools/adapters/deterministic_decode_adapter.py:195  ← 工具链路
_inline_multilayer_decode  agents/crypto_toolkit.py:950     ← 第三份
```

前两份**函数体 830 字符逐字相同**。第三份注释写着「**替代有 bug 的 base64_multilayer**」。

### 实测出的缺陷

```
输入 "666c61677b6865787d"   （"flag{hex}" 的 hex）
  skills/base64_multilayer → '뮜�^�������'
  crypto_toolkit           → '뮜�^�������'     ← 同一个错
```

**两个都错。**

### 根因：hex 是 base64 的真子集

`"666c61677b6865787d"` 长 18，`18%4=2`，补 `==` 后是合法 base64。
解出 `뮜�^...`，**其中有字符满足 `isprintable()`**，于是通过检查、提前 return。
**永远走不到 Base16 分支。**

> **这个误判是结构性的，不是偶然**——`0-9a-fA-F` 全在 base64 字母表里。

### 修复：按特异性排序

判定越严格的越先试：**Base16（全 hex + 偶数长）→ Base32 → Base64**。

| 输入 | 前 | 后 |
|---|---|---|
| hex | `'뮜�^...'` | `'flag{hex}'` ✅ |
| base64 / base32 | 正常 | 正常 ✅ |

### 守卫 11 条（2 源码 + 3 行为 + 5 跨区 + 1 能力边界）

**源码层踩了坑**：用 `find("# Base16")` 定位，但 `_strip_comments` 把注释剥了 → `-1`。
改用代码特征 `bytes.fromhex` / `b32decode` / `b64decode` 定位。
→ **R117 的教训再验一次：断言要找代码特征，不是注释痕迹。**

**跨区一致 5 条**：同一输入，skills 与 tools 两条链路必须同答案。

**能力边界 1 条**：把"agents 版更强"写成断言，防止有人以为三者等价。

变异：`if False:` 掉 Base16 → 2 failed，hex 又变回乱码 ✅

### 三条可复用的

1. **顺序是功能，不是排版。** `try A; try B` 看着像并列，实际是优先级；A 的条件比 B 宽松时 B 永不执行。
2. **注释里"替代有 bug 的 X"要当真**——但它只修了一半，bug 在两处活了下来。
3. **"功能更强"和"功能正确"是两件事。** agents 版加了循环和 ROT13，但 base16 那条分支的 bug 原样继承。
   **扩展一个错误的实现，错误会一起扩展。**
